# Building WorkFlow 과거 작업 내용 분석

- 작성일: 2026-08-12
- 분석 대상: 저장소 루트의 현재 문서, 2026-07-01~2026-07-04 Git 이력, 과거 단계 회고 문서, 당시 작성한 리서치 보고서
- 작성 목적: 이 프로젝트에서 과거에 무엇을 만들고 조사했는지, 왜 그런 작업을 했는지, 어떤 실패를 겪었는지 기록한다.
- 제외 범위: 비밀·자격 증명 파일, 외부 제품 정보의 현재 시점 재검증

## 1. 핵심 요약

- 이 프로젝트는 **Claude, Codex, Gemini 같은 AI 에이전트와 MCP·에이전트 프레임워크를 안전하게 평가하고 활용하는 공통 작업 체계**를 만들기 위해 시작됐다.
- 처음에는 Codex가 다른 에이전트를 호출하고 여러 작업을 자동 조정하는 큰 자동화 시스템을 구상했다.
- 실제 사용 과정에서 작업 큐, CLI 래퍼, 다단계 오케스트레이터, 주간 자동 보고는 규모에 비해 복잡하고 충분히 검증되지 않았다고 판단해 제거했다.
- 이후 Claude가 조사를 주도하고 Codex는 필요한 경우에만 교차검증하는 **요청형 리서치·평가 프로젝트**로 축소됐다.
- 최종적으로 남은 것은 실행 프로그램보다 규칙, 보안 정책, 출처 평가 기준, 체크리스트, 역할 프롬프트, 결과 스키마, 조사 기록이다.
- 루트 Git 작업은 2026-07-01부터 2026-07-04까지 11개 커밋에 집중돼 있으며, 그 뒤 관련 작업은 `Workspace/`의 별도 프로젝트들에서 이어진 흔적이 있다.

## 2. 사용자가 제시한 핵심 의도

이 절은 초기 기획 문서, 당시 handoff, 사용자가 승인하거나 변경한 결정, 이후 `Workspace/` 프로젝트에 반복해서 남은 원칙을 대조해 재구성했다. 아래 1인칭 문장은 여러 기록을 한 문장으로 합친 것으로, 사용자의 직접 인용은 아니다.

> 나는 특정 AI 에이전트 하나에 종속된 자동화 도구를 만들려는 것이 아니다. Claude, Codex, Gemini 등 서로 다른 에이전트가 같은 규칙과 작업 상태를 공유하고, 필요한 역할을 나눠 수행하며, 서로의 결과를 비교·검증할 수 있는 작업 환경을 만들고 싶었다. 반복 작업은 자동화하되 보안과 비용을 통제하고, 외부 변경이나 중요한 판단은 내 승인 아래 두며, 대화가 끝나거나 에이전트가 바뀌어도 파일에 남은 맥락을 바탕으로 작업을 이어갈 수 있어야 했다. 실제 업무에서 얻은 성공과 실패를 다시 작업 규칙과 시스템 개선에 반영해 점진적으로 발전시키는 것이 목적이었다.

### 2.1 특정 에이전트에 종속되지 않는다

- Claude, Codex, Gemini 등 여러 에이전트를 필요에 따라 사용할 수 있어야 했다.
- 한 에이전트의 답을 최종 진실로 받아들이지 않고 다른 에이전트와 공식 출처로 교차검증하려 했다.
- 어떤 에이전트가 실행하더라도 사용자의 작업 기준과 안전 경계가 달라지지 않아야 했다.
- Codex 중심에서 Claude 중심으로 운영 주체가 바뀌어도 프로젝트의 규칙·스키마·검증 기준은 이어지게 하려 했다.

### 2.2 대화 기억이 아니라 파일이 맥락을 소유한다

- 세션이 끝나도 무엇을 했고 무엇이 남았는지 복구할 수 있어야 했다.
- 규칙, 현재 상태, 출처 근거, 실패 기록을 파일에 남겨 다른 에이전트가 이어받게 하려 했다.
- 같은 설명을 매번 사용자에게 다시 요구하지 않는 환경을 지향했다.
- 규칙은 한 곳에서 관리하고, 나머지 문서는 그 원본을 참조하게 해 오래된 지침이 섞이는 문제를 줄이려 했다.

### 2.3 여러 에이전트의 역할을 나누고 결과를 비교한다

- 조사, 검토, 레드팀, 요약, 설계 검토를 구분해 한 번의 답변에 모든 판단을 맡기지 않으려 했다.
- 각 에이전트 결과를 같은 구조로 받아 사실, 약한 주장, 출처, 보안 문제, 비용, 후속 작업을 비교하려 했다.
- 최종 통합자는 외부 에이전트의 결과를 그대로 채택하지 않고 충돌과 근거를 확인해야 했다.
- 여러 에이전트를 많이 호출하는 것 자체가 목적이 아니라, 서로 다른 관점이 실제 결과의 정확성과 안전성을 높이는지가 중요했다.

### 2.4 반복 작업은 자동화하되 통제 가능한 범위에서 시작한다

- 처음에는 AI 에이전트 동향을 정기적으로 조사하고 학습 자료로 축적하려 했다.
- 작은 반복 업무 하나를 자동화하고 성공을 확인한 뒤 확장하는 MVP 방식을 원했다.
- 비용, timeout, retry, 최대 실행 범위와 실패 기록이 통제돼야 했다.
- 게시, 메시지 전송, PR, 배포, 데이터베이스 변경처럼 외부에 영향을 주는 작업은 자동화 범위에서 제외하고 사용자 승인을 남겨두려 했다.

### 2.5 보안과 검증을 기능보다 우선한다

- 비밀정보와 개인정보를 에이전트 입력·로그·보고서에 남기지 않으려 했다.
- 도구는 가능한 읽기 전용과 최소 권한으로 실행하려 했다.
- 공식 문서, 실제 설치 버전, 로컬 실행 결과가 일치하는지 확인한 뒤 연동하려 했다.
- 자동화가 동작한다는 사실보다 안전하게 실패하고 중단할 수 있는지가 중요했다.

### 2.6 실제 작업에서 얻은 경험으로 시스템을 개선한다

- 조사 결과는 외부 기술을 평가하는 데서 끝나지 않고 현재 작업 방식의 개선점으로 연결돼야 했다.
- 개선안은 바로 적용하지 않고 적용, 보류, 거절로 나눠 판단하려 했다.
- 실패 원인과 검증 결과를 다음 세션과 다른 에이전트가 재사용할 수 있게 남기려 했다.
- 실제 사용량과 필요에 맞지 않는 자동화는 유지하지 않고 단순화하려 했다.

### 2.7 작업 과정에서 변경된 의도와 유지된 의도

| 구분 | 처음의 방향 | 이후 사용자가 선택한 방향 | 계속 유지된 핵심 의도 |
|---|---|---|---|
| 실행 주체 | Codex가 외부 에이전트를 조정 | Claude가 직접 통합하고 Codex는 선택적 교차검증 | 특정 에이전트에 결과를 독점시키지 않음 |
| 실행 주기 | 한국어 주간 AI 에이전트 브리핑 | 예약 작업을 중단하고 필요할 때 조사 | 최신 도구를 근거 중심으로 학습·평가 |
| 자동화 규모 | 래퍼, 작업 큐, 오케스트레이터, 다층 로그 | 대화 안에서 직접 수행하는 경량 흐름 | 반복 가능성, 검증, 실패 기록 |
| 결과 저장 | 구조화 JSON과 대규모 실행 기록 | Markdown 보고서와 필요 시 구조화 결과 | 대화 밖에 근거와 상태를 남김 |
| 권한 | 읽기 중심 MVP | 외부 쓰기는 계속 명시적 승인 필요 | 사용자 통제와 최소 권한 |

즉, 주간 보고·Codex 중심·대형 오케스트레이션은 사용자의 최종 목적 그 자체가 아니라 당시 선택한 구현 방식이었다. 기록 전체에서 일관되게 남은 의도는 **에이전트 교체 가능성, 공유 가능한 작업 맥락, 결과 교차검증, 사용자 승인 경계, 실제 경험을 통한 점진적 개선**이다.

## 3. 프로젝트 문서에 구현된 의도

### 3.1 AI 에이전트 도구를 안전하게 평가한다

Claude, Codex, Gemini, MCP 서버, AutoGen, LlamaIndex, CrewAI 같은 도구를 바로 도입하지 않고 다음 항목을 먼저 확인하려 했다.

- 공식 문서와 실제 설치 환경이 일치하는지
- 어떤 파일·터미널·브라우저·외부 서비스 권한을 요구하는지
- 비밀정보, 개인정보, 프롬프트 인젝션 위험이 있는지
- 자동 실행이 비용 폭주나 반복 실패로 이어질 수 있는지
- 최소 성공 호출을 재현할 수 있는지

프로젝트의 우선순위는 `보안 > 정확성 > 비용`으로 정리됐다.

### 3.2 에이전트가 바뀌어도 같은 기준으로 작업하게 한다

특정 대화나 특정 모델의 기억에 의존하지 않고, 모든 에이전트가 같은 파일에서 규칙과 상태를 읽도록 만들려 했다.

- `PROJECT_RULES.md`: 공통 규칙의 단일 원본
- `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`: 각 에이전트가 공통 규칙으로 들어오는 포인터
- `SESSION_HANDOFF.md`: 마지막 작업 상태와 미완료 항목
- `docs/INDEX.md`: 필요한 문서만 찾아 읽는 파일 지도

### 3.3 조사 결과를 비교 가능한 형태로 남긴다

외부 에이전트의 답을 그대로 믿지 않고, 확인된 사실과 약한 주장을 분리해 기록하려 했다.

- 공식·1차 출처 우선의 6단계 출처 등급
- researcher, reviewer, redteam, summarizer, architect 역할 분리
- 보안 문제, 비용, 후속 확인 항목을 포함한 공통 결과 스키마
- 조사 후 레드팀 검토와 시스템 개선안 분류

### 3.4 공통 규칙과 실제 프로젝트를 분리한다

저장소 루트는 “어떻게 일할 것인가”를 담당하고, 실제 유튜브·영상·리서치 작업은 `Workspace/<project>/` 아래에서 진행하는 2계층 구조를 만들었다.

여러 하위 프로젝트에서 반복되는 규칙만 루트로 올리고, 개별 도메인 작업은 서로 침범하지 않게 하는 것이 의도였다.

## 4. 시간순 작업 내용

### 4.1 Git 이관 이전: Codex 중심 자동화 구상

현재 저장소 이전에는 `Building WorkFlow Codex/`에서 다음 구조를 구상하고 일부 구현했다.

- Codex가 외부 Claude CLI를 호출하는 PowerShell/Python 래퍼
- `pending`, `running`, `completed`, `failed` 상태를 갖는 작업 큐
- JSON Schema 기반 작업 입력과 에이전트 결과 구조
- 여러 단계를 선언적으로 실행하는 워크플로 오케스트레이터
- 전체 실행 기록, 최신 상태, JSONL 이벤트 색인으로 나눈 실행 로그
- AI 에이전트 동향을 정기적으로 조사하는 주간 보고 체계

이 단계의 목표는 Codex가 조사·검토·요약 역할을 다른 에이전트에 배분하고 결과를 구조화해 통합하는 것이었다.

### 4.6 2026-07-02: Codex MCP 교차검증 경로 정리

처음에는 Claude 환경에서 로컬 Codex CLI에 접근하기 위해 파일 큐와 실행 스크립트를 만들었다. 이후 Claude Desktop에 OpenAI의 `codex mcp-server`를 직접 연결하면서 중간 큐와 스크립트를 제거했다.

최종 프로토콜은 다음과 같았다.

### 6.1 Claude Code CLI 래퍼 실행이 반복해서 실패함

- **상황:** Codex가 샌드박스 안에서 외부 Claude Code CLI를 호출하고, 결과를 `agent_result.schema.json`에 맞춰 저장하는 래퍼를 시험했다.

- **확인된 실패 유형:**

  3. exit code 124 타임아웃

### 6.2 에이전트 출력과 JSON Schema가 반복해서 충돌함

- **상황:** 여러 에이전트 결과를 비교하기 위해 17개 필드를 강제하고 `additionalProperties: false`를 사용하는 엄격한 결과 스키마를 적용했다.
- **발생한 현상:** `confirmed_facts`가 객체 배열이어야 하는데 문자열 배열로 오거나, 허용되지 않은 `output_format`, `risks` 같은 키가 추가됐다. 어떤 실행은 JSON 자체가 아닌 자연어를 반환했다.
- **직접 원인:** 프롬프트가 모델에 요구한 형태와 검증기가 실제로 허용한 형태가 충분히 일치하지 않았다.
- **근본 원인:** 설치된 CLI와 모델이 구조화 출력을 어떻게 반환하는지 최소 호출로 확인하기 전에 엄격한 스키마부터 자동화에 결합했다.
- **당시 결과:** 스키마 검증 실패가 최소 7회 기록됐고, `New-AgentPrompt`에 필드 형태를 장문으로 명시한 뒤 smoke test 7에서 통과했다.
- **반복 방지 기준:** 작은 예제로 실제 출력 구조를 먼저 고정하고, 스키마·프롬프트·검증기를 같은 예제로 동시에 시험한다. 자유형 모델 출력에 엄격한 스키마를 붙일 때는 실패를 정상 경로로 취급한다.

### 6.3 샌드박스 네트워크 제한을 코드 결함처럼 계속 수정하려 함

- **상황:** Codex 실행 환경에서 Claude Code CLI를 이용한 실시간 리서치를 시도했다.
- **발생한 현상:** `claude-cli-options-research`, 재시도, live 실행이 모두 `API Error: ConnectionRefused`로 실패했다.
- **직접 원인:** Codex가 실행된 샌드박스에서 외부 네트워크 연결이 차단돼 있었다.
- **근본 원인:** 실행 환경의 고정 제약과 래퍼 코드의 결함을 초기에 분리하지 못했다. 코드 수정으로 환경 제한을 해결할 수 있다고 보고 재시도했다.
- **당시 결과:** 세 번의 리서치 실행이 모두 실패했고 해당 문제는 Codex 단계에서 해결되지 않았다. 이후 Claude가 직접 네트워크 리서치를 수행하는 구조로 바꾸면서 우회했다.
- **반복 방지 기준:** 동일한 `ConnectionRefused`가 환경 경계에서 재현되면 코드 수정 전에 샌드박스·네트워크 정책을 확인한다. 권한 밖의 환경 제약이면 즉시 다른 실행 경로를 선택한다.

### 6.4 같은 smoke test를 일곱 번 반복함

- **상황:** wrapper hardening smoke test가 인증, 타임아웃, 스키마 문제로 연속 실패했다.
- **발생한 현상:** `wrapper-hardening-smoke-test-2`부터 `-7`까지 같은 목표를 계속 수정·재실행했다.
- **직접 원인:** 각 실패 뒤 프롬프트나 옵션을 바꾸면 다음에는 성공할 것이라고 판단했다.
- **근본 원인:** 당시 이미 존재하던 “같은 목표 3회 실패 시 중단” 규칙을 실행 흐름에서 실제 게이트로 적용하지 않았다. 실패 원인을 분류하기 전에 다음 수정으로 넘어갔다.
- **당시 결과:** 일곱 번째 시도에서 성공했지만, 불필요한 시간·토큰을 사용했고 규칙과 실제 행동이 불일치했다.
- **반복 방지 기준:** 같은 목표가 세 번 실패하면 성공 가능성이 남아 있어도 멈춘다. 실패 원인, 계속할 위험, 재조사할 항목을 기록하고 사용자 판단을 기다린다.

### 6.5 프롬프트 지시를 실제 권한 경계로 사용함

- **상황:** Claude Code CLI를 리서치 전용 read-only 에이전트처럼 실행하려 했다.
- **발생한 현상:** 래퍼는 프롬프트에 “도구를 사용하지 말라”고 적었지만, 실행 도구 자체에서 파일·bash 권한을 확실하게 제거하지 않았다.
- **직접 원인:** `--permission-mode`, `--disallowedTools` 등 설치 버전에서 가능한 실제 권한 통제를 일관되게 적용하지 않았다.
- **근본 원인:** 모델에 내린 행동 지시와 프로세스에 강제한 보안 권한을 같은 것으로 취급했다.
- **당시 결과:** 실제 사고가 기록되지는 않았지만 프로젝트의 read-only 정책과 구현 사이에 보안 공백이 있었다. 아키텍처 리뷰가 이를 가장 중요한 결함으로 지적했다. 래퍼가 폐기돼 코드 수정 없이 사라졌다.
- **반복 방지 기준:** 프롬프트는 보안 경계가 아니다. 파일, 셸, 네트워크, 환경변수, 외부 쓰기 권한은 실행기 설정과 샌드박스에서 강제한다.

### 6.6 다단계 워크플로를 end-to-end로 검증하지 못함

- **상황:** 위상정렬, 단계 의존성, review gate, 실패 정책을 포함한 선언형 워크플로 오케스트레이터를 구현했다.
- **발생한 현상:** `-ValidateOnly`와 `-DryRun`은 작동했지만, 실제 에이전트 호출을 포함해 처음부터 끝까지 완료한 다단계 실행 기록은 없었다. 의미 검토 gate도 자동 실행되지 않고 `skipped`로 남았다.
- **직접 원인:** 하위 래퍼가 인증·스키마·네트워크 문제로 불안정한 상태에서 상위 오케스트레이터를 먼저 만들었다.
- **근본 원인:** 구성 파일의 구문 검증과 실제 업무 성공을 같은 진척도로 취급했다. 가장 작은 종단 흐름을 먼저 입증하지 않았다.
- **당시 결과:** 스키마와 스크립트는 존재했지만 운영 가능한 자동화로 검증되지 못했고 Claude-first 전환 때 제거됐다.
- **반복 방지 기준:** 한 단계의 실제 성공 → 두 단계 종단 성공 → 실패 복구 확인 순서로 확장한다. dry-run 성공은 실행 성공으로 기록하지 않는다.

### 6.7 실제 사용량보다 큰 저장·오케스트레이션 구조를 설계함

- **상황:** 하루 수십 회 자동 실행을 전제로 4상태 작업 큐, 3단계 실행 로그, source cache, 범용 wrapper, 향후 MCP Gateway까지 설계했다.
- **발생한 현상:** 실제 사용은 가끔 수행하는 조사와 교차검증이었고, 작업 큐와 source cache 일부는 설계만 있고 실제 파일이나 소비자가 없었다.
- **직접 원인:** 예상되는 미래 확장과 현재 필요한 기능을 같은 MVP 범위에 넣었다.
- **근본 원인:** Codex의 네트워크 제약을 해결하는 문제와 장기적인 다중 에이전트 플랫폼 구축을 한 번에 다뤘다.
- **당시 결과:** 많은 문서·스키마·스크립트가 실제 사용 없이 유지 대상이 됐고, Claude-first 전환 때 대부분 삭제됐다.
- **반복 방지 기준:** 실제 반복 횟수와 소비자가 확인된 구조만 만든다. 미래용 스키마·캐시·게이트웨이는 전환 조건이 충족될 때 추가한다.

### 6.8 파일 큐 우회 방식을 만들었지만 연결 방식 변화로 곧 폐기함

- **상황:** Claude 환경의 샌드박스에서 사용자의 로컬 Codex CLI에 직접 접근할 수 없었다.
- **발생한 현상:** Claude가 `pending/`에 작업 파일을 쓰고 사용자가 PowerShell 실행기를 수동 실행한 뒤 `completed/` 결과를 읽는 방식을 만들었다. 매 호출마다 사용자 개입이 필요했다.
- **직접 원인:** 샌드박스와 로컬 실행 환경 사이에 직접 호출 경로가 없었다.
- **근본 원인:** 당시 사용 가능한 연결 표면을 충분히 확인하기 전에 파일 기반 중계 구조를 구현했다.
- **당시 결과:** 동작은 했지만 곧 공식 `codex mcp-server` 직접 연결이 가능해져 큐와 스크립트를 제거했다.
- **반복 방지 기준:** 임시 우회 구조를 만들 때는 어떤 제약을 우회하는지, 제거 조건이 무엇인지 함께 기록한다. 공식·직접 연결 경로를 먼저 확인한다.

### 6.9 공식 문서의 경로와 실제 설치 환경이 달랐음

- **상황:** Windows Store(MSIX) 버전 Claude Desktop에 Codex MCP 서버를 연결하려 했다.
- **발생한 현상:** 일반적으로 안내된 `%APPDATA%\Claude\claude_desktop_config.json` 경로가 존재하지 않았고, 앱의 `Edit Config` 버튼이 실제로 읽지 않는 파일을 열었다. 설정을 바꿔도 도구가 나타나지 않았다.
- **직접 원인:** MSIX 빌드는 실제 설정을 `%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\Roaming\Claude\claude_desktop_config.json`에서 읽었다.
- **근본 원인:** 공식·일반 설치 문서를 로컬 설치 형식에 그대로 적용했다. UI가 여는 파일을 정본이라고 가정했다.
- **당시 결과:** 실제 경로를 찾아 직접 수정하고 앱을 트레이에서 완전히 종료·재실행한 뒤 연결에 성공했다.
- **반복 방지 기준:** 경로가 없거나 수정이 반영되지 않으면 같은 설정을 반복하지 않는다. 설치 형식, 실제 프로세스가 읽는 파일, 앱 완전 종료 여부를 확인한다.

### 6.10 파일 수정 후 디스크 사본이 잘리는 현상이 반복됨

- **상황:** 긴 Markdown과 JSON 파일을 편집 도구로 수정했다.
- **발생한 현상:** 편집 도구가 성공을 보고했는데도 bash에서 보이는 파일이 일부만 저장되거나 끝부분이 잘린 경우가 여러 번 발생했다. 새로 쓰기를 해도 재현된 기록이 있다.
- **직접 원인:** 편집 결과와 bash-visible 파일 사이의 동기화 문제로 관찰됐다.
- **근본 원인:** `미확정`. 당시 문서에는 환경의 파일 동기화 특이 현상으로만 기록돼 있으며 정확한 시스템 원인은 규명되지 않았다.
- **당시 결과:** 저장 성공 메시지만 믿을 수 없었고, byte count·파일 tail·JSON 유효성·괄호 균형을 다시 확인해야 했다.
- **반복 방지 기준:** 긴 파일은 수정 직후 실제 디스크 파일의 크기, 마지막 부분, 파서 통과 여부를 확인한다. 도구의 성공 응답만으로 완료 처리하지 않는다.

### 6.11 외부 에이전트가 Codex 자동화 실행 방식을 잘못 설명함

- **상황:** Claude가 Codex 프로젝트 자동화의 실행 위치와 조건을 조사했다.
- **발생한 현상:** 로컬 앱과 컴퓨터가 꺼져 있어도 클라우드에서 계속 실행된다는 내용을 보고서에 기록했다.
- **직접 원인:** 공식 동작 조건과 로컬 제품 동작을 충분히 대조하지 않은 외부 에이전트 출력을 채택했다.
- **근본 원인:** 그럴듯한 설명을 사실로 받아들이고, 시간·제품 상태에 민감한 주장에 필요한 출처 검증을 생략했다.
- **당시 결과:** 후속 레드팀 조사에서 프로젝트 범위 자동화는 로컬 Codex 앱 실행, 켜진 컴퓨터, 디스크의 프로젝트가 필요하다는 충돌을 발견해 기존 주장을 폐기했다.
- **반복 방지 기준:** 자동 실행 위치, 권한, 비용, 가격, 보안처럼 의사결정에 영향을 주는 주장은 공식 문서와 실제 설치 환경으로 이중 확인한다. 외부 에이전트 결과는 증거 후보일 뿐이다.

### 6.12 약한 출처와 불완전한 날짜 표기로 사실 충돌이 생김

- **상황:** AutoGen 릴리스 날짜와 여러 공급자의 시장·가격·Managed Agent 주장을 조사했다.
- **발생한 현상:** GitHub 릴리스 화면이 연도 없이 `30 Sep`만 표시해 연도 충돌이 생겼고, 일부 정량 주장은 2차 기사만 근거로 남았다.
- **직접 원인:** UI의 축약 표기와 2차 출처를 완전한 원문 정보처럼 해석했다.
- **근본 원인:** 날짜·가격·시장 규모처럼 변동성이 큰 주장에 독립된 1차 메타데이터 확인을 처음부터 강제하지 않았다.
- **당시 결과:** AutoGen 날짜는 PyPI 업로드 메타데이터와 Trusted Publishing provenance를 확인해 2025-09-30으로 정리했다. 약한 정량 주장은 확정 사실에서 제외했다.
- **반복 방지 기준:** 날짜는 릴리스 태그뿐 아니라 패키지 저장소 메타데이터로 확인한다. 가격·시장·제품 기능은 결정 직전에 공식 출처로 다시 확인하고 약한 주장을 명시적으로 표시한다.

### 6.13 주간 자동 보고가 실제 사용 방식과 맞지 않았음

- **상황:** 한국어 주간 AI 에이전트 브리핑을 정기적으로 만들기 위해 보고서 템플릿, 월별 색인, 전용 체크리스트와 예약 실행을 구상했다.
- **발생한 현상:** Claude-first 구조에서는 실제 주간 보고를 end-to-end로 한 번도 실행하지 않았고, 사용자는 당시 예약 자동화가 작동하거나 필요하지 않다고 확인했다.
- **직접 원인:** 반복 주기가 실제 사용 습관과 필요보다 먼저 고정됐다.
- **근본 원인:** 수동 실행이 몇 차례 유용하게 반복되는지 확인하기 전에 정기 자동화를 프로젝트의 핵심 운영 방식으로 잡았다.
- **당시 결과:** 주간 보고 템플릿, 기존 주간 결과, 월별 색인, 관련 예약 작업을 삭제하고 요청형 리서치로 바꿨다.
- **반복 방지 기준:** 예약 자동화는 동일 수동 작업이 실제로 반복되고 입력·완료 조건이 안정된 뒤 도입한다.

### 6.14 백업을 활성 파일과 함께 과도하게 Git에 포함함

- **상황:** Codex 단계 자료를 현재 저장소로 이관하면서 리팩토링 전 전체 사본, 역사 보고서, 중복 체크리스트까지 첫 커밋에 넣었다.
- **발생한 현상:** 첫 커밋은 63개 파일, 약 5,130줄을 추가했고 그중 상당수가 중복 백업이었다. 다음 날 커밋 `132d644`에서 백업 36개, 약 3,445줄을 다시 삭제했다.
- **직접 원인:** 복구 가능성을 높이기 위한 백업과 활성 작업 세트를 같은 Git 범위에 넣었다.
- **근본 원인:** 단기 수정 전 백업, 역사 보관, 현재 운영 문서의 수명주기를 구분하지 않았다.
- **당시 결과:** 파일 지도와 현재 정본을 파악하기 어려워졌고, 이관 직후 대량 정리 작업이 필요했다.
- **반복 방지 기준:** 활성 정본, 역사 기록, 단기 백업의 위치와 보존 기간을 분리한다. 전체 사본을 추가하기 전에 Git 이력만으로 복구 가능한지 확인한다.

### 6.15 Antigravity의 세부 권한 문서를 끝내 확인하지 못함

- **상황:** Antigravity 도입 가능성을 판단하기 위해 보안·권한·runtime 자료를 조사했다.
- **발생한 현상:** Google 공식 글에서 sandboxing, credential masking, hardened Git 정책, remote sandbox 언급은 확인했지만 제품 설정 단위 권한 모델과 안정적인 runtime 문서 URL은 찾지 못했다.
- **직접 원인:** 당시 공개·확인 가능한 공식 자료가 상위 수준 설명에 머물렀다.
- **근본 원인:** `미확정`. 문서가 없었던 것인지, 다른 제품 문서 체계에 있었으나 찾지 못한 것인지 기록만으로 구분할 수 없다.
- **당시 결과:** 상세 권한을 확인한 것처럼 결론 내리지 않고 도입 판단을 보류했으며, 마지막 handoff의 미완료 항목으로 남겼다.
- **반복 방지 기준:** 공식 상세 문서를 찾지 못한 사실 자체를 결과로 기록한다. 보안 기능의 마케팅 설명을 실제 권한 모델로 대체하지 않는다.

## 7. 실패 경험이 당시 운영 규칙에 남긴 흔적

| 실패 경험 | 이후 문서에 반영된 규칙 |
|---|---|
| CLI 동작을 추측하고 래퍼부터 작성 | 새 도구 연결 전에 최소 성공 호출과 설치 버전 확인 |
| 프롬프트만으로 권한 제한 | 실제 실행 도구와 권한 설정에서 최소 권한 적용 |
| 동일 smoke test 7회 반복 | 같은 실패 3회 시 중단하고 원인 재조사 |
| 잘못된 자동화 실행 방식 기록 | 공식 문서와 로컬 설치 동작이 다르면 로컬에서 재검증 |
| 약한 출처의 날짜·가격·시장 주장 | 출처 등급과 Confirmed/Likely/Unverified 구분 |
| 대형 오케스트레이터의 낮은 실사용성 | Claude 직접 수행과 소수 subagent 중심으로 축소 |
| 주간 자동 보고의 낮은 적합성 | 예약 실행보다 요청형 리서치로 전환 |
| 외부 에이전트 결과의 오류 | 외부 에이전트 출력은 권위가 아닌 검증 대상 증거로 취급 |
| 인증·스키마·네트워크 오류를 같은 재시도로 처리 | 실패를 환경·인증·호출·출력·검증 단계로 먼저 분류 |
| dry-run만 성공한 워크플로 | 검증 수준을 구분하고 end-to-end 성공 전에는 운영 완료로 보지 않음 |
| MSIX 설정 경로와 일반 문서 불일치 | 실제 설치 형식과 프로세스가 읽는 로컬 경로 확인 |
| 저장 성공 후 파일 잘림 | byte count, tail, parser로 실제 디스크 결과 재검증 |
