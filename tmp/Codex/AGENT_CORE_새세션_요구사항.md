## 이 문서만 읽는 사람을 위한 전제

1. **최종 설계는 아직 없다.** Git submodule, monorepo, 별도 Core 저장소, fallback 문서 등은 모두 과거에 검토되거나 성급하게 권장됐던 후보일 뿐, 사용자가 승인한 결론이 아니다.
2. **현재 작업은 구현 단계가 아니다.** 파일 이동, 저장소 분리, 이름 변경, submodule 도입, Core 교체를 시작하면 안 된다.
3. **과거 실패의 중심은 기술 선택 자체보다 작업 순서였다.** 기존 Core의 목적·구조·비용을 끝까지 확인하기 전에 일반적인 아키텍처와 Git 해법부터 제안했다.
4. **이 문서의 작업기록은 과거 대화에서 실제로 오간 시도와 교정을 기록한 역사다.** 기록 속 기술 주장은 현재의 확정 사실이 아니므로 새 세션에서 다시 검증해야 한다.
5. **원본 분석 대상은 읽기 전용이다.** `C:\Users\Hugh\Claude\Projects\Building WorkFlow\Workspace\김실버유튜브\`에서는 읽기 외의 작업을 하면 안 된다.

## 1. 사용자가 만들려는 것

사용자는 YouTube와 무관한 **Agent 공통 규칙과 운영 기반**을 `Agent Core`로 분리하려 한다.

이 Agent Core는 다음 두 목적을 함께 만족해야 한다.

1. YouTube, 강의 판매, 프로그램 판매처럼 서로 전혀 다른 프로젝트들이 하나의 Core를 공유한다.
2. Claude, Codex 등 여러 Agent가 하나의 프로젝트 안에서 같은 규칙과 작업 내용을 바탕으로 함께 작업한다.

YouTube 채널·영상 워크플로는 Core 자체가 아니라 Core를 사용하는 하나의 실제 프로젝트다.

### 작업기록

- **시도했던 작업:** 처음에는 Core를 여러 프로젝트에서 재사용하는 공통 계층 또는 Git 배포 단위로 설명했고, 이후 여러 Agent가 한 프로젝트에서 규칙과 작업 내용을 공유하는 목적을 추가해 다시 정리했다.
- **개선하려던 내용:** `서로 다른 프로젝트의 재사용`과 `한 프로젝트 안의 다중 Agent 공동 작업`을 Agent Core의 동등한 두 목적으로 반영하려 했다.
- **실패한 이유:** 초기 분석이 YouTube용 워크플로 또는 공통 코드 배포 문제에 치우쳐 기존 Core의 실제 역할을 먼저 확인하지 않았다. 그 결과 다중 Agent의 상태·규칙·인수인계 공유 목적을 뒤늦게 반영했다.
- **사용자에게 발생한 결과:** 사용자는 Core가 무엇인지 같은 설명을 여러 차례 반복해야 했고, 이후의 Git·문서 구조 제안도 잘못된 전제 위에서 시작됐다.
- **다음 세션의 검증 조건:** 기존 Core 안의 실제 파일과 연결을 근거로 `프로젝트 간 공유`와 `프로젝트 내 다중 Agent 협업`이 각각 어떻게 구현돼 있었는지 먼저 설명해야 한다.

## 2. 공통 정보와 개별 정보의 분리

여러 프로젝트와 작업에는 다음 두 종류의 정보가 존재한다.

1. 여러 곳에서 공통으로 사용할 수 있는 정보
2. 각 프로젝트·세션·작업 내용에 맞게 구분해야 하는 정보

이 두 종류의 정보가 서로 섞이면 안 된다.

Core에는 특정 YouTube 프로젝트나 특정 수익화 작업의 내용이 아니라 Agent들이 공통으로 사용하는 내용만 들어가야 한다.

각 프로젝트의 규칙·상태·데이터·작업 내용은 해당 프로젝트에 맞게 별도로 관리돼야 한다.

### 작업기록

- **시도했던 작업:** `Core = 공통`, `Extension = 개별`이라는 단순 구분과 Core·프로젝트 루트·Extension·작업별 정보의 책임 분리를 제안했다.
- **개선하려던 내용:** 공통 규칙과 프로젝트별 규칙·상태·데이터가 섞이지 않는 경계를 만들려 했다.
- **실패한 이유:** 실제 Core가 어떤 파일과 데이터를 관리하는지 확인하기 전에 일반적인 분류부터 제안했다. `Agent 공통`, `프로젝트 공통`, `세션·작업별` 정보의 차이를 충분히 검증하지 못해 추상적인 분류에 머물렀다.
- **사용자에게 발생한 결과:** 단순한 `Core/Extension` 이름만 생겼을 뿐, 어떤 파일과 데이터가 어디에 속해야 하는지 판단할 기준은 얻지 못했다.
- **다음 세션의 검증 조건:** 실제 항목을 최소한 `Agent 공통`, `프로젝트 공통`, `Extension 전용`, `세션·작업 전용` 후보로 분류하되, 지금 당장 세부 분류를 확정하지 말고 경계 원칙부터 제시해야 한다.

## 3. 여러 Extension으로 확장

현재 김실버유튜브에서는 Extension에 있는 특정 파일을 참고하는 방식으로 문제를 임시 해결해 두었다.

새 설계는 이 방식을 하나의 Extension에만 맞춘 상태로 두지 않고, 여러 Extension으로 확장할 수 있게 개선해야 한다.

검토해야 할 핵심은 다음과 같다.

1. 하나의 Core가 여러 Extension과 연결되는 방식
2. Extension마다 다른 규칙·상태·데이터를 분리하는 방식
3. 현재 임시 연결 방식에서 유지할 부분과 개선할 부분

### 작업기록

- **시도했던 작업:** Extension registry, 프로젝트별 Host, 여러 하위 작업 범위 같은 일반화된 확장 구조를 제안했다.
- **개선하려던 내용:** 하나의 Extension 파일을 직접 참고하는 임시 방식을 여러 Extension에 적용할 수 있는 공통 연결 방식으로 바꾸려 했다.
- **실패한 이유:** 김실버유튜브의 실제 참조 경로·호출 방향·문서 간 관계를 끝까지 분석하기 전에 새 구조부터 제안했다. 그래서 현재 방식에서 무엇을 보존하고 무엇을 제거해야 하는지 근거를 제시하지 못했다.
- **사용자에게 발생한 결과:** 기존 임시 방식의 장점을 잃을 수 있는 새 개념만 늘었고, 여러 Extension으로 확장하는 실제 경로는 확정되지 않았다.
- **다음 세션의 검증 조건:** 현재 Core가 어느 Extension 파일을 어떤 문서에서 어떤 방향으로 참조하는지 도식화한 뒤, 그 연결을 2개 이상의 Extension으로 늘릴 때 바뀌는 지점만 제안해야 한다.

## 4. 여러 Agent의 공동 작업

Core와 Extension을 나눈 이유는 여러 프로젝트에서 Core를 재사용하기 위해서만이 아니다.

여러 Agent가 하나의 프로젝트 안에서 함께 작업하고, 서로 작업을 이어받을 수 있는 구조도 유지해야 한다.

따라서 새 설계는 Git 저장소 연결만 설명해서는 안 된다. 여러 Agent가 프로젝트 안에서 공통 규칙과 작업 내용을 어떻게 사용하게 되는지도 함께 다뤄야 한다.

### 작업기록

- **시도했던 작업:** 처음에는 Core Git 공유와 버전 고정에 집중했고, 이후 루트 규칙·상태 문서·인수인계를 통한 Agent 간 작업 공유를 설명에 포함했다.
- **개선하려던 내용:** 저장소 재사용 구조에 다중 Agent의 공통 규칙, 현재 상태, 이어받기 기능을 함께 넣으려 했다.
- **실패한 이유:** 다중 Agent 공동 작업이 Core를 만든 핵심 목적이라는 사실을 초기에 놓쳤다. 저장소 연결을 먼저 결정하려 하면서 Agent들이 실제로 무엇을 읽고 어떻게 이어받는지에 대한 설계가 뒤따라가는 형태가 됐다.
- **사용자에게 발생한 결과:** 제안된 Git 구조가 Core 파일은 공유할 수 있어도 Agent 간 문맥·상태·인수인계를 공유할 수 있는지는 설명되지 않았다.
- **다음 세션의 검증 조건:** 각 대안에서 Agent가 프로젝트를 열 때 읽는 순서, 공통 규칙을 찾는 경로, 현재 작업 상태를 이어받는 경로를 함께 제시해야 한다.

## 5. 기존 Core의 실제 위치와 이력

사용자가 제공한 현재 사실은 다음과 같다.

1. 처음에는 `Building WorkFlow`를 Core 역할로 만들려고 했다.
2. `Building WorkFlow` 안에는 별도 Git 저장소인 김실버유튜브 프로젝트가 들어 있다.
3. 실제 작업 과정에서는 `Building WorkFlow\Workspace\김실버유튜브\core`가 Core 역할을 하게 됐다.
4. 김실버유튜브가 첫 실제 작업이었고 Core를 계속 수정해야 할 일이 생기면서, Core가 그 프로젝트 안에서 발전한 것으로 사용자는 보고 있다.
5. Core와 기존 Git 저장소의 연결은 관리 과정에서 잘못 구성됐다.
6. 과거의 Tier·계층 상속 개념은 오래전에 폐기됐다. 새 분석에서 현재 구조처럼 사용하면 안 된다.

새 세션은 추측으로 Core 위치와 역할을 정하지 말고, 위 경로의 실제 폴더 구조와 Git 이력을 읽어서 판단해야 한다.

### 작업기록

- **시도했던 작업:** `Building WorkFlow`와 김실버유튜브 내부 Core의 폴더·Git 관계를 읽고 최초 의도와 실제로 발전한 Core를 구분하려 했다.
- **개선하려던 내용:** 잘못 연결된 중첩 Git 구조와 실제 Core의 위치를 근거로 확인하려 했다.
- **실패한 이유:** 초기에는 기존 저장소 위치를 잘못 추측했고, 이미 폐기된 Tier·계층 상속 문구를 현재 구조의 근거로 다시 사용했다. 실제 폴더와 Git 이력보다 과거 문서 문구를 먼저 믿은 것이 원인이었다.
- **사용자에게 발생한 결과:** 현재 Core에 대한 사실 보고까지 신뢰하기 어려워졌고, 사용자는 기존 내용 분석을 처음부터 다시 시작하라고 요구했다.
- **다음 세션의 검증 조건:** 현재 파일 내용, 폴더 위치, `.git` 경계, Git 이력을 각각 구분해 증거를 제시하고 폐기된 Tier 개념은 역사적 오류로만 표시해야 한다.

## 6. 명칭

`Building WorkFlow`라는 명칭은 사용하지 않으려 한다.

사용자가 선호하는 명칭은 `Agent Core`다.

### 작업기록

- **시도했던 작업:** 이후 설명과 문서에서 `Agent Core` 또는 `Agent-Core` 명칭을 사용했다.
- **개선하려던 내용:** 기존 `Building WorkFlow` 명칭을 사용자 의도에 맞는 이름으로 교체하려 했다.
- **실패한 이유:** 명칭 합의 자체에는 실패가 없다. 다만 저장소 구조가 확정되지 않았기 때문에 실제 폴더·저장소 이름 변경은 시도하지 않았다.
- **사용자에게 발생한 결과:** 문서상 선호 명칭은 정리됐지만 실제 경로와 저장소 이름은 그대로이며, 새 이름이 어느 범위에 적용될지는 미정이다.
- **다음 세션의 검증 조건:** 구조가 승인된 뒤에만 이름 변경 대상과 Git 영향 범위를 별도 계획으로 제시한다.

## 7. 프로젝트마다 달라야 하는 루트 문서

`PROJECT_RULES.md`처럼 프로젝트 루트의 특정 위치와 파일명이 의미를 가지는 문서는 프로젝트마다 내용이 달라야 한다.

같은 문제는 다음과 같은 루트 문서에도 적용될 수 있다.

- `AGENTS.md`
- `PROJECT_RULES.md`
- `SESSION_HANDOFF.md`

이 파일들을 Core가 공통으로 소유하는 구조로 가정하면 안 된다.

각 프로젝트가 자기 루트 문서를 가지면서도 Agent Core의 공통 규칙을 사용할 수 있는 연결 방식을 찾아야 한다.

### 작업기록

- **시도했던 작업:** 한때 Agent Core 저장소 루트에 `AGENTS.md`, `PROJECT_RULES.md`, `SESSION_HANDOFF.md`를 함께 두는 구조를 제안했고, 이후 각 Extension 프로젝트가 자기 루트 문서를 소유하는 방향으로 수정했다.
- **개선하려던 내용:** 프로젝트별 문서가 Core의 공통 규칙을 참조하도록 책임을 분리하려 했다.
- **실패한 이유:** 독립 저장소로 열었을 때의 Agent Core 루트와 다른 프로젝트 안에 삽입됐을 때의 Core 하위 폴더를 같은 실행 문맥으로 취급했다. 그 결과 프로젝트마다 달라야 하는 루트 문서를 Core가 소유하는 모순이 생겼다.
- **사용자에게 발생한 결과:** 제안대로 구성하면 Host 프로젝트의 규칙과 Core 개발 규칙이 충돌하거나, 필요한 루트 문서가 엉뚱한 위치에 놓이는 문제가 생길 수 있었다. 이 모순은 사용자가 먼저 지적했다.
- **다음 세션의 검증 조건:** `Agent Core를 독립적으로 연 경우`와 `Host 프로젝트 안의 하위 Core인 경우`를 별도 시나리오로 나눠 각 루트 문서의 소유자와 읽기 경로를 제시해야 한다.

## 8. Core 내부의 특수 파일 문제

Agent Core가 별도의 폴더 형태로 다른 프로젝트 안에 들어가는 구조라면, Core 내부에서 루트 의미를 가지는 다음 파일들을 사용하는 것은 피하고 싶다.

- `AGENTS.md`
- `PROJECT_RULES.md`
- `SESSION_HANDOFF.md`

사용자가 원하는 동작은 다음과 같다.

1. Agent Core 자체를 독립 프로젝트로 작업할 때는 Agent가 Core의 작업 규칙이나 문서를 자동으로 읽을 수 있다.
2. 같은 Core가 다른 프로젝트 안의 하위 폴더나 서브모듈로 들어갔을 때는 그 문서가 불필요하게 읽히거나 의미를 갖지 않는다.
3. Core 내부에 하위 `AGENTS.md`가 존재해 언제든 읽힐 가능성이 남는 것 자체도 피하고 싶다.

`README.md` 또는 다른 일반 문서, Codex의 문서 탐색 설정, 조건부 적용 방식 등이 이 요구를 실제로 만족할 수 있는지 검증해야 한다.

### 작업기록

- **시도했던 작업:** Core 내부 `AGENTS.md`, 조건문이 들어간 `AGENTS.md`, `CORE_GUIDE.md` 같은 일반 문서, Agent 설정의 fallback 문서 등록 방식을 차례로 검토했다.
- **개선하려던 내용:** Core를 독립 프로젝트로 작업할 때만 규칙이 자동으로 읽히고, Extension 내부 하위 폴더가 됐을 때는 의미가 사라지는 문서 방식을 찾으려 했다.
- **실패한 이유:** `core/AGENTS.md`가 루트에서 자동으로 읽히지 않는다는 이유만으로 존재해도 괜찮다고 판단해, 언제든 읽힐 가능성 자체를 없애고 싶다는 요구를 충족하지 못했다. 일반 문서는 별도 참조나 설정 없이는 자동 적용이 보장되지 않으며 Agent별 동작도 달라 최종 방식을 확정하지 못했다.
- **사용자에게 발생한 결과:** Core 내부에 어떤 자동 지침 파일을 둘 수 있는지 결론이 계속 바뀌었고, 잘못 읽힐 위험이 남은 구조를 권장받았다.
- **다음 세션의 검증 조건:** 후보마다 `독립 Core에서 자동 발견`, `Host 내부에서 자동 발견`, `수동 참조 필요`, `Codex/Claude 차이`를 표로 판정해야 한다.

## 9. 하위 AGENTS.md 동작 확인

다음 내용을 정확히 확인해야 한다.

1. Codex는 하위 폴더의 `AGENTS.md`를 읽을 수 있는가?
2. 읽는다면 어떤 조건과 시점에 읽는가?
3. Agent Core 프로젝트가 아닌 경우 해당 문서를 적용하지 않는다는 내용으로 우회할 수 있는가?

이 문제는 추측하지 말고 Agent별 실제 동작을 확인해서 설명해야 한다.

### 작업기록

- **시도했던 작업:** Codex가 작업 위치에 따라 하위 `AGENTS.md`를 읽는다는 설명과, 문서 안의 조건문으로 비적용을 지시하는 우회안을 제시했다.
- **개선하려던 내용:** Core 독립 작업과 Extension 내부 작업에서 같은 파일의 적용 여부를 구분하려 했다.
- **실패한 이유:** 작업 시작 위치·대상 파일 경로·Agent 종류에 따른 차이를 공식 근거와 실제 검증으로 한 번에 정리하지 못했다. 조건문 방식도 파일을 먼저 읽어야 무시할 수 있으므로 `읽을 가능성 자체를 없앤다`는 요구를 해결하지 못했다.
- **사용자에게 발생한 결과:** 사용자는 하위 `AGENTS.md`가 실제로 언제 읽히는지 확신할 수 없었고, 그 동작을 전제로 한 설계를 승인할 수 없었다.
- **다음 세션의 검증 조건:** 공식 문서와 최소 재현 실험으로 작업 시작 위치와 대상 경로별 동작을 확인하고, 확인되지 않은 Agent에는 같은 결론을 일반화하지 않는다.

## 10. Git을 통한 Core 연결

Core를 각 프로젝트에 사람이 수동으로 복사하는 방식은 원하지 않는다.

Git 시스템 안에서 Core Git을 각 프로젝트가 가져다 사용하는 방식을 검토해야 한다.

다음 질문에 답해야 한다.

1. 프로젝트마다 Git 저장소 하나와 별도 Core Git 저장소 하나를 운영하는 구조인가?
2. 프로젝트가 Core의 특정 버전을 어떤 방식으로 가져오고 갱신하는가?
3. Core를 여러 프로젝트가 공유할 때 실제 Git 저장소 개수와 연결 관계는 어떻게 되는가?

### 작업기록

- **시도했던 작업:** 처음에는 검증된 Core 버전을 각 프로젝트에 복사해 넣는다고 설명했고, 수동 복사가 아니라는 요구가 확인된 뒤 Git submodule로 특정 Core 커밋을 참조하는 방식을 설명했다.
- **개선하려던 내용:** 하나의 Core Git을 여러 프로젝트가 버전별로 가져오고 갱신하는 자동화된 연결을 만들려 했다.
- **실패한 이유:** 처음의 `복사` 표현이 수동 작업으로 이해될 수 있었고, clone·초기화·업데이트·버전 고정의 실제 흐름과 저장소 개수 관계를 처음부터 명확히 설명하지 못했다. 최종 연결 방식도 다른 요구사항 검증 전에 submodule 쪽으로 기울었다.
- **사용자에게 발생한 결과:** 사용자는 수동 복사를 해야 하는지, 프로젝트 수만큼 Core Git이 생기는지, 하나의 Core 정본을 어떻게 받는지 기본 구조부터 혼란을 겪었다.
- **다음 세션의 검증 조건:** 예시로 `Core 1개 + 프로젝트 N개`의 원격·로컬 저장소 수, 최초 가져오기, 버전 고정, 업데이트, 롤백 흐름을 그림 또는 짧은 단계로 설명해야 한다.

## 11. Git 구조 대안 비교

다음 방식을 현재 프로젝트에 적용했을 때의 차이와 장단점을 분석해야 한다.

1. Git submodule
2. monorepo
3. 필요하면 두 방식 외의 차선책

비교할 때는 단순한 Git 기능 설명이 아니라 현재 Agent Core 목적에 맞춰 다음 항목을 따져야 한다.

1. 여러 프로젝트의 Core 공유
2. 여러 Agent의 한 프로젝트 내 공동 작업
3. 프로젝트별 규칙·상태·데이터 격리
4. Core 버전 관리와 업데이트
5. Core 직접 수정 방지
6. 비용 증가

어떤 방법도 모든 조건을 완전히 만족하지 못한다면 그 사실과 차선책을 함께 설명해야 한다.

### 작업기록

- **시도했던 작업:** submodule과 monorepo의 일반적인 장단점을 비교하고, Core를 별도 Git으로 고정할 수 있다는 이유로 submodule을 권장했다.
- **개선하려던 내용:** Core의 독립 버전 관리와 여러 프로젝트의 선택적 업데이트를 동시에 만족시키려 했다.
- **실패한 이유:** 프로젝트별 루트 문서, Core 내부 특수 파일, 다중 Agent 협업, 현재 임시 Extension 연결, 비용을 모두 검증하기 전에 권장안을 정했다. 일반적인 Git 장점이 현재 Agent Core 요구를 실제로 충족한다는 근거가 부족했다.
- **사용자에게 발생한 결과:** submodule이라는 결론이 먼저 제시됐지만 요구사항을 하나씩 대입하자 해결되지 않은 문제가 계속 발견됐고, 권장안 전체를 다시 검토해야 했다.
- **다음 세션의 검증 조건:** 모든 대안을 동일한 요구사항 행렬에 대입하고, 치명적 미충족 조건과 보완 장치, 도입·운영 비용을 함께 공개한 뒤에만 권장한다.

## 12. 프로젝트 안에서 Core 수정 방지

Extension 프로젝트 안에 들어간 Core를 그 프로젝트에서 직접 개발하거나 수정하지 못하게 강제할 수 있는지 확인해야 한다.

단순히 문서에 금지 규칙을 쓰는 것인지, 프로젝트 설정·Git·권한·검증 장치로 실제 차단할 수 있는지 구분해 분석해야 한다.

### 작업기록

- **시도했던 작업:** `프로젝트의 core/에서는 직접 개발하지 않는다`는 규칙, Git 변경 감지, hook·CI·권한 같은 차단 수단을 언급했다.
- **개선하려던 내용:** 실수로 Core를 수정하는 것을 안내 수준이 아니라 기술적으로 막을 수 있는지 구분하려 했다.
- **실패한 이유:** 문서 규칙의 억제 효과와 파일 쓰기 권한의 실제 차단, Git에서 변경을 감지해 실패시키는 검증을 명확히 구분하지 못했다. 로컬에 체크아웃된 submodule도 기본적으로 수정 가능하다는 한계를 포함한 확정적 분석이 없었다.
- **사용자에게 발생한 결과:** `수정하지 않는다`는 운영 규칙이 실제 강제인 것처럼 들렸지만, 로컬 수정 가능성을 없애는 해법은 확인되지 않았다.
- **다음 세션의 검증 조건:** 예방, 즉시 차단, 변경 감지, 커밋·병합 차단, 복구를 서로 다른 수준으로 나누고 각 수단이 어디까지 보장하는지 명시해야 한다.

### 작업기록

- **사용자에게 발생한 결과:** 기존보다 Agent 호출·문맥 로딩·동기화·관리 부담이 커질 수 있는 구조를 좋은 구조처럼 권장받았고, 사용자가 비용 누락을 직접 지적해야 했다.
