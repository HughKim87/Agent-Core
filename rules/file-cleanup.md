# 추출 후 파일 정리

- 목적: 파일의 지식·출처·소유권·의존성이 안전하게 이전된 뒤에만 유지·제외·이동·삭제를 판정한다.
- 읽는 시점: 파일·문서·보고서·근거·cache·파생물의 물리적 유지, 삭제, 이동, 개명이나 활성 트리 제외를 판정할 때. 규칙 내용의 의미 통합은 제외한다.
- 책임: 에이전트가 추출 완료·참조·복구·승인 상태를 검증하고, 사용자가 정확한 삭제·이동 대상을 승인한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [상시 정책](../PROJECT_RULES.md), [정보 소유 구조](../docs/INFORMATION_ARCHITECTURE.md).

## 1. 정리 전제

정리 판정 전에 상위 라우터가 함께 선택한 지식 추출 결과가 있어야 한다. 추출할 내용이 없다면 확인한 범위와 `추출 없음`의 근거를 남긴다.

다음 항목 중 하나라도 미확정이면 삭제·이동 후보로 확정하지 않는다.

- 활성 정책·규칙·계약·현재 상태의 소유 여부
- 사용자 승인·source lineage·유일한 검증 근거의 소유 여부
- inbound link, route, import, schema, build, startup, test 의존성
- Git commit 또는 사용자가 승인한 외부 경계의 복구 수단
- 정확한 대상과 실제로 발생할 변화에 대한 승인

삭제 후보 안에 다음 경계가 있으면 상위 경로의 승인에 포함된 것으로 보지 않는다.

- 독립 Git 저장소, submodule, worktree
- symbolic link, junction, reparse point, mount와 그 밖의 별도 filesystem 경계
- 다른 작업이 쓰고 있거나 승인 뒤 내용이 변한 경로

이 경계는 내용을 변경하기 전에 별도 owner와 정확한 대상 경로를 제시하고 다시 승인받는다.
삭제는 운영체제가 제공하는 휴지통·trash를 사용하는 **복구 가능한 삭제**로만 수행한다. 영구 삭제는 사용자의 명시적 요청·승인, 정확한 대상 확인, 현재 작업 scratch 여부와 관계없이 금지한다.

삭제를 실행하기 전에는 정확한 대상 경로와 실제 변화를 제시하고 사용자 승인을 요청한다. 승인된 제거 실행은 플랫폼 휴지통·trash 동작으로 구성한다. 사용할 수 있는 휴지통·trash 수단이 없으면 필요한 도구·환경 준비 또는 다른 복구 가능한 처리 방법을 제시하고 그 행동을 별도로 승인받는다. 이 승인은 영구 삭제를 허용하지 않는다.

## 2. 파일별 판정

| 상태 | 판정 |
|---|---|
| 현재 정책·계약·규칙·schema·검증 코드 | 유지 |
| 현재 상태·승인·source lineage의 유일한 owner | 유지 또는 owner 이전 후 재판정 |
| 추출과 참조 해제가 끝난 중복·역사 자료 | 활성 트리 제외 후보 |
| 생성 절차와 owner가 확인된 cache·파생물 | 재생성 가능 후보 |
| 승인 범위 밖의 보호 원본·파생물 | 정리 대상에서 제외 |
| owner·출처·의존·복구 중 하나가 불명확 | 보류 |

서로 다른 파일을 한 묶음으로 판정하지 않는다. 단 하나의 현재 작업이 만든 격리된 scratch root는 §4의 조건을 모두 만족할 때만 묶어서 판정한다.

## 3. 정리 절차

1. 정확한 대상 경로, 현재 owner, 추출 결과와 남은 출처 정보를 대조한다.
2. 삭제 후보 안의 독립 저장소·worktree·submodule·filesystem 경계와 활성 쓰기 여부를 확인한다. 발견한 경계는 상위 대상에서 분리하고 별도 승인 전에는 변경하지 않는다.
3. 참조 유형별로 검색하고 남은 실행·검증·탐색 의존성을 현재 owner로 이전한다.
4. 정리 뒤에도 필요한 source lineage가 원래 Git 또는 Consumer owner에서 복원되는지 확인한다.
5. 관련 route·링크·schema·테스트와 저장소 gate를 실행한다.
6. scoped diff와 정확한 대상이 사용자 승인 범위와 같은지 확인한다.
7. 삭제·이동은 위 조건이 모두 통과한 뒤 실행한다. 분석·보고·추출 요청은 mutation 권한을 포함하지 않는다.
8. 삭제 승인을 받은 뒤 실제 제거 명령을 플랫폼 휴지통·trash 동작으로 구성하고 그 결과를 확인한다. 복구 가능한 삭제 수단이 없으면 필요한 준비나 대안을 사용자에게 제시하고 별도 승인 전에는 변경하지 않는다.

정리 근거만 보존하기 위한 sidecar 보고서나 저장소 내부 backup 사본을 만들지 않는다. 재사용 지식은 정본에 흡수하고 완료 과정과 복구는 Git이 소유한다.

## 4. 현재 작업 scratch의 예외

다음 조건을 모두 만족하면 현재 작업의 scratch root를 파일별 의미 재분석 없이 한 번에 정리할 수 있다.

- 작업 시작 baseline에는 없었고 현재 작업만 생성했다.
- scratch root의 정확한 대상 경로가 작업 계약에 정해져 있다.
- 유지 파일·최종 산출물·승인·source lineage·보호 경로가 없다.
- 필요한 판단은 이미 유지 정본에 흡수되었다.
- 제거 뒤 final·maintained·protected 경로의 변화가 없다.

pre-existing, shared, owner 불명, 보호 경로는 이 예외를 사용할 수 없다.
이 예외는 파일별 의미 재분석만 생략한다. 복구 가능한 삭제와 경계 확인 의무는 생략하지 않는다.

## 5. 검증

- 각 후보에 정확한 대상 경로, 판정, 추출 완료 여부, owner, 남은 참조, 복구 수단, 승인 상태가 있는지 확인한다.
- 상위 경로 승인만으로 독립 저장소·worktree·submodule·filesystem 경계를 변경하지 않았는지 확인한다.
- 활성 쓰기나 승인 뒤 변경이 발견된 경로가 별도 승인 전에는 변경되지 않았는지 확인한다.
- 삭제 대상에만 남은 활성 규칙·상태·승인·source lineage·유일 근거가 0인지 확인한다.
- 삭제·이동 뒤 고아 route·링크·schema·import가 없고 관련 회귀와 gate가 통과하는지 확인한다.
- 모든 삭제가 플랫폼 휴지통·trash를 사용했고, 사용자 승인이나 scratch 예외로 영구 삭제가 실행되지 않았으며, 실패 시 영구 삭제로 대체되지 않았는지 확인한다.
- 삭제 전에 정확한 대상 경로와 실제 변화에 대한 승인을 받았고, 승인된 제거 실행이 휴지통·trash 동작으로 구성됐는지 확인한다.
- 보호 경로와 무관한 사용자 변경이 scoped diff에 섞이지 않았는지 확인한다.
- 실행하지 않은 정리와 검사를 완료·통과로 기록하지 않는다.
