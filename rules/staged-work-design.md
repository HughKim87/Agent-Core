# 단계 작업 설계

- 목적: 여러 단계와 세션에 걸친 작업을 짧고 재개 가능한 설계로 관리하고, 오래된 승인으로 실행이 계속되지 않게 한다.
- 읽는 시점: 의존 관계가 있는 여러 단계로 구성된 `controlled` 작업을 설계·실행·재개·전환할 때.
- 책임: 에이전트가 설계와 전환을 유지하고 사용자가 단계 구성과 성공 조건을 승인한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [상시 정책](../PROJECT_RULES.md). 계약 무효화의 소유자는 라우터에서 선택한다.

---

## 1. 세 가지 책임의 분리

| 책임 | 소유 | 포함하지 않는 것 |
|---|---|---|
| 전체 설계 | 단계 구성, 의존 순서, 단계별 성공 조건 | 현재 진행 상황 |
| 현재 단계 설계 | 이번 단계의 결정 대상, 변경 범위, 검증 명령, 복구 방법 | 다른 단계의 상세 |
| 현재 상태 | 현재 단계, 차단, 승인 상태, 첫 다음 행동 | 완료된 단계의 과정 |

각 책임의 내용을 중복 복제하지 않는다. 단계는 독립적인 진입·성공 조건이 필요한 의존 구간으로 정하며, 조사·구현·검증·상태 갱신이라는 활동 구분만으로 단계를 늘리지 않는다.

## 2. 단계 진행 절차

1. **진입 확인**: 이전 단계의 성공 게이트와 증거를 읽고 선행 조건 충족을 확인한다.
2. **현황 조사**: 현재 파일과 실행 결과를 우선한다. 과거 보고서를 현재 사실로 쓰지 않는다.
3. **단계 설계**: 결정 대상, 변경 범위, 제외 범위, 변경 영향에 맞는 검증 방법과 확대 조건, 복구 방법을 정한다.
4. **사용자 확인**: 기존 승인·위임으로 결정할 수 있는지 확인한다. 그 경계를 넘는 정책·구조·범위·성공 조건의 변경은 구현 전에 결정을 받는다.
5. **구현**: 승인되거나 명백히 위임된 범위만 최소 단위로 변경한다.
6. **직접 검증**: 3에서 정한 검증을 현재 작업 트리에서 실제로 실행한다.
7. **후보 판정**: 각 성공 조건을 `pass`, `fail`, `not_run`, `not_applicable` 중 하나로 판정한다. 이 시점의 통과는 완료 후보일 뿐이다.
8. **후보 snapshot 생성**: 상태와 다음 첫 행동을 갱신하고 정확한 변경만 단계 후보 커밋으로 만든다.
9. **커밋 snapshot 확인**: 실제 후보 커밋의 경로와 선택된 검증 증거를 확인한다. 릴리스·재현성·패키징·submodule 도달성을 주장하는 단계는 임시 clean clone에서 그 주장에 필요한 검사를 실행한다.
10. **전환**: 후보 커밋에 선택된 모든 필수 게이트가 `pass`인 경우에만 완료로 확정하고 다음 단계 작업을 시작한다.

## 3. 조건과 행동

- **조건**: 한 단계의 게이트가 `fail` 또는 `not_run`이다.
  - **행동**: 다음 단계를 시작하지 않는다. 현재 단계에 머물러 원인과 재시작 조건을 기록한다.
- **조건**: 작업 트리는 통과하지만 후보 커밋에 선택된 snapshot 검증이 실패한다.
  - **행동**: 후보를 그 완료 수준의 이력으로 주장하지 않고 다음 단계 작업을 시작하지 않는다. 누락 경로와 상태를 교정한 새 후보에서 실패한 증거를 다시 확인한다.
- **조건**: 현재 단계 범위를 넘어야만 해결되는 문제를 발견한다.
  - **행동**: 후속 단계를 선행 구현하지 않는다. 차단 사항과 필요한 결정으로 보고한다.
- **조건**: 전체 설계 또는 현재 단계 설계가 바뀌었다.
  - **행동**: §5로 승인된 결정에 미치는 영향을 확인한다. 작업 계약 소유자가 실질적 계약 변경으로 판정한 경우에만 대기 중 변경을 중단하고 설계·승인을 다시 확정한다.

## 4. 활성 단계는 하나

한 번에 활성 단계는 정확히 하나다. 여러 단계를 한꺼번에 완료 처리하지 않는다.

한 커밋에 여러 단계의 산출물을 섞으면 어느 단계가 어떤 근거로 통과했는지 추적할 수 없다. 단계 완료는 단계마다 별도 체크포인트로 남긴다.

## 5. 설계 변경 감지

설계 변경은 문서의 식별값 변화와 승인된 결정의 변화를 구분한다. 계약 무효화는 상위 라우터가 선택한 작업 계약 소유자가 판정한다.

- 승인된 결정과 현재 설계의 대응을 식별할 수 있어야 한다.
- 진행 상태·검증 근거·표현 갱신은 승인된 결정이 유지되면 기존 위임 안에서 반영한다. 필수 보장·검증 수준을 낮춘 변경을 단순 갱신으로 취급하지 않는다.
- fingerprint, 커밋 SHA 또는 동등한 값은 설계 내용을 식별하는 수단이며, 값이 바뀌었다는 사실만으로 재승인을 요구하지 않는다.

## 6. 예외

- 단계가 하나뿐인 작업에는 이 규칙을 적용하지 않는다. 라우터가 선택하는 작업 계약 소유자로 충분하다.
- 사용자가 전체 단계를 위임한 경우 기존 위임 안의 판단마다 확인을 반복하지 않는다. 위임은 상위 정책의 승인 경계나 게이트 판정 의무를 면제하지 않는다.

## 7. 검증

- 두 단계 이상의 작업을 중단·재개·전환해 본다.
- 완료된 단계의 상세가 현재 상태 문서에 누적되지 않는지 확인한다.
- 활성 단계가 둘 이상이 아닌지 확인한다.
- 각 단계에 진입 조건, 성공 게이트, 전환 조건이 있는지 확인한다.
- 같은 성공 조건의 근거 갱신은 계속 진행하고, 승인 경계를 바꾸거나 필수 보장을 낮춘 변경은 재확정하는지 대조한다.
- route·패키징·submodule 재현성을 주장하는 단계에서는 작업 트리에만 존재하는 대상이 선택된 snapshot 검사에서 탐지되는지 확인한다.
