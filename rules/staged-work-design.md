# 단계 작업 설계

- 목적: 여러 단계와 세션에 걸친 작업을 짧고 재개 가능한 설계로 관리하고, 오래된 승인으로 실행이 계속되지 않게 한다.
- 읽는 시점: 의존 관계가 있는 여러 단계로 구성된 `controlled` 작업을 설계·실행·재개·전환·전체 종료할 때.
- 책임: 에이전트가 설계와 전환을 유지하고 사용자가 단계 구성과 성공 조건을 승인한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [상시 정책](../PROJECT_RULES.md). 계약 무효화의 소유자는 라우터에서 선택한다.

---

## 1. 세 가지 책임의 분리

| 책임 | 소유 | 포함하지 않는 것 |
|---|---|---|
| 전체 설계 | 단계 구성, 의존 조건, 단계별 성공 조건 | 현재 진행 상황 |
| 현재 단계 설계 | 이번 단계의 결정 대상, 변경 범위, 검증 방법, 복구 방법 | 다른 단계의 상세 |
| 현재 상태 | 주 진입단계, 재개에 필요한 독립 활동, 차단, 승인 상태, 첫 다음 행동 | 재개 판단에 필요 없는 완료 과정 |

각 책임의 내용을 중복 복제하지 않는다. 단계는 독립적인 진입·성공 조건이 필요한 의존 구간으로 정하며, 조사·구현·검증·상태 갱신이라는 활동 구분만으로 단계를 늘리지 않는다.

## 2. 단계 진행 기준

다음은 단계별로 충족할 기준이다. 선행 결과에 의존하는 행동은 그 결과의 게이트를 기다린다. 그 밖의 순서·도구·작업 분담은 같은 품질·안전·증거 수준을 충족하는 방법으로 조정할 수 있다.

1. **진입 확인**: 이번 행동이 의존하는 성공 게이트와 증거를 읽고 선행 조건 충족을 확인한다.
2. **현황 조사**: 현재 파일과 실행 결과를 우선한다. 과거 보고서를 현재 사실로 쓰지 않는다.
3. **단계 설계**: 결정 대상, 변경 범위, 제외 범위, 변경 영향에 맞는 검증 방법과 확대 조건, 복구 방법을 정한다.
4. **승인 확인**: 기존 승인·위임으로 결정할 수 있는지 확인한다. 그 경계를 넘는 정책·구조·범위·성공 조건의 변경은 구현 전에 결정을 받는다.
5. **구현**: 승인되거나 명백히 위임된 범위를 변경한다. 공유 쓰기·권한·예산·결과의 충돌이 없고 선행 조건에 의존하지 않는 활동은 병렬로 진행할 수 있다.
6. **직접 검증**: 선택한 검증을 현재 작업 트리에서 실제로 실행한다.
7. **후보 판정**: 각 성공 조건을 `pass`, `fail`, `not_run`, `not_applicable` 중 하나로 판정한다. 이 시점의 통과는 완료 후보일 뿐이다.
8. **후보 체크포인트**: 상태와 첫 다음 행동, 검증한 내용의 식별 근거를 갱신한다. 승인된 Git 변경 작업은 정확한 이번 변경만 커밋하며 중간 보존과 검증 완료를 구분한다. 명시적 커밋 보류나 안전한 분리·권한 문제로 커밋하지 못하면 미커밋 범위와 동일 workspace 재개 의존을 명시한다.
9. **증거 수준 확인**: 검증된 작업 트리 체크포인트와 commit snapshot을 구분한다. 완료 커밋을 만들었거나 gitlink·portable·릴리스 재현성을 주장하면 실제 커밋의 경로와 검증 증거를 확인한다. 필요한 커밋 권한이 없으면 작업 트리 수준까지만 보고하고 더 높은 수준의 완료를 보류한다. 릴리스·재현성·패키징·submodule 도달성을 주장하는 단계는 임시 clean clone에서 그 주장에 필요한 검사를 실행한다.
10. **전환**: 요청된 완료 수준에 선택된 모든 필수 게이트가 `pass`인 경우에만 해당 단계의 완료를 확정하고 그 결과에 의존하는 행동을 시작한다. 허용된 커밋 보류 자체는 같은 workspace에서 검증하고 전환하는 작업의 차단이 아니지만, 실제 커밋이 필요한 완료 수준은 충족해야 한다.

## 3. 조건과 행동

- **조건**: 한 단계의 필수 게이트가 `fail` 또는 `not_run`이다.
  - **행동**: 그 결과에 의존하는 행동을 보류하고 원인과 재시작 조건을 기록한다. 이미 승인된 독립 활동은 §2의 충돌 조건을 확인해 계속할 수 있다.
- **조건**: 작업 트리는 통과하지만 후보 커밋에 선택된 snapshot 검증이 실패한다.
  - **행동**: 후보를 그 완료 수준의 이력으로 주장하지 않고 해당 증거에 의존하는 전환을 보류한다. 누락 경로와 상태를 교정한 새 후보에서 영향받은 증거를 다시 확인한다.
- **조건**: 현재 단계의 방법이나 순서를 바꿔야 해결되는 문제를 발견한다.
  - **행동**: 같은 승인·성공 조건 안의 조정이면 설계와 의존 조건을 갱신한다. 승인 경계를 넘거나 충족하지 못한 선행 조건을 요구하는 행동은 보류하고 필요한 결정을 보고한다.
- **조건**: 전체 설계 또는 현재 단계 설계가 바뀌었다.
  - **행동**: §5로 승인된 결정에 미치는 영향을 확인한다. 작업 계약 소유자가 실질적 계약 변경으로 판정한 경우에만 대기 중 변경을 중단하고 설계·승인을 다시 확정한다.

## 4. 주 진입단계와 독립 활동

재개 기준이 되는 주 진입단계는 하나로 식별한다. 함께 진행하는 독립 활동 중 재개 판단에 영향을 주는 것은 소유자·범위·의존 조건·검증 상태를 현재 상태에서 식별할 수 있어야 한다. 개별 도구 호출이나 완료된 조사를 활동 목록으로 누적하지 않는다. 활동을 병렬로 시작했다는 이유로 미충족 단계나 여러 단계의 완료를 일괄 선언하지 않는다.

단계별 내용과 성공 증거를 식별할 수 있는 체크포인트를 남긴다. 커밋 단위는 단계 번호보다 논리적 완료·원자성·복구 가능성으로 정하며, 여러 단계의 변경을 함께 담아야 일관성이 유지되면 함께 커밋할 수 있다. 이때 각 성공 조건과 근거의 연결은 유지한다. 미커밋 체크포인트를 독립 clone에서 복원 가능한 이력으로 표현하지 않는다.

## 5. 설계 변경 감지

설계 변경은 문서의 식별값 변화와 승인된 결정의 변화를 구분한다. 계약 무효화는 상위 라우터가 선택한 작업 계약 소유자가 판정한다.

- 승인된 결정과 현재 설계의 대응을 식별할 수 있어야 한다.
- 방법·순서·작업 분담·진행 상태·검증 근거·표현의 조정은 승인된 결과·경계·필수 보장이 유지되면 기존 위임 안에서 반영한다. 필수 보장·검증 수준을 낮춘 변경을 단순 갱신으로 취급하지 않는다.
- fingerprint, 커밋 SHA 또는 동등한 값은 설계 내용을 식별하는 수단이며, 값이 바뀌었다는 사실만으로 재승인을 요구하지 않는다.

## 6. 전체 단계 작업의 종료 보고

이 규칙이 적용되는 controlled 의존 단계 작업 전체를 완료·부분 완료·중단·실패로 종료할 때, 작업 소유 Consumer 내부에 최종보고 문서 하나를 작성하거나 같은 작업의 기존 보고서를 갱신한다. 전체 종료 시 현재 상태를 갱신해 최종 판정·보고서 참조·남은 행동을 남긴다. 최종 응답에서 문서 링크와 최종 판정을 함께 보고한다. Git 변경 작업이면 보고서도 이번 작업의 로컬 커밋에 포함하고, 허용된 커밋 보류 시 실제 저장 위치와 미커밋 사유를 밝힌다.

개별 단계 전환은 기존 설계·현재 상태의 결과와 검증 근거를 갱신하며 단계마다 별도 최종보고서를 만들지 않는다. 단순 세션 인계·일시 정지는 상태를 갱신하고 재개하며 전체 종료로 취급하지 않는다. 단일 단계 일반 작업·읽기·제안만 수행하는 요청에 이 보고 의무를 확대하지 않는다. 사용자의 명시적 보고서 생략·형식 지시는 우선한다.

전체 종료의 완료 조건에는 보고서 저장·필요한 커밋·최종 응답 링크를 포함한다. 구현 성공과 보고서 미완료를 구분한다. 보고서의 내용·저장·중복 방지는 문서 작업의 책임이며, 현재 상태에는 판정·보고서 참조·남은 행동만 남긴다.

## 7. 예외

- 단계가 하나뿐인 작업에는 이 규칙을 적용하지 않는다. 라우터가 선택하는 작업 계약 소유자로 충분하다.
- 사용자가 전체 단계를 위임한 경우 기존 위임 안의 판단마다 확인을 반복하지 않는다. 위임은 상위 정책의 승인 경계나 게이트 판정 의무를 면제하지 않는다.

## 8. 검증

- 두 단계 이상의 작업을 중단·재개·전환하고, 주 진입단계와 독립 활동의 의존 조건을 복원할 수 있는지 확인한다.
- 현재 상태에는 재개 판단에 필요한 결정·제약·증거가 남고 불필요한 완료 과정이 누적되지 않는지 확인한다.
- 각 단계에 진입 조건, 성공 게이트, 전환 조건이 있는지 확인한다.
- 선행 게이트 실패가 의존 행동을 막고, 충돌 없는 승인된 독립 활동까지 막지 않는지 대조한다.
- 같은 성공 조건의 방법·근거 조정은 계속 진행하고, 승인 경계를 바꾸거나 필수 보장을 낮춘 변경은 재확정하는지 대조한다.
- route·패키징·submodule 재현성을 주장하는 단계에서는 작업 트리에만 존재하는 대상이 선택된 snapshot 검사에서 탐지되는지 확인한다.
- 허용된 커밋 보류의 workspace 전환과 실제 커밋이 필요한 완료 수준을 구분하고, 후자에 커밋 증거가 빠지면 그 수준으로 전환하지 않는지 확인한다.
- 전체 종료 보고서의 실제 위치·판정·필수 내용·최종 응답 링크와 커밋 또는 보류 사유를 확인한다. 개별 단계·일시 인계·단일 단계 일반 작업에 보고서가 남발되지 않는지 대조한다.
