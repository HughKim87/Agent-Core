# 실패 처리와 예방책 흡수

- 목적: 한 사용자 실행 명령 안의 반복 실패를 제한하고, 해결·검증된 실패의 일반화 가능한 예방책만 기존 규칙·검사에 흡수해 사건 이력 없이 재발을 줄인다.
- 읽는 시점: 현재 사용자 실행 명령에서 결과 시도가 실패했을 때, 해결·검증된 실패의 예방책을 판단할 때.
- 책임: 에이전트가 현재 실행 명령의 임시 실패 카운터와 예방 소유자를 관리하고, 사용자가 새 정본 추가를 승인한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [상시 정책](../PROJECT_RULES.md).

## 1. 실패 분류

| 분류 | 의미 | 처분 |
|---|---|---|
| 환경 | 런타임, 경로, 인코딩, 샌드박스 제약 | 원인이 환경이면 코드를 고치지 않는다 |
| 권한 | 승인 부재, 접근 차단 | 안전 정지다. 실패 지식이 아니다 |
| 입력 | 요청 모호, 대상 불명확 | 계약을 다시 세운다 |
| 계약 | 문서와 구현의 불일치 | 권위 있는 요구와 대조해 문서·구현 중 잘못된 쪽을 확인한다. 구현에 맞추려고 요구를 낮추지 않는다 |
| 구현 | 코드 결함 | 재현 조건을 먼저 고정한다 |
| 검증 | 검사 자체의 결함이나 부재 | 검사를 먼저 고친다 |

분류는 진단과 다음 방법 선택의 근거다. 서로 다른 분류를 구분하되 현재 실행 명령의 실패 횟수를 분류별로 나누지는 않는다.

## 2. 현재 실행 명령의 반복 실패 제한

### 명령 창과 결과 시도

- `사용자 실행 명령`은 실행·수정·재시도·재개를 새로 지시한 사용자 메시지다. 상태 질문이나 설명 요청만으로는 실행 명령이 시작되지 않는다.
- `명령 창`은 사용자 실행 명령을 처리하기 시작할 때 열리고, 최종 응답·사용자 취소·새 사용자 실행 명령 중 먼저 발생한 시점에 닫힌다.
- 도구 호출, 중간 commentary, 하위 Agent와 자동 계속은 새 사용자 실행 명령이 아니다.
- `결과 시도`는 후보 방법이나 변경 묶음 하나를 적용하고 요청 결과와 선택된 필수 게이트를 한 번 판정하는 단위다.
- `임시 실패 상태`는 현재 명령 창의 카운터, 확인된 실패 횟수, 시도 방법과 순서, 중단 여부를 뜻한다.

### 카운터와 중단

1. 명령 창마다 임시 카운터 하나만 만들고 모든 하위 단계와 Agent가 공유한다.
2. 결과 또는 선택된 필수 게이트의 미충족이 확인되어 후보를 폐기하거나 수정해야 할 때 결과 시도 실패를 1회 올린다.
3. 후보 하나에서 결과와 여러 필수 게이트가 함께 실패해도 카운터는 최대 1만 올린다.
4. 진단용 탐색, 빈 검색 결과, 의도된 실패 테스트, 복구된 일시적 도구 오류는 결과 시도 실패가 아니다. 도구 오류 때문에 후보 전체를 포기하면 도구 오류 수가 아니라 그 후보를 1회로 계산한다.
5. 승인·권한·필요 결정·보호 경계 때문에 결과 시도를 시작하지 않은 안전 정지는 실패가 아니다. 외부 효과의 성공 여부가 불명확한 상태도 확인된 실패로 세지 않고 상태 확인 전 재시도하지 않는다.
6. 첫 번째와 두 번째 실패 뒤에는 확인한 원인을 반영한 다른 결과 시도를 선택할 수 있지만 같은 명령 창의 카운터를 초기화하지 않는다.
7. 결과 후보는 직렬로 판정하고 남은 허용 횟수보다 많은 후보를 미리 시작하지 않는다. 결과 시도가 아닌 독립 진단은 병렬로 수행할 수 있다.
8. 세 번째 실패가 확정되면 현재 명령 창에서 네 번째 결과 시도를 시작하지 않는다. 직전 안전 상태로의 복원, 위해 제한, 최소 읽기 확인과 최종 보고는 허용하지만 요청 결과를 달성하기 위한 새 수정은 네 번째 결과 시도다.
9. 명령 창이 닫히면 카운터와 중단 상태를 즉시 폐기한다. 사용자가 같은 결과를 다시 실행하도록 지시해도 새 명령 창은 0부터 시작하며, 교정과 함께 실행을 재개한 경우도 같다.

이 임시 실패 상태는 현재 상태, 핸드오프, 별도 실패 문서나 다음 세션에 저장하지 않는다.

### 제한 근거와 허용 대안

- 예방하는 위해는 확인된 원인을 해소하지 못한 결과 변경이 같은 명령 안에서 계속되어 검증된 상태를 훼손하거나 변경 범위·비용을 통제하지 못하게 되는 것이다.
- 제한은 같은 명령 창의 세 번째 결과 실패가 확인된 때에만 발동하며 진단, 안전 정지와 복구, 위해 제한, 최소 읽기 확인, 최종 보고는 막지 않는다.
- 최종 보고 뒤 사용자가 원인과 남은 위험을 보고 새 실행 명령을 내리면 새 명령 창에서 다시 진행할 수 있다.
- 방법별·하위 단계별 제한이나 경고만으로는 방법 교체와 병렬 후보가 제한을 우회할 수 있으므로, 명령 창 전체가 공유하는 단일 카운터와 직렬 결과 판정이 필요한 최소 제한이다.

## 3. 해결된 실패의 기본 처분

실패가 해결되고 검증되면 Agent의 일반화된 판단·행동 변경이 필요한지 먼저 구분한다. 구현에만 특정되고 그런 변경이 필요하지 않으면 기존 회귀 검사만 보강하며, 아래 규칙 흡수 절차는 적용하지 않는다.

1. 일반화된 판단·행동이 필요하면 가장 좁은 기존 규칙 소유자를 먼저 찾는다. 구별되는 trigger와 독립 책임으로 기존 소유자가 수용할 수 없을 때만 상위 라우터가 선택한 규칙 거버넌스에 따라 새 소유자를 판정한다.
2. 일반화 가능한 판단·행동은 활성 규칙 하나의 조건·행동에 한 번 표현한다. 테스트와 fixture는 관측 가능한 입력·결과·near-miss를 검증하며 독립된 정책 정본을 만들지 않는다.
3. 예방책이 실제 결함을 탐지하거나 기대 행동을 재현하는지 검증한다. 구조 검사·합성 모델·Agent 의미 재현을 구분하고 실제로 관측한 수준만 주장한다.
4. 별도 실패 이력 없이 다음 작업의 선택·검증·복구 판단이 같으면 처분을 종료한다.

검색·정규식은 검토 후보를 찾는 진단에 사용할 수 있지만 그 결과만으로 자연어 의미·규범 중복·소유권을 확정하지 않는다. 구조적 route 유일성은 기계 검사로, 규칙의 의미와 일반화는 상위 라우터가 선택한 규칙 거버넌스의 독립 감사로 판정한다. 실패 사건 문서는 예방책이나 사건 이력을 다시 소유하지 않는다.

## 4. 기록하지 않는 것

| 대상 | 이유 |
|---|---|
| 임시 실패 상태와 사건별 실패 서사 | 현재 명령에만 유효하며 재사용 지식이 아니다 |
| 미해결 차단의 시도 이력 | 현재 상태에는 원인·필요 결정·재시작 조건만 필요하다 |
| 거부된 승인 요청 | 예상된 안전 정지다 |
| 교정된 일회성 오타·인용 오류·옵션 실수 | 재사용 가치가 없다 |
| 복구된 일시적 도구 오류 | 재현되지 않으면 지식이 아니다 |
| 규칙에 흡수되고 테스트로 검증된 해결 사례 | 예방 소유자가 이미 재발을 막는다 |
| 같은 원인의 두 번째 문서 | 기존 예방 소유자를 갱신한다 |

실패의 원인이 아직 해결되지 않았으면 실패 지식으로 저장하지 않는다. 현재 작업을 재개하는 데 필요한 원인·필요 결정·재시작 조건과 실제 파일·Git 상태만 현재 상태에 유지하고, 해결되면 제거한다.

## 5. 조건과 행동

- **조건**: 현재 명령 창의 결과 시도가 실패한다.
  - **행동**: §2의 임시 카운터에 반영하고 남은 결과 시도와 허용된 복구·보고 경계를 적용한다.
- **조건**: 해결되고 검증된 실패에 일반화된 Agent 판단·행동의 변경이 필요하다.
  - **행동**: §3에 따라 기존 규칙에 흡수하고 그 예방책을 검증한다.
- **조건**: 기존 예방 소유자와 같은 원인의 실패가 재발한다.
  - **행동**: §3의 분류에 따라 해당 기존 소유자를 보강한다. 구현에만 특정된 재발은 회귀 검사만 보강하고, Agent 판단·행동의 변경이 필요한 재발만 규칙을 보강한다.
- **조건**: 해결된 실패가 구현에만 특정되고 Agent의 판단·행동을 바꾸지 않는다.
  - **행동**: 기존 회귀 검사만 보강하고 활성 규칙을 바꾸지 않는다.
- **조건**: 실패의 원인이 아직 확인되지 않았다.
  - **행동**: 실패 지식으로 저장하지 않고 현재 차단과 재시작 조건만 유지한다.

## 6. 검증

- 같은 사용자 실행 명령에서 세 번째 결과 시도 실패 뒤 네 번째 결과 시도가 차단되는지 확인한다.
- 명령 창이 닫힌 뒤 같은 결과의 새 사용자 실행 명령이 0부터 시작하는지 확인한다.
- 사용자 교정과 함께 실행을 재개해도 이전 명령의 횟수를 승계하지 않는지 확인한다.
- 후보 하나의 여러 미충족, 비계수 진단·안전 정지, 복구와 새 결과 시도의 경계를 확인한다.
- 하위 단계·Agent와 병렬 진단이 임시 카운터 경계를 우회하지 않는지 확인한다.
- 해결 사례의 일반화된 판단·행동이 활성 규칙 정확히 하나에만 있고 테스트·fixture가 규범 소유자가 되지 않았는지 확인한다.
- 구현에만 특정된 회귀 검사가 불필요한 활성 규칙을 만들지 않았는지 확인한다.
- 현재 상태와 핸드오프에 §2가 정의한 임시 실패 상태가 남지 않는지 확인한다.
