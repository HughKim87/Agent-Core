# 실패 경험의 예방책 흡수

- 목적: 현재 세션의 같은 작업 실패를 제한하고, 검증된 실패 경험을 기존 규칙·검사에 흡수해 같은 원인의 재발을 줄인다.
- 읽는 시점: 현재 세션에서 같은 작업의 실패를 누적·중단할 때, 실질적이고 일반화 가능한 실패가 확인됐을 때, 실패 문서의 종료를 판단할 때.
- 책임: 에이전트가 현재 세션의 작업별 실패 카운터와 예방 소유자를 관리하고, 사용자가 새 정본 추가와 기존 문서 삭제·이동을 승인한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [상시 정책](../PROJECT_RULES.md).

---

## 1. 실패 분류

| 분류 | 의미 | 처분 |
|---|---|---|
| 환경 | 런타임, 경로, 인코딩, 샌드박스 제약 | 원인이 환경이면 코드를 고치지 않는다 |
| 권한 | 승인 부재, 접근 차단 | 안전 정지다. 실패 지식이 아니다 |
| 입력 | 요청 모호, 대상 불명확 | 계약을 다시 세운다 |
| 계약 | 문서와 구현의 불일치 | 정본을 먼저 고친다 |
| 구현 | 코드 결함 | 재현 조건을 먼저 고정한다 |
| 검증 | 검사 자체의 결함이나 부재 | 검사를 먼저 고친다 |

**분류가 먼저다.** 서로 다른 분류의 실패를 같은 재시도로 묶으면 원인이 확정되지 않은 채 시도만 늘어난다.
분류는 진단과 다음 방법 선택의 기준이며 같은 사용자 결과에 대한 실패 카운터를 분리하거나 초기화하는 기준은 아니다.

## 2. 기본 처분

실패가 해결되고 검증되면 새 문서를 만드는 대신 다음 순서로 처분한다.

1. 같은 원인의 재발을 막을 가장 좁은 기존 규칙 또는 검사 소유자를 찾는다.
2. 재발 조건을 규칙의 조건·행동이나 결함 주입 테스트로 표현한다.
3. 그 예방책이 실제로 실패를 탐지하거나 행동을 차단하는지 실행한다.
4. 별도 실패 문서가 없어도 다음 작업의 선택·검증·복구 판단이 같으면 기록을 종료한다.

예방책의 활성 정본은 규칙 또는 테스트 하나다. 실패 문서는 같은 예방책을 다시 소유하지 않는다.

## 3. 기록하지 않는 것

| 대상 | 이유 |
|---|---|
| 미해결 차단 | 현재 상태 문서가 소유한다 |
| 거부된 승인 요청 | 예상된 안전 정지다 |
| 교정된 일회성 오타·인용 오류·옵션 실수 | 재사용 가치가 없다 |
| 일시적 도구 오류 | 재현되지 않으면 지식이 아니다 |
| 규칙·테스트에 완전히 흡수된 해결 사례 | 예방 소유자가 이미 재발을 막는다 |
| 같은 원인의 두 번째 문서 | 기존 예방 소유자를 갱신한다 |

## 4. 예외적 최소 진단 문서

다음 조건을 **모두** 만족할 때만 최소 진단 문서를 유지할 수 있다.

1. 원인·해결·검증이 확인되었다.
2. 같은 원인이 다시 발생할 수 있다.
3. 현재 규칙·테스트만으로 도출할 수 없는 비자명한 진단 정보가 남는다.
4. 그 비자명한 정보가 무엇인지 한 문장으로 설명할 수 있다.

문서는 비자명한 진단과 적용 경계만 남긴다. 실패 서사, 반복된 예방책, transcript, 작업 유형→실패 문서 매핑은 보존하지 않는다. 일반 작업 route와 기본 시작 컨텍스트에도 추가하지 않는다.

## 5. 현재 세션의 반복 실패 중단

### 작업과 실패

- 하나의 사용자 결과를 달성하기 위한 전체 실행 연쇄를 같은 작업으로 식별한다.
- 방법·도구·진단·검증·복구·하위 단계를 바꿔도 사용자 결과가 같으면 같은 작업이다.
- 결과·필수 게이트 미충족과 확인된 요구 미충족에 대한 사용자 교정은 실패다.
- 사용자가 실제 요구를 변경해 작업 계약이 무효화된 경우와 승인·권한 부재로 실질 실행을 시작하지 않은 안전 정지는 실패가 아니다.

### 카운터와 중단

1. 같은 작업의 실패가 확정될 때마다 현재 세션의 카운터를 1씩 올린다.
2. 첫 번째와 두 번째 실패 뒤에는 원인을 반영한 다른 방법을 선택할 수 있지만 카운터를 초기화하지 않는다.
3. 세 번째 실패가 확정되면 성공 가능성이나 새 방법의 유무와 관계없이 해당 작업 실행을 중단한다. 네 번째 실행을 시작하지 않는다.
4. 중단 시 실패 유형, 확인한 원인, 시도한 방법, 대체 방법, 재시작 조건을 보고한다. 작업을 인계해야 하면 현재 상태에도 남기되 카운터 자체는 승계 가능한 상태로 기록하지 않는다.

카운터는 현재 세션에서만 관리한다. 새 세션은 이전 카운터를 이어받지 않으며, 중단 절차로 수행하는 보고·복구·핸드오프 작성은 원 작업의 추가 시도가 아니다. 같은 작업이 성공하거나 사용자가 실제 요구를 변경하면 그 작업의 카운터는 더 이상 활성 상태가 아니다.

## 6. 조건과 행동

- **조건**: 해결되고 검증된 실패가 재발할 수 있다.
  - **행동**: 기존 규칙 또는 테스트를 보강하고 같은 원인의 결함을 재현해 예방책을 검증한다.
- **조건**: 실패의 원인이 아직 확인되지 않았다.
  - **행동**: 실패 지식으로 저장하지 않는다. 현재 상태의 차단으로 남긴다.
- **조건**: 기존 예방 소유자와 같은 원인의 실패가 재발한다.
  - **행동**: 새 문서를 만들지 않고 그 규칙 또는 테스트의 조건과 검증을 보강한다.
- **조건**: 같은 작업의 세 번째 실패가 확정된다.
  - **행동**: 방법을 바꿔 계속하지 않고 해당 작업 실행을 중단한 뒤 원인·대안·재시작 조건을 보고한다.

## 7. 예외

- 사용자가 특정 실패의 기록을 요청하면 만들 수 있다. 단 미해결임과 종료 조건을 명시하고 기본 route에는 추가하지 않는다.

## 8. 검증

- 미해결 실패가 현재 상태 밖에서 해결된 지식으로 저장되지 않았는지 확인한다.
- 해결 사례의 예방 항목이 규칙 또는 테스트 소유자 정확히 하나에 흡수됐는지 확인한다.
- 실패 문서를 제거해도 정책 선택, 검증, 복구 판단이 달라지지 않는지 확인한다.
- 유지 문서마다 규칙에서 도출할 수 없는 비자명한 정보가 한 문장으로 설명되는지 확인한다.
- 실패 문서가 일반 route나 기본 시작 컨텍스트에 추가되지 않았는지 확인한다.
- 방법·도구가 달라져도 같은 사용자 결과의 실패가 누적되고 세 번째 실패 뒤 네 번째 실행이 차단되는지 확인한다.
- 요구 미충족 교정, 실제 요구 변경, 새 세션, 핸드오프 작성의 카운터 경계를 확인한다.
