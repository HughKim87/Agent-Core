# 작업 계약

- 목적: 에이전트가 무엇을 해야 하고 하지 말아야 하며 무엇으로 완료를 판단할지 작업 내내 명시적으로 유지한다.
- 읽는 시점: 여러 파일이나 동작을 바꾸는 작업을 시작할 때, 요청 범위가 모호할 때, 사용자가 진행 중인 작업을 교정할 때, 완료를 보고하기 전.
- 책임: 에이전트가 계약을 유지하고 사용자가 결과와 금지 범위를 소유한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [상시 정책](../PROJECT_RULES.md).

---

## 1. 최소 계약

작업을 시작하기 전에 다음 일곱 항목을 확인한다. 문서로 만들 필요는 없고 `controlled` 작업에서만 명시적으로 기록한다.

| 항목 | 내용 |
|---|---|
| 원하는 결과 | 검증 가능한 표현으로 서술한 최종 상태 |
| 허용 행동 | 이 작업에서 해도 되는 변경의 종류 |
| 제외 범위 | 명시적으로 하지 않을 것 |
| 입력 참조 | 근거로 삼을 정확한 파일과 출처 |
| 보호 경계 | 건드리면 안 되는 경로와 데이터 |
| 필요한 결정 | 사용자만 정할 수 있는 항목 |
| 검증 수준 | 완료 판정에 필요한 최소 증거 |

`원하는 결과`를 검증 가능한 표현으로 쓸 수 없으면 작업을 시작하지 않는다. "개선한다", "정리한다", "좋게 만든다"는 검증 가능한 결과가 아니다.

## 2. 조건과 행동

- **조건**: 요청이 여러 파일이나 동작을 바꾼다.
  - **행동**: §1의 일곱 항목을 확인하고, 확인되지 않은 항목이 승인된 결과를 바꾸면 질문한다.
- **조건**: 요청이 모호하다.
  - **행동**: 가장 좁은 해석으로 진행하고 그 해석을 결과와 함께 밝힌다. 해석에 따라 되돌릴 수 없는 결과가 갈리면 질문한다.
- **조건**: 사용자가 가능성·개선안·계획·남은 작업을 묻지만 변경이나 실행을 명시적으로 지시하지 않았다.
  - **행동**: 요청에 맞는 분석과 보고를 제공하고, 새 개선 아이디어가 필요하면 제안할 수 있다. 질문이나 제안을 구현·파일 수정·환경 변경·외부 쓰기의 승인으로 확대하지 않는다.
- **조건**: 사용자가 진행 중인 작업을 교정한다.
  - **행동**: 교정이 확인된 요구의 미충족을 지적하는지, 실제 원하는 결과나 제외 범위를 바꾸는지 먼저 판정한다. 미충족 지적이면 같은 작업의 실패로 처리하고 계약은 유지한다. 실제 요구 변경이면 대기 중인 변경을 즉시 멈추고 기존 계약을 무효화한다. 새 계약을 세우기 전에는 이전 계획의 어떤 단계도 실행하지 않는다.
- **조건**: 작업 도중 제외 범위 밖의 문제를 발견한다.
  - **행동**: 고치지 않는다. 발견 사실을 보고하고 현재 계약을 계속한다.

## 3. 작업 동일성과 실패 판정

- `작업`은 하나의 사용자 결과를 달성하기 위한 전체 실행 연쇄다. 방법·도구·진단·검증·복구·하위 단계의 변경은 새 작업을 만들지 않는다.
- 실행 결과가 확인된 원하는 결과나 선택된 필수 게이트를 충족하지 못하면 그 실행 연쇄의 한 번의 실패다.
- 사용자가 확인된 요구의 미충족을 지적하면 실패다. 사용자가 원하는 결과·제외 범위·보호 경계처럼 계약을 실질적으로 변경하면 기존 계약의 실패가 아니라 새 계약 경계다.
- 승인 부재나 권한 차단으로 실질 실행을 시작하지 않은 안전 정지는 실패 시도가 아니다.
- 같은 작업의 실패 누적과 중단은 [상시 정책](../PROJECT_RULES.md)의 route를 통해 실패 경험 소유자가 판정한다.

## 4. 예외

- `quick` 등급은 §1의 명시적 확인 없이 진행할 수 있다. 단 제외 범위와 보호 경계는 항상 적용된다.
- 사용자가 명시적으로 위임한 창의적·형식적 선택은 매번 승인을 다시 받지 않는다. 위임은 그 작업에 한정되며 권한 경계를 넓히지 않는다.

## 5. 계약 무효화

다음 중 하나가 발생하면 현재 계약은 무효다.

1. 사용자가 원하는 결과를 바꾼다.
2. 사용자가 제외 범위를 바꾼다.
3. 승인된 보호 경계가 바뀐다.
4. 필요한 결정의 답이 이전 가정과 다르게 확정된다.

무효화된 계약으로 실행을 계속할 수 없다. 무효화 시점 이후의 모든 변경은 새 계약에 근거해야 한다.

## 6. 완료 보고

완료 보고는 최초 요청의 각 조건에 대응해야 한다.

| 보고 항목 | 대응 |
|---|---|
| 무엇을 했는가 | 원하는 결과 |
| 무엇을 하지 않았는가 | 제외 범위 |
| 무엇으로 확인했는가 | 검증 수준과 실제 실행한 검사 |
| 무엇이 미검증인가 | 실행하지 않은 검사 |

실행하지 않은 검사를 통과로 기록하지 않는다. 부분 완료를 완료로 보고하지 않는다.

## 7. 검증

- 완료 결과를 최초 요청의 각 조건과 대조한다.
- 제외 범위의 작업이 계획이나 결과에 포함되었는지 검사한다.
- 계약 무효화 이후의 변경이 새 계약에 근거하는지 확인한다.
- 요구 미충족 교정과 실제 요구 변경이 같은 실패 판정으로 섞이지 않았는지 확인한다.
