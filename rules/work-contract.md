# 작업 계약

- 목적: 에이전트가 무엇을 해야 하고 하지 말아야 하며 무엇으로 완료를 판단할지 작업 내내 명시적으로 유지한다.
- 읽는 시점: 여러 파일을 바꾸거나 둘 이상의 변경·쓰기 행동을 함께 수행하는 작업을 시작할 때, 요청 범위가 모호할 때, 사용자가 진행 중인 작업을 교정할 때.
- 책임: 에이전트가 계약을 유지하고 사용자가 결과와 금지 범위를 소유한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [상시 정책](../PROJECT_RULES.md).

---

## 1. 최소 계약

작업을 시작하기 전에 다음 일곱 항목을 확인한다. 문서로 만들 필요는 없고 `controlled` 작업에서만 명시적으로 기록한다.

| 항목 | 내용 |
|---|---|
| 원하는 결과 | 검증 가능한 표현으로 서술한 최종 상태 |
| 허용 행동 | 이 작업에서 해도 되는 변경의 종류 |
| 제외 범위 | 명시적으로 하지 않을 것 |
| 입력 참조 | 근거로 삼을 정확한 파일과 출처 |
| 보호 경계 | 건드리면 안 되는 경로와 데이터 |
| 필요한 결정 | 사용자만 정할 수 있는 항목 |
| 검증 수준 | 완료 판정에 필요한 최소 증거 |

파일을 생성·갱신하는 작업에서는 입력 참조·보호 경계·검증 수준을 실제 작업 소유 root, 보존 목적지, 승인된 외부 예외와 대조한다. 생성기·하위 명령에 출력 위치를 지정할 수 있으면 명시하며, 목적지를 통제할 수 없는 임시 자원은 상시 정책의 저장 경계로 판정한다. 별도 경로 목록 문서나 매 파일 재승인은 요구하지 않는다.

"개선한다", "정리한다", "좋게 만든다"만으로는 구현의 완료 조건이 충분하지 않다. 먼저 허용된 자료를 조사해 문제와 검증 가능한 결과를 구체화한다. 기존 승인 안에서 되돌릴 수 있는 행동은 합리적인 가정을 밝히고 진행하며, 사용자만 결정할 사항이나 승인 경계를 넘는 변경은 해당 행동 전에 확인한다. 조사·제안 요청에 구현의 완료 조건을 선행 요구하지 않는다.

## 2. 조건과 행동

- **조건**: 요청이 여러 파일을 바꾸거나 둘 이상의 변경·쓰기 행동을 함께 수행한다.
  - **행동**: §1의 일곱 항목을 확인하고, 확인되지 않은 항목이 승인된 결과를 바꾸면 질문한다.
- **조건**: 요청이 모호하다.
  - **행동**: 가장 좁은 해석으로 진행하고 그 해석을 결과와 함께 밝힌다. 해석에 따라 되돌릴 수 없는 결과가 갈리면 질문한다.
- **조건**: 사용자가 가능성·개선안·계획·남은 작업을 묻지만 변경이나 실행을 명시적으로 지시하지 않았다.
  - **행동**: 요청에 맞는 분석과 보고를 제공하고, 새 개선 아이디어가 필요하면 제안할 수 있다. 질문이나 제안을 구현·파일 수정·환경 변경·외부 쓰기의 승인으로 확대하지 않는다.
- **조건**: 사용자가 특정 범위의 개선·수정·적용을 지시했다.
  - **행동**: 실행 요청으로 해석한다. 적용되는 승인 조건을 충족하면 그 범위의 구현과 검증을 진행하고 같은 결정을 반복 확인하지 않는다. 범위 안의 방법 변경은 새 승인을 요구하지 않으며 Core 변경·보호 데이터·외부 효과 등 별도 승인 경계는 유지한다.
- **조건**: 일부 행동에 필요한 승인이나 사용자 결정이 부족하다.
  - **행동**: 그 경계를 넘는 행동과 그 결과에 의존하는 실행만 보류한다. 승인된 독립 조사·분석·검증은 계속하고, 남은 행동 모두가 해당 결정에 의존할 때만 전체 작업을 중단한다.
- **조건**: 사용자가 진행 중인 작업을 교정한다.
  - **행동**: 교정이 확인된 요구의 미충족을 지적하는지, 실제 원하는 결과나 제외 범위를 바꾸는지 먼저 판정한다. 미충족 지적이면 계약을 유지하고, 실제 요구 변경이면 대기 중인 변경을 즉시 멈추고 기존 계약을 무효화한다. 새 계약을 세우기 전에는 이전 계획의 어떤 단계도 실행하지 않는다.
- **조건**: 작업 도중 현재 요청 조건과 이번 변경의 영향에 무관한 문제를 발견한다.
  - **행동**: 현재 작업의 결함과 구분해 보고하고 별도 작업으로 제안한다. 발견 자체를 변경 승인으로 해석하지 않는다.

## 3. 작업 동일성과 결과 판정

- `작업`은 하나의 사용자 결과를 달성하기 위한 전체 실행 연쇄다. 방법·도구·진단·검증·복구·하위 단계의 변경은 새 작업을 만들지 않는다.
- 실행 결과가 확인된 원하는 결과나 선택된 필수 게이트를 충족하지 못하면 작업은 아직 완료되지 않은 상태다.
- 사용자가 확인된 요구의 미충족을 지적하면 기존 계약을 유지한다. 사용자가 원하는 결과·제외 범위·보호 경계처럼 계약을 실질적으로 변경하면 새 계약 경계다.
- 승인 부재나 권한 차단으로 실질 실행을 시작하지 않은 안전 정지는 완료나 결과 미충족 판정이 아니다.
- 결과 시도의 실패 판정, 재시도 제한과 중단은 [상시 정책](../PROJECT_RULES.md)의 route를 통해 실패 처리 소유자만 판정한다.

### 완료 조건 대조

- `standard`와 `controlled` 변경 작업은 구현 전에 현재 계약의 요청 조건·제외 범위·확인된 미충족 원인과 영향받는 표면, 선택된 필수 검증을 대응한다. `controlled`는 이미 필요한 설계에서 이 대응을 명시하고 `standard`는 별도 산출물 없이 내부에서 대조한다. 특정 표 형식이나 추가 문서는 요구하지 않는다.
- 범위 내 요청 조건은 `구현됨` 또는 근거 있는 `not_applicable`로 처분하고 제외 범위는 별도로 대조한다. 검증·감사 항목은 실제 통과 또는 해당 소유자가 허용한 근거 있는 `not_applicable`로만 닫는다. 비해당 항목은 이유를 남기고 필수 게이트 집합에서 제외하며, 남은 선택 필수 게이트가 모두 실제 통과하기 전에는 완료를 주장하지 않는다.
- 영향 표면은 보고된 위치 하나로 자동 축소하지 않고 확인된 원인이 영향을 주는 계약·구조·의미 경계에서 정한다. 완료 검증 전에 범위 내 조건의 처분과 각 필수 게이트의 실행 방법·전제를 대조한다. 범위 내 조건을 제외 범위로 옮기려면 §5의 계약 변경 절차를 따른다.
- 새 근거나 변경이 완료 판단에 영향을 주면 해당 항목과 그에 의존한 증거만 다시 검증한다. 이미 확인한 결과 시도 실패를 없던 것으로 하거나 그 계수를 초기화하지 않는다. 후보·단계 전환·실패 처리는 상위 라우터가 선택한 기존 소유자를 따른다.
- 검토 지적은 위반하는 요청 조건 또는 이번 변경과의 인과관계, 근거, 영향을 대조해 다음과 같이 처분한다.

| 지적 | 완료 판단 |
|---|---|
| 이번 변경으로 발생한 회귀 또는 기존 요청 조건의 미충족 | 현재 완료 근거를 정정하고 영향받는 범위를 해결·재검증한다. 필요한 수정이 승인 경계를 넘으면 차단과 필요한 결정을 보고한다 |
| 현재 요청·변경 영향과 무관한 기존 결함 또는 선택적 개선 | 별도 작업으로 제안하며 현재 완료의 필수 조건에 추가하지 않는다 |
| 적용 전제나 영향이 불명확한 지적 | 판단에 필요한 사실을 확인한다. 필수 보장에 영향을 주는 불확실성이 남으면 완료로 판정하지 않는다 |

선택된 완료 조건을 충족하면 그 범위의 작업을 종료한다. 추가 개선의 존재나 합의한 성공 조건이 아닌 평가 점수만으로 완료를 취소하지 않는다. 재검토 요청은 그 요청 범위에서 수행하고, 기존 완료의 정정 여부는 위 대조로 판단한다.

## 4. 예외

- `quick` 등급은 §1의 명시적 확인 없이 진행할 수 있다. 단 제외 범위와 보호 경계는 항상 적용된다.
- 사용자가 명시적으로 위임한 창의적·형식적 선택은 매번 승인을 다시 받지 않는다. 위임은 그 작업에 한정되며 권한 경계를 넓히지 않는다.

## 5. 계약 무효화

다음 중 하나가 발생하면 현재 계약은 무효다.

1. 사용자가 원하는 결과·허용 행동·성공 조건을 실질적으로 바꾼다.
2. 사용자가 제외 범위를 바꾼다.
3. 승인된 보호 경계가 바뀐다.
4. 필요한 결정의 답이 이전 가정과 다르게 확정된다.

같은 성공 조건을 증명하는 검사 사례·방법의 보강, 진행 상태·검증 근거·표현의 갱신만으로는 계약을 무효화하지 않는다. 필수 보장이나 검증 수준을 줄이는 변경은 방법 보강이 아니다. 검증 확대와 승인 경계는 상위 정책을 따른다.

무효화된 계약으로 실행을 계속할 수 없다. 무효화 시점 이후의 모든 변경은 새 계약에 근거해야 한다.

## 6. 완료 보고

이 규칙이 이미 route된 논리적 작업에서는 완료 보고 전에 계약과 결과를 대조한다. 완료 보고라는 이유만으로 이 규칙을 새로 읽지 않으며, 같은 작업에서 이미 읽은 소유자는 다시 읽지 않는다.

완료 보고는 최초 요청의 각 조건에 대응해야 한다.

| 보고 항목 | 대응 |
|---|---|
| 무엇을 했는가 | 원하는 결과 |
| 무엇을 하지 않았는가 | 제외 범위 |
| 무엇으로 확인했는가 | 검증 수준과 실제 실행한 검사 |
| 무엇이 미검증인가 | 실행하지 않은 검사 |

실행하지 않은 검사를 통과로 기록하지 않는다. 부분 완료를 완료로 보고하지 않는다.

기존 상태를 바꾼 결과는 사용자가 변경을 판단하는 데 필요한 주요 대상의 변경 전·변경 후와 실제 확인 여부, 남은 예외를 함께 보고한다. 이전 값을 확보하지 못했으면 미확인으로 표시하고 추정해 채우지 않는다. 신규 생성은 이전 값 대신 신규임을 표시할 수 있으며, 사용자 판단에 영향을 주지 않는 사소한 내부 변경까지 전후 표로 나열하거나 별도 보고서·고정 형식을 만들 필요는 없다.

## 7. 검증

- 완료 결과를 최초 요청의 각 조건과 대조한다.
- 제외 범위의 작업이 계획이나 결과에 포함되었는지 검사한다.
- 계약 무효화 이후의 변경이 새 계약에 근거하는지 확인한다.
- 요구 미충족 교정과 실제 요구 변경, 내용 갱신만 있는 설계 변경이 구분되는지 확인한다.
- 회귀·요청 미충족·무관한 개선·영향 불명확 지적을 완료 조건과 대조해 처분했는지 확인한다.
