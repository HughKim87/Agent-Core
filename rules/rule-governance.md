# 규칙 거버넌스

- 목적: 시작 문맥을 작게 유지하면서 조건부 규칙이 발견되고 적용되고 검증된 경험으로 개선되게 한다.
- 읽는 시점: 규칙을 추가·변경·통합·감사할 때, 그리고 `controlled` 작업을 종료하기 전.
- 책임: 사용자가 규칙 변경을 승인하고 에이전트가 배치와 라우팅을 유지한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [상시 정책](../POLICY.md)이 상위이며 조건부 라우팅을 소유한다.

---

## 1. 규칙 배치

- 모든 작업에 항상 필요한 경계는 상시 정책에 둔다. 조건부 절차를 시작 정책으로 옮기지 않는다.
- 조건부 행동은 그 trigger가 이미 포함하는 가장 좁은 기존 소유자에 둔다.
- 새 규칙은 trigger가 구별되고 기존 소유자가 책임을 섞지 않고는 표현할 수 없을 때만 만든다.
- 소유자 계층은 재사용 가능한 trigger와 결과로 정한다. 근거를 제공한 경로·보고서·대화로 정하지 않는다.
- 도메인 어휘, 도메인 artifact, 도메인 워크플로 단계에 의존하는 행동은 Core의 규칙이 아니다.
- 하나의 초안이 도메인 중립 절차와 도메인 적용을 섞고 있으면 라우팅 전에 분리한다.
- 승인이 없다는 것은 중단 조건이지 규칙을 다른 계층에 두는 이유가 아니다.
- 대화·보고서·위임 결과를 근거로 쓸 때 발화자와 권위를 분리한다. 에이전트의 제안은 승인 없이 정책이 되지 않는다.

## 2. 규칙의 형태

모든 활성 규칙 파일은 다음을 명시한다.

- `목적`: 이 규칙이 보호하는 지속적 결과
- `읽는 시점`: 이 규칙으로 라우팅되는 관측 가능한 trigger
- `책임`
- `상태`
- `관련 권위`: 상위 정책 또는 결정 소유자

운영 규칙은 조건, 행동, 예외, 검증을 구분할 수 있어야 한다. 역사나 예시만 기록하는 문서는 활성 규칙이 아니다.

하나의 규칙 소유자는 하나의 일관된 trigger와 책임을 갖는다. 추출과 삭제, 정책과 절차, 재사용 가능한 불변식과 작업별 근거를 한 파일에 합치지 않는다.

## 3. 규칙 라우팅

- [상시 정책](../POLICY.md) §4가 이 저장소의 유일한 규칙 라우터다. 병렬 규칙 색인을 만들지 않는다.
- 모든 활성 규칙은 관측 가능한 trigger, 동작하는 링크, 올바른 소유자를 가진 route를 **정확히 하나** 갖는다.
- 규칙 파일끼리 서로를 라우팅하지 않는다. 다른 규칙이 필요하면 상위 라우터를 경유한다.
- 보고서, 후보, 캐시, 역사 문서를 활성 규칙으로 라우팅하지 않는다.
- 규칙이 개명·분할·병합·폐기되면 같은 논리적 체크포인트에서 라우터, 인바운드 링크, 테스트를 함께 갱신한다.
- 여러 규칙이 일치하면 모두 한 번씩 읽고, 충돌은 최신 사용자 지시 → 상위 정책 → 활성 소유자 순으로 해소한다.

## 4. 규칙 읽기

- 상시 정책과 현재 상태를 먼저 읽고, 그다음 현재 행동에 route가 일치하는 규칙만 읽는다.
- 각 규칙은 논리적 작업당 한 번 EOF까지 읽는다. 전체 규칙을 미리 읽지 않는다.
- 규칙 안의 참조는 라우팅 힌트이지 무관한 규칙이나 보호 데이터로 넓힐 권한이 아니다.
- 사용자가 작업을 바꾸거나 교정하면 대기 중인 변경을 멈추고 기존 규칙 선택을 폐기한 뒤 route를 다시 계산한다.
- 체크포인트에는 적용한 규칙 소유자와 검증만 기록한다. 규칙 본문을 보고서에 복사하지 않는다.

## 5. 의도 fixture

새로 만들거나 바꾼 모든 활성 route는 test 전용 의도 fixture 케이스를 갖는다.

| 케이스 종류 | 의미 |
|---|---|
| `initial` | 작업을 시작하는 최초 요청 |
| `colloquial` | 같은 의도의 구어체 표현 |
| `mid-task` | 작업 도중 새 경계가 생기는 전환 |
| `near-miss` | 비슷하지만 이 규칙에 해당하지 않는 요청 |
| `composed` | 둘 이상의 소유자가 함께 일치해야 하는 요청 |

각 케이스는 발화, mid-task의 이전 소유자, 기대 소유자, 금지 소유자, 이유를 기록한다.

fixture는 테스트 근거이며 활성 라우터, 시작 소유자, runtime 의존이 될 수 없다.

## 6. 활성화 조건

route를 활성화하기 전에 두 종류의 검증을 각각 통과한다.

| 검증 | 성격 | 통과 조건 |
|---|---|---|
| 결정론적 fixture 검사 | 기계 | 모든 케이스에서 기대 소유자가 선택되고 금지 소유자가 배제된다 |
| 의미 기반 재현 | 모델 | 새 세션의 대상 에이전트가 키워드가 아니라 행동·경계를 근거로 같은 선택을 한다 |

두 검증은 서로 다른 증거다. 하나를 다른 하나로 대체하지 않는다. 체크포인트에는 런타임, 날짜, 통과·실패 요약만 남기고 재현 대화를 유지 데이터로 보존하지 않는다.

의미 기반 재현이 아직 수행되지 않았으면 route의 증거 수준은 `static-validated`이며 `cross-agent`가 아니다.

## 7. 작업 종료 시 감사

`controlled` 작업을 완료하기 전에 그 작업에 일치했던 각 규칙을 다음으로 분류한다.

1. 빈틈없이 적용됨
2. 기존 소유자를 간결하게 보강해야 함
3. 검증된 재발이 기존 실패 사례에 속함
4. 구별되는 trigger가 새 소유자를 요구함

규칙 변경은 현재 작업이나 검증된 역사의 근거로만 한다. 사용자가 요구하지 않는 한 별도 종료 보고서를 만들지 않는다.

## 8. 검증

- 라우팅 링크가 완전하고 유일하며 존재하는 파일을 가리키는지 확인한다.
- 모든 활성 route에 §2의 형태 항목과 §5의 fixture 적용 범위가 있는지 확인한다.
- fixture가 상위 라우팅 체인을 통해서만 소유자를 참조하고 병렬 라우터가 되지 않았는지 확인한다.
- 고아 규칙과 중복 route가 0인지 확인한다.
