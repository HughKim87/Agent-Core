# 규칙 거버넌스

- 목적: 시작 문맥을 작게 유지하면서 조건부 규칙이 발견되고 적용되고 검증된 경험으로 개선되게 한다.
- 읽는 시점: 규칙을 추가·변경·통합·감사할 때, 그리고 `controlled` 작업을 종료하기 전.
- 책임: 사용자가 규칙 변경을 승인하고 에이전트가 배치와 라우팅을 유지한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [상시 정책](../PROJECT_RULES.md)이 상위이며 조건부 라우팅을 소유한다. [Core 헌장](../docs/CHARTER.md) §7과 [Kernel 범위](../docs/KERNEL_SCOPE.md) §1이 일반화 포함 기준을 소유한다.

---

## 1. 규칙의 목적과 배치

### 기본 원칙

- 규칙의 첫 목적은 반복되는 작업에서 일정한 품질의 결과물을 재현하고, 서로 다른 Agent가 검증된 작업 방법을 공유하게 하는 것이다.
- 규칙은 Agent의 행동을 통제하는 금지 목록보다 작업 순서, 판단 기준, 품질 기준, 확인 방법을 설명한다.
- 도구 선택, 세부 절차, 문제 해결 접근은 결과 품질과 안전 경계를 만족하는 범위에서 Agent가 선택한다.
- 행동 제한은 데이터 손실, 보호 정보 노출, 외부 효과, 비용 발생, 되돌리기 어려운 변경처럼 구체적인 위해를 예방하는 데 꼭 필요한 경우에만 둔다.
- 제한을 둘 때는 예방하는 위해, 발동 조건, 허용되는 대안, 더 약한 방법으로 충분하지 않은 이유를 함께 명시한다.

### 배치 기준

- 모든 작업에 항상 필요한 경계는 상시 정책에 둔다. 조건부 절차를 시작 정책으로 옮기지 않는다.
- 조건부 행동은 그 trigger가 이미 포함하는 가장 좁은 기존 소유자에 둔다.
- 새 규칙은 trigger가 구별되고 기존 소유자가 책임을 섞지 않고는 표현할 수 없을 때만 만든다.
- 소유자 계층은 재사용 가능한 trigger와 결과로 정한다. 근거를 제공한 경로·보고서·대화로 정하지 않는다.
- 도메인 어휘, 도메인 artifact, 도메인 워크플로 단계에 의존하는 행동은 Core의 규칙이 아니다.
- 하나의 초안이 도메인 중립 절차와 도메인 적용을 섞고 있으면 라우팅 전에 분리한다.
- 승인이 없다는 것은 중단 조건이지 규칙을 다른 계층에 두는 이유가 아니다.
- 대화·보고서·위임 결과를 근거로 쓸 때 발화자와 권위를 분리한다. 에이전트의 제안은 승인 없이 정책이 되지 않는다.

## 2. Core 일반화 적합성 게이트

Core 활성 규칙을 새로 만들거나 의미를 추가·수정·흡수하기 전에 변경된 의미 표면이 다음 조건을 모두 통과해야 한다. 사용자 승인, 단일 사건의 심각성, 구현 편의는 일반화 근거를 대신하지 않는다.

1. **Core 보장 기여**: [Core 헌장](../docs/CHARTER.md)의 G1~G6 또는 이미 승인된 Core 계약·역할 불변식 중 무엇을 직접 제공하거나 검증하는지 식별한다. 연결할 보장이 없으면 Consumer가 소유한다.
2. **소비자 독립 표현**: trigger·결과·위해·검증을 특정 프로젝트 이름·경로·도메인 어휘·도메인 artifact 또는 원본 Consumer에만 특정된 외부 도구 없이 Core가 정의한 역할과 공개 계약으로 표현한다. `host`, `maintainer`, `consumer`, `core_path`처럼 Core가 정의한 공통 역할·계약은 프로젝트 특수사항이 아니다. 권위 있는 활성 Core 공개 계약이 명시적으로 승인한 도구만 mechanism owner의 절차·검증에서 사용할 수 있고, 전용 규칙은 그 도구의 배치를 소유할 뿐 승인 근거를 스스로 만들 수 없다. 상위 불변식의 표현은 승인된 도구에도 종속시키지 않는다.
3. **일반화 근거**: 제안이 활성 Core 불변식·공개 계약의 직접적인 귀결이거나, 서로 독립된 둘 이상의 실제 Consumer 맥락에서 같은 trigger와 결과가 확인돼야 한다. 합성 fixture 두 개는 구현 검증이지 복수 Consumer 근거가 아니다. 단일 Consumer 사건은 후보를 제기할 근거일 뿐 Core 일반화의 증거가 아니다.
4. **적용 경계**: 적용되는 조건과 적용되지 않는 near-miss를 함께 제시하고, 근거가 지지하는 범위보다 넓게 표현하지 않는다.
5. **소유권 분리**: 재사용 가능한 불변식·절차·검증만 Core에 두고 원본 프로젝트의 적용 문구·경로·데이터·wrapper 구현·운영 상태는 해당 Consumer에 남긴다.
6. **최소 소유자**: 기존 Core 소유자가 일반화된 의미를 책임 분리 없이 수용할 수 있으면 그 소유자를 보강한다. 새 규칙은 구별되는 trigger와 독립 책임이 있을 때만 만든다.

위 조건을 통과하지 못한 후보는 Core 규칙으로 활성화하지 않는다. Consumer 규칙이나 한시 근거로 남길 정확한 owner를 제시하며, 일부만 일반화 가능하면 Core 공통 부분과 Consumer 적용 부분을 분리한다. 이미 활성인 규칙에서 비일반화 내용을 발견했을 때도 자동 삭제·확대하지 않고 해당 의미 표면을 비활성화·이관할 변경 범위를 사용자에게 제시한다.

`controlled` 규칙 변경의 작업 계약에는 최소한 다음 판단을 명시한다. 별도 보고서 파일을 만들 필요는 없다.

- 일반화한 불변식과 연결된 Core 보장
- 계약 귀결 또는 복수 Consumer라는 근거 유형
- Core에서 제외한 source-specific 요소
- 적용 조건과 near-miss
- 기존 소유자 보강 또는 새 소유자 필요 판정

의미를 바꾼 후보는 현재 작업 문맥을 받지 않은 독립 Agent에게 후보 문구와 위 다섯 판단만 제공해 반례 감사를 수행한다. 독립 감사는 프로젝트 특수사항 잔존, 근거보다 넓은 적용, Consumer 소유 정보의 Core 유입이 모두 없을 때만 `pass`다. 감사하지 못하면 일반화 의미 검증은 `not_run`이며 활성화 완료로 판정하지 않는다. 오탈자·링크·서식만 바꾸고 의미가 그대로인 수정에는 이 독립 감사를 적용하지 않는다.

## 3. 규칙의 형태

모든 활성 규칙 파일은 다음을 명시한다.

- `목적`: 이 규칙이 보호하는 지속적 결과
- `읽는 시점`: 이 규칙으로 라우팅되는 관측 가능한 trigger
- `책임`
- `상태`
- `관련 권위`: 상위 정책 또는 결정 소유자

운영 규칙은 조건, 행동, 예외, 검증을 구분할 수 있어야 한다. 역사나 예시만 기록하는 문서는 활성 규칙이 아니다.

작업 방법을 소유하는 규칙은 가능한 범위에서 다음을 제공한다.

- 반복 작업이 도달해야 할 결과와 품질 기준
- 권장 작업 순서와 상황에 따라 Agent가 판단할 지점
- 결과를 확인할 최소 증거와 필요할 때 검증을 확대하는 기준
- 행동 제한이 있다면 구체적 위해, 좁은 적용 조건, 허용되는 대안

모든 항목을 기계적인 순서로 강제하지 않는다. 특정 순서를 벗어나면 품질이나 안전이 깨지는 경우에만 필수 순서로 선언한다.

하나의 규칙 소유자는 하나의 일관된 trigger와 책임을 갖는다. 추출과 삭제, 정책과 절차, 재사용 가능한 불변식과 작업별 근거를 한 파일에 합치지 않는다.

## 4. 규칙 라우팅

- [상시 정책](../PROJECT_RULES.md) §4가 이 저장소의 유일한 규칙 라우터다. 병렬 규칙 색인을 만들지 않는다.
- 모든 활성 규칙은 관측 가능한 trigger, 동작하는 링크, 올바른 소유자를 가진 route를 **정확히 하나** 갖는다.
- 규칙 파일끼리 서로를 라우팅하지 않는다. 다른 규칙이 필요하면 상위 라우터를 경유한다.
- 보고서, 후보, 캐시, 역사 문서를 활성 규칙으로 라우팅하지 않는다.
- 규칙이 개명·분할·병합·폐기되면 같은 논리적 체크포인트에서 라우터, 인바운드 링크, 테스트를 함께 갱신한다.
- 여러 규칙이 일치하면 모두 한 번씩 읽고, 충돌은 최신 사용자 지시 → 상위 정책 → 활성 소유자 순으로 해소한다.
- 명시적 키워드는 안정적인 호출 별칭으로 사용할 수 있지만 유일한 trigger가 아니다. 같은 작업 의도는 표현이 달라도 동일한 정본으로 route되어야 한다.
- `AGENTS.md`, `CLAUDE.md`와 다른 Agent 진입점은 규칙 본문을 복제하지 않고 같은 상위 정책과 route 정본을 가리킨다.

## 5. 규칙 읽기

- Core 정책, 소비 정책, 소비 상태를 먼저 읽고, 그다음 현재 행동에 route가 일치하는 Core·소비 규칙만 읽는다.
- 각 규칙은 논리적 작업당 한 번 EOF까지 읽는다. 전체 규칙을 미리 읽지 않는다.
- 규칙 안의 참조는 라우팅 힌트이지 무관한 규칙이나 보호 데이터로 넓힐 권한이 아니다.
- 사용자가 작업을 바꾸거나 교정하면 다음 실질 행동의 route를 다시 계산하되 같은 논리적 작업에서 이미 읽은 소유자의 이력은 유지한다. 새로 일치한 소유자만 끝까지 읽는다. 교정이 기존 요구의 미충족이면 기존 계약·진행·승인은 유지하고, 실제 목표·권한·보호 경계·필수 성공 조건 변화의 중단과 재확정은 작업 계약 소유자가 판정한다. 새 위험이 확인된 행동은 해당 승인·보호 경계에서 멈추며 이를 전체 읽기 이력 초기화로 확대하지 않는다.
- 체크포인트에는 적용한 규칙 소유자와 검증만 기록한다. 규칙 본문을 보고서에 복사하지 않는다.

## 6. 의도 fixture

새로 만들거나 바꾼 모든 활성 route는 test 전용 의도 fixture 케이스를 갖는다.

| 케이스 종류 | 의미 |
|---|---|
| `initial` | 작업을 시작하는 최초 요청 |
| `colloquial` | 같은 의도의 구어체 표현 |
| `mid-task` | 작업 도중 새 경계가 생기는 전환 |
| `near-miss` | 비슷하지만 이 규칙에 해당하지 않는 요청 |
| `composed` | 둘 이상의 소유자가 함께 일치해야 하는 요청 |

각 케이스는 발화, mid-task의 이전 소유자, 기대 소유자, 금지 소유자, 이유를 기록한다. 기대 소유자는 발화에 적용되는 소유자 중 `prior_owners`에서 이미 읽은 것을 뺀 **이번 전환의 새 최소 집합**이며, 의미 재현의 선택 집합은 기대 집합과 정확히 같아야 한다. 금지 소유자는 near-miss의 의도를 명시하고 실패 원인을 좁히는 진단 필드다.

fixture는 테스트 근거이며 활성 라우터, 시작 소유자, runtime 의존이 될 수 없다.

## 7. 활성화 조건

route를 활성화하기 전에 두 종류의 검증을 각각 통과한다.

| 검증 | 성격 | 통과 조건 |
|---|---|---|
| route·fixture 구조 검사 | 기계 | route 링크·유일성, 규칙 형태, fixture schema·참조·종류가 유효하다 |
| 의미 기반 재현 | 모델 | 새 세션의 대상 에이전트가 키워드가 아니라 행동·경계를 근거로 이번 전환에서 새로 읽을 기대 소유자의 정확 집합만 선택한다 |

기계 검사는 발화의 의미나 소유자 선택의 정확성을 판정하지 않는다. 두 검증은 서로 다른 증거이며 하나를 다른 하나로 대체하지 않는다.

독립 Agent 의미 재현은 다음 순서로 수행한다.

1. 현재 작업 대화를 전달하지 않은 새 세션을 열고, 대상 Runtime과 날짜를 고정한다.
2. 각 케이스에서 `utterance`와 `prior_owners`만 제시하고, Agent에게 이미 읽은 소유자를 제외해 이번 전환에서 새로 읽을 소유자만 선택하게 한다. `expected_owners`, `forbidden_owners`, `reason`은 응답이 끝날 때까지 공개하지 않는다.
3. Agent가 선택한 소유자와 행동·경계 근거를 받은 뒤 선택 집합이 기대 집합과 정확히 같은지 비교하고 금지 소유자 선택 여부를 별도 진단한다.
4. 모든 케이스가 조건을 만족해야 통과한다. 실패 후 trigger를 바꿨다면 같은 세션을 재사용하지 않고 새로운 콜드 세션에서 전체 세트를 다시 실행한다.
5. 체크포인트에는 Runtime, 날짜, 전체 케이스 수, 실패 ID, 실패 원인 요약만 남긴다. transcript는 유지 데이터로 보존하지 않는다.

의미 기반 재현이 아직 수행되지 않았으면 route의 증거 수준은 `static-validated`이며 `cross-agent`가 아니다.

## 8. 작업 종료 시 감사

`controlled` 작업의 종료 감사는 현재 계약의 산출물과 완료 근거가 적용 규칙을 준수하는지 확인한다. 적용 규칙 전체의 개선 가능성을 소진하는 것을 완료 조건으로 삼지 않는다.

지적은 위반하는 조건·보장, 반례 또는 근거, 영향에 연결한다. 같은 원인의 중복 지적은 통합하고, 현재 결함·무관한 개선·전제 불확실성의 처분과 재검증 범위는 상위 라우터가 선택한 작업 계약 소유자의 완료 조건 대조를 따른다. 규칙 보강 제안 자체가 현재 작업의 범위나 승인·성공 조건을 바꾸지는 않는다.

규칙 자체의 감사·변경이 요청 범위이거나 현재 요구를 충족하려면 규칙 변경이 필요한 경우에 그 의미 표면을 검토한다. 기존 소유자가 요구를 충족할 수 없을 때만 새 소유자를 제안한다. 구현에만 특정된 결함은 상위 라우터가 선택한 실패 처리 소유자의 처분을 따른다.

Core 규칙의 의미를 추가·변경·흡수했다면 §2의 일반화 판단과 독립 반례 감사를 확인한다. 변경의 의미 영향을 받지 않는 규칙까지 이 게이트의 대상으로 확장하지 않는다. 감사 대상의 행동 제한은 §1의 구체적 위해·허용 대안·최소 제한 근거로 검토한다.

규칙 변경은 현재 작업이나 검증된 역사의 근거와 승인 범위 안에서만 한다. 사용자가 요구하지 않는 한 별도 종료 보고서를 만들지 않는다.

## 9. 검증

- 라우팅 링크가 완전하고 유일하며 존재하는 파일을 가리키는지 확인한다.
- 모든 활성 route에 §3의 형태 항목과 §6의 fixture 적용 범위가 있는지 구조 검사로 확인한다.
- fixture가 상위 라우팅 체인을 통해서만 소유자를 참조하고 병렬 라우터가 되지 않았는지 확인한다.
- 고아 규칙과 중복 route가 0인지 확인한다.
- route 의미 정확성은 §7의 독립 Agent 절차 결과로만 판정한다.
- 명시적 키워드와 의미가 같은 구어체 요청이 동일한 정본으로 route되는지 확인한다.
- 새 행동 제한마다 구체적 위해, 발동 조건, 허용 대안, 최소 제한 근거가 있는지 확인한다.
- Core 규칙 의미 변경마다 G1~G6 또는 활성 계약과의 연결, 일반화 근거, source-specific 제외 요소, 적용 조건·near-miss, 최소 소유자 판정이 있는지 확인한다.
- 독립 반례 감사가 프로젝트 특수사항·과잉 적용·Consumer 정보 유입을 모두 검사했고 `pass`인지 확인한다. 기계 구조 검사나 사용자 승인으로 이 의미 검증을 대체하지 않는다.
