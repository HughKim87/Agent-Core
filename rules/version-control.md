# 버전 관리

- 목적: Git 쓰기와 복구의 경계를 정하고 완료 이력이 실제로 복구 가능하게 유지한다.
- 읽는 시점: 스테이지, 커밋, 브랜치, push, 복구, 백업을 하기 전.
- 책임: 에이전트가 커밋 단위를 유지하고 사용자가 push와 원격 조작을 승인한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [상시 정책](../PROJECT_RULES.md) §6이 승인 경계를 소유한다.

---

## 1. 커밋 단위

- 하나의 커밋은 하나의 논리적 완료를 담는다.
- 여러 단계의 산출물을 한 커밋에 섞지 않는다. 어느 단계가 어떤 근거로 통과했는지 추적할 수 없게 된다.
- 커밋 메시지는 무엇을 왜 바꿨고 어떤 게이트를 어떻게 통과했는지를 담는다. 이것이 완료 이력의 정본이다.
- 실행하지 않은 검증을 커밋 메시지에 통과로 적지 않는다.
- 단계 후보 커밋은 실제 commit snapshot의 경로와 선택된 검증 증거가 작업 트리의 완료 주장과 일치해야 한다. clean clone은 릴리스·재현성·패키징·submodule 도달성 확인이 필요한 후보에서 사용한다.

## 2. 스테이지 범위

- 변경한 정확한 경로만 스테이지한다. 전체 스테이지 명령으로 무관한 변경을 함께 넣지 않는다.
- 현재 작업과 무관한 사용자의 미커밋 변경을 스테이지하지 않는다.
- 보호 데이터는 어떤 경우에도 스테이지하지 않는다.

## 3. 조건과 행동

- **조건**: 사용자가 커밋을 지시하거나 위임했다.
  - **행동**: 논리적 완료마다 커밋한다. 위임은 push를 포함하지 않는다.
- **조건**: 커밋 지시나 위임이 없다.
  - **행동**: 커밋하지 않는다. 변경만 남기고 보고한다.
- **조건**: push, 태그 게시, 원격 브랜치 조작이 필요하다.
  - **행동**: 항상 사용자 승인을 먼저 받는다. 위임된 작업에서도 예외가 아니다.
- **조건**: 되돌려야 할 상태가 생겼다.
  - **행동**: 커밋 이력에서 마지막 검증된 상태를 찾아 복구한다. 저장소 안에 백업 사본을 만들지 않는다.
- **조건**: 단계 후보 커밋을 만들었다.
  - **행동**: `git show`와 상태 대조로 실제 snapshot의 경로를 확인하고, 단계가 선택한 관련 검증을 snapshot 기준으로 확인한다. clean clone이 선택된 후보는 임시 clone에서 필요한 route·링크·테스트·통합 게이트만 실행한다.
- **조건**: 선택된 후보 commit snapshot 검증이 실패했다.
  - **행동**: 다음 단계로 진행하지 않고 누락된 파일·선언·상태를 교정한다. 실패한 후보를 통과 이력으로 설명하지 않는다.

### Git 쓰기의 대상과 증거

Git 쓰기를 준비할 때는 해당 작업의 실제 저장소와 작업 맥락, 의도한 결과와 보존할 상태를 승인 범위와 대조한다. 원격 ref를 생성·갱신·삭제하면 endpoint, 완전한 대상 ref와 의도한 사후 상태를 식별하고, 원본 객체를 사용하는 작업은 그 객체도 함께 식별한다. 부모 저장소와 submodule, fetch용 목적지와 push용 목적지, 로컬 ref와 원격 ref를 같은 대상으로 추정하지 않는다. 필요한 값이 모호하면 먼저 읽기 전용으로 확인한다.

원본 객체를 사용하는 원격 쓰기는 그 원본이 실행 중 다른 값으로 해석되지 않도록 객체 ID로 고정한다. 작업에서 포함하기로 한 로컬 이력이 있다면 그 원본에 포함되는지 확인한다. 필요한 객체와 참조는 해당 저장소의 실제 조회 조건에서 사용할 수 있는지 확인한다. 누락·훼손·다른 저장소 의존성을 발견하면 기존 작업을 바꾸거나 임의의 다른 원본을 게시하지 않는다. 필요한 복구·의존성 처리의 범위와 승인부터 확인한다. 원격 ref 삭제는 게시할 원본 객체를 요구하지 않고 승인된 대상과 삭제 조건·의도한 ref 부재를 대조한다.

실행 방법과 실효 설정이 선택하는 ref·endpoint 및 알려진 클라이언트 측 추가 쓰기를 승인된 집합과 대조한다. 암묵적인 추가 태그, 재귀 게시, client hook이나 간접 참조 때문에 결과가 달라질 수 있으면 해당 효과를 확인·통제할 수 있는 방법을 선택한다. 안전하게 포함하거나 배제할 수 없는 효과는 정상 경로로 간주하지 않는다.

확인 이후의 대상 변경은 그 대상과 조건에 맞는 실행 시점 보호로 처리한다. 예상된 기존 값만 비교하는 수단을 대상의 동일성·ref 종류·서버 내부의 모든 쓰기까지 보장하는 수단으로 확대하지 않는다. 선택한 보호가 필요한 조건을 충족하지 못하면 쓰기를 시작하지 않고 확인 가능한 다른 방법이나 필요한 결정을 제시한다.

실행 후에는 요청별 결과와 실제 관측한 대상 상태를 의도한 결과와 대조하고, 작업이 영향을 줄 수 있는 로컬 상태의 보존 여부를 확인한다. 성공 응답만으로 원격 쓰기 완료를 선언하지 않으며 성공 여부가 불명확하면 상태를 먼저 확인하고 재시도한다. 서버 내부 hook의 독립적인 쓰기·중간 동작·영속 보관까지 증명해야 하는 요청은 endpoint의 확인 가능한 계약이나 감사 증거 등 별도 근거가 있어야 한다.

단순 읽기 전용 진단에는 게시 승인을 요구하지 않으며, 원격 ref 쓰기를 수반하지 않는 로컬 작업에는 endpoint·원격 사후 조회 요건을 적용하지 않는다. 추가 효과나 특별한 저장 구성이 있다는 이유만으로 모든 작업을 금지하거나 전체 이력 복제를 요구하지 않는다. 필요한 증거와 안전한 방법을 작업에 맞게 정하되 근거 없는 가정으로 쓰기 범위를 넓히거나 완료 수준을 높이지 않는다.

## 4. 백업

저장소 로컬 백업 스냅샷과 역사 보고서 사본을 만들지 않는다. 완료 이력과 복구는 Git이 소유한다.

전체 사본을 추가하기 전에 Git 이력만으로 복구 가능한지 먼저 확인한다.

## 5. 예외

- 사용자가 명시적으로 요청한 백업은 만들 수 있다. 위치와 보존 기간을 함께 정한다.
- 되돌릴 수 없는 이력 조작은 사용자 승인 없이 하지 않는다.

## 6. 검증

- 커밋된 경로가 의도한 범위와 일치하는지 대조한다.
- 보호 데이터가 스테이지되지 않았는지 확인한다.
- 커밋 메시지의 검증 주장이 실제 실행 결과와 일치하는지 확인한다.
- `git show`로 후보 snapshot의 경로를 확인하고, 완료 주장에 선택된 snapshot 검증 결과가 실제 실행 증거와 일치하는지 확인한다.
