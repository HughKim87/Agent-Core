# 버전 관리

- 목적: Git 쓰기와 복구의 경계를 정하고 완료 이력이 실제로 복구 가능하게 유지한다.
- 읽는 시점: Git 저장소임이 확인된 변경 작업을 시작하거나 체크포인트·완료를 판단할 때, 또는 스테이지·커밋·브랜치·push·복구·백업을 하기 전.
- 책임: 에이전트가 커밋 단위를 유지하고 사용자가 push와 원격 조작을 승인한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [상시 정책](../PROJECT_RULES.md) §6이 승인 경계를 소유한다.

---

## 1. 커밋 단위와 저장 시점

승인된 Git 변경에는 이번 변경의 로컬 stage·commit이 위임된다. stage만으로는 복구 지점이 생기지 않는다. 로컬 커밋만으로 디스크 손실 대비나 portable 전달을 보장할 수 없다.

| 시점 | 커밋과 증거 |
|---|---|
| 큰 수정·실험 직전, 재개·비교 가치가 있는 중간 결과, 단계 전환·중단·인계 직전 | 미기록 변경을 보존한다. 중간 커밋은 `checkpoint`를 표시하고 목적·남은 일·실패 또는 미실행 등 실제 검증 상태를 적는다. 이후 필수 게이트는 유지한다 |
| 관련 검증을 통과한 논리적 완료, 전체 종료 직전 | 변경 이유·실제 통과한 검증과 방법·한계를 기록한다. 종료 전 최종 산출물·필요 상태·요구된 보고서까지 대조한다 |

이번 변경이 없으면 빈·중복 커밋을 만들지 않는다. 파일·명령·시간·단계 번호 대신 함께 설명·검증·복구할 수 있는 변경을 묶는다. 여러 단계가 함께 반영되어야 유효하면 한 커밋에 담고 각 성공 조건과 증거를 추적할 수 있게 한다.

## 2. 스테이지 범위

시작할 때 worktree와 index의 기존 변경을 확인한다. 이번 변경의 정확한 경로와 안전하게 분리 가능한 부분만 담고, 보호 데이터는 스테이지하지 않는다. 무관한 미커밋·staged 변경을 커밋하거나 해제·폐기하지 않는다. 안전하게 분리할 수 없으면 해당 커밋만 보류하고 범위·이유·해소 방법을 식별한다. 분리 가능한 변경은 기록한다. 다음 보존 시점에 보류 이유를 재평가하고 기존 변경까지 포함해야 하면 추가 위임을 확인한다.

## 3. 조건과 행동

- **로컬 보존**은 §1을 따른다. 명시적 커밋 금지·보류, 저장소·범위 불명확, 변경 분리 불가, 실행기 차단이면 해당 커밋과 snapshot·portable·gitlink 재현성에 의존한 완료만 보류한다. 미커밋 범위·이유와 동일 workspace 의존을 알리고 독립 작업을 계속한다. 저장소 생성이나 권한·기존 index 변경으로 우회하지 않는다.
- **실행기 차단**은 실제 실패한 저장소·행동·오류로 판단한다. 기존 위임 안의 정확한 작업에는 실행기의 정식 승인 경로를 사용한다. 기본 실행 실패나 submodule 조회 오류만으로 부모 커밋 불가를 단정하지 않는다. 정식 경로 미시도·실제 실패·승인 심사 거절을 구분한다.
- **후보 커밋**은 `git show`와 상태 대조로 실제 snapshot 경로와 남은 변경을 확인한다. 완료의 관련 검증은 snapshot을 기준으로 하고 체크포인트는 실제 상태를 기록한다. 릴리스·재현성·패키징·submodule 도달성 확인에 clean clone이 필요할 때 임시 clone에서 필요한 route·링크·테스트·통합 게이트만 실행한다. 후보 검증 실패 시 의존한 완료·전환을 보류하고 누락된 파일·선언·상태를 교정한다.
- **복구**할 때는 Git 이력에서 마지막 검증된 커밋을 찾는다. **원격 쓰기**(push·태그 게시·원격 브랜치 조작)는 같은 대상·목적·범위에 대한 사용자 승인이 필요하다. 같은 범위의 명시적 지시는 승인으로 인정한다.

### Git 쓰기의 대상과 증거

1. 실제 저장소·작업 맥락, 의도한 결과와 보존할 상태를 승인 범위와 대조한다. 원격 ref 생성·갱신·삭제는 endpoint, 완전한 대상 ref, 의도한 사후 상태를 특정한다. 부모/submodule, fetch/push 목적지, 로컬/원격 ref가 같다고 가정하지 말고 모호하면 읽기 전용으로 확인한다.
2. 원본을 게시하면 객체 ID로 고정하고 합의한 로컬 이력이 포함되는지, 필요한 객체·참조가 해당 저장소의 실제 조회 조건에서 사용 가능한지 확인한다. 누락·훼손·타 저장소 의존이 발견되면 기존 작업을 바꾸거나 임의의 다른 원본을 게시하지 않는다. 필요한 복구·의존성 처리의 범위와 승인을 먼저 확인한다. 삭제에는 원본 객체가 필요 없으며 승인된 대상·삭제 조건·사후 ref 부재를 대조한다.
3. 실행 방법·실효 설정이 선택하는 ref와 endpoint, 암묵적 태그·재귀 게시·client hook·간접 참조의 추가 쓰기를 승인 집합과 대조한다. 발생 가능한 효과는 통제 가능한 방법을 택한다. 대상 변경은 실행 시점에 해당 조건을 보호한다. 예상 기존 값 일치는 대상 동일성·ref 종류·서버 내부의 모든 쓰기를 보장하지 않는다. 필요한 통제가 안 되면 쓰기 전에 안전한 대안이나 필요한 결정을 제시한다.
4. 실행 후 요청별 응답, 실제 대상 상태와 영향받을 수 있는 로컬 상태의 보존을 확인한다. 성공 응답만으로 원격 완료를 선언하지 않고 불명확하면 재시도 전에 상태부터 조회한다. 서버 hook의 독립 쓰기·중간 동작·영속 보관을 증명해야 하면 endpoint의 계약이나 감사 증거가 필요하다.

읽기 진단은 게시 승인이 필요 없고 로컬 작업은 원격 endpoint·사후 조회를 요구하지 않는다. 별도 저장 구성이나 추가 효과가 있어도 일괄 중단·전체 이력 복제를 요구하지 않는다. 작업에 필요한 증거와 통제 가능한 방법을 정한다.

## 4. 백업과 검증 근거

복구 지점과 완료 이력의 정본은 Git이다. 전체 사본 추가 전 이력으로 복구 가능한지 확인하고, Git을 대신할 저장소 내 백업·중복 이력 보고서를 만들지 않는다. 요구된 단계 최종보고서는 결과·검증·남은 일을 요약하고 이력을 참조한다. Consumer는 검증 대상·결과·재개 조건을 찾을 최소 근거만 보존할 수 있다. 검증한 revision·hash는 관측 당시 snapshot을 식별한다. 현재 배포 revision의 별도 정본이나 정책·이력 복제의 근거로 쓰지 않는다.

## 5. 예외

사용자가 명시적으로 요청한 백업은 위치와 보존 기간을 정해 만든다. 되돌릴 수 없는 이력 조작에는 사용자 승인이 필요하다.

## 6. 검증

종료 전 이번 위임 변경의 경로·보호 경계, 실제 commit snapshot, 메시지의 검증 주장과 실행 근거를 대조한다. 논리적 완료의 성공 조건별 증거와 미완성 체크포인트를 구분한다. 구현·문서 상태와 로컬 보존 상태를 각각 보고하고 미커밋이 남으면 관련 커밋·검증, 남은 정확한 범위·이유·해소 방법을 식별한다. 별도 보고서나 저장소 전체 clean은 요구하지 않는다.
