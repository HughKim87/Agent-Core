# Core 변경 통제

- 목적: 선언된 Core를 기본 불변 영역으로 유지하고 Maintainer에서 승인된 최소 변경만 검증해 수용한다.
- 읽는 시점: 소비 계약의 `core_path`를 생성·수정·삭제·이동·개명·재생성하거나 간접 변경하기 전.
- 책임: 사용자가 변경 범위를 승인하고 Maintainer가 최소 변경과 검증을 수행한다.
- 상태: 활성 규칙. L2 작업 계약 계층.
- 관련 권위: [Core 상시 정책](../PROJECT_RULES.md) §8, 소비 저장소의 `agent-core-consumer:v1` 선언.

---

## 1. 적용 대상

구성된 소비 저장소에서는 소비 계약의 `core_path` 전체가 Core다. Core 자체 검증에서는 전달된 `--core-root`가 Core다.

Core 경로는 특정 디렉터리 이름으로 추측하지 않는다. 선언과 CLI 입력을 대조해 결정한다.

## 2. 역할별 기본값

| 역할 | Core 읽기·공개 검사 | Core 수정 | Core push |
|---|---:|---:|---:|
| `host` | 허용 | 금지. Maintainer 작업으로 이관 | 원격 read-only 권한으로 거부돼야 함 |
| `maintainer` | 허용 | 정확한 현재 승인 뒤 허용 | 별도 사용자 승인과 쓰기 권한 필요 |

프롬프트는 권한 경계가 아니다. Host push 거부는 실제 Deploy Key 권한으로 검증한다.

## 3. Core 변경의 정의

- 파일 생성·수정·삭제·이동·개명
- 파생 artifact 재생성
- 의존성·설정·도구 체인 변경으로 생기는 간접 변경
- submodule 안에서 새 commit을 만드는 행동

읽기, 승인된 공개 인터페이스 실행, 부모 저장소의 검증된 gitlink 갱신은 Core 파일 변경이 아니다.

## 4. Maintainer 승인 조건

Core 변경은 다음이 모두 충족될 때만 시작한다.

1. 소비 역할이 `maintainer`다.
2. 정확한 이유가 확인됐다.
3. 정확한 대상 경로가 확인됐다.
4. 현재 대화에서 사용자가 그 범위를 승인했다.

과거 승인, 상시 목표, 활성 계획, 추론된 이득은 새 Core 변경 승인이 아니다. 사용자가 다단계 전체를 명시적으로 위임한 경우에도 그 범위를 벗어날 수 없다.

## 5. 조건과 행동

- `host`에서 변경 필요성을 발견하면 Core를 고치지 않고 정확한 근거와 diff 대상을 Maintainer로 이관한다.
- 승인된 Maintainer 변경은 최소 범위만 수행한다.
- 승인 범위를 벗어나는 파일이 필요하면 구현을 멈추고 새 승인을 받는다.
- 무인·예약 작업은 Core 변경을 추론하거나 승인을 대기하지 않고 비성공으로 종료한다.

## 6. 변경 후 검증

- 실제 Git 변경 경로를 승인 목록과 대조한다.
- Core 자체 gate를 실행한다.
- 소비 계약에 영향을 주면 소비 통합 gate도 실행한다.
- 로컬 후보 commit을 clean clone해 동일 게이트를 다시 실행한다.
- 실행하지 않은 필수 검사는 통과로 기록하지 않는다.
- push는 정확한 후보 commit을 사용자가 확인하고 별도로 승인한 뒤에만 수행한다.

## 7. 검증 시나리오

- Host Core 수정 시도 정지
- Maintainer 무승인 수정 정지
- 승인 범위 밖 파일 탐지
- 승인된 최소 수정과 gate 통과
- Host read-only key의 fetch 성공·push 거부
- gate 전후 Core tree 무부작용
