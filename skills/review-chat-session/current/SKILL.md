# 채팅 세션 분석

- 목적: 원래 대화가 없는 Maintainer도 문제 상황과 근거를 검토할 수 있게 전달한다.
- 적용 범위: Core와 프로젝트별 Extension이 없는 환경의 현재 채팅. 프로젝트 자체가 없어도 사용할 수 있다. CORE/EXTENSION은 개선을 검토할 영역의 분류이며 실제 설치나 반영 경로가 존재한다는 뜻이 아니다.
- 책임: 분석 에이전트는 CORE/EXTENSION 잠정 분류·적합도·필수 여부를 평가하고 관측된 문제·근거·영향·개선이 필요한 이유를 정리한다. 구체적인 개선안·해결 방법·작업 순서와 최신 Core와의 관계, 반영 여부·위치·우선순위·검증 설계·최종 결론은 Maintainer가 판단한다.
- 상태: PC 개인용 공통 스킬. Core 설치 없이 실행하며 프로젝트와 Git도 선택이다.
- 관련 권위: 현재 사용자 요청과 해당 도구의 접근·보존 권한. 보고서는 활성 정책이나 변경 승인이 아니다.

## 출력 계약

다른 분야에서도 검토할 가치가 있는 관측 사항이 있고 실제 근거로 뒷받침될 때만 Markdown 인계 보고서를 저장한다. Core를 모르더라도 문제 상황을 전달할 수 있다. 이 문턱은 보고 자료의 보존 여부에 대한 판단이며, Core 변경이 필요하다는 판정이 아니다.

- 일회성 취향, 해당 프로젝트에만 적용되는 요구, 이미 해결돼 재사용할 관측 가치가 없는 사항, 근거가 부족한 추측뿐이면 파일을 만들지 않는다. 분석 범위와 미생성 이유를 채팅에 짧게 알린다.
- 이미 해결된 사례도 다른 작업에서 살펴볼 가치가 있는 문제가 관측됐다면 당시 문제와 실제 해결 경과를 사실로 기록할 수 있다. 그 해결 방식을 Core의 권장 방법으로 바꾸지 않는다.
- 문제가 없는 성공 사례에서 억지로 결함을 만들거나 일반적인 지침을 반복하기 위해 보고서를 만들지 않는다.
- 사용자가 채팅 보고만 요청하거나 파일 생성을 금지하면 그 지시를 우선한다. 빈 보고서는 만들지 않는다.

파일 생성 여부와 채팅의 보고 범위는 구분한다. 프로젝트 전용의 재사용 가능한 관측은 EXTENSION으로, 근거가 부족한 항목은 근거 부족으로 나누어 채팅 표에 보고한다. 특정 외형·수치 같은 일회성 요구 자체를 개선 항목으로 만들지는 않는다.

저장할 때는 다음을 따른다.

- 프로젝트가 있으면 기존 보존 정책을 따르고 프로젝트 내부를 기본 위치로 삼는다. 외부 보존은 사용자가 지정하거나 이미 승인한 대상·목적·범위에서만 허용한다. 쓰기 가능한 경로라는 사실만으로 외부 보존이 승인되지는 않는다.
- 프로젝트가 없으면 사용자 지정 또는 현재 확인된 작업 폴더를 사용한다. 저장소나 임의 작업 root를 새로 만들지 않는다. 안전한 저장 위치가 없으면 채팅 보고를 완성하고 미생성 이유를 밝힌다.
- 설명 가능한 Markdown 파일명을 사용하고 기존 파일을 덮어쓰지 않는다. 이름이 충돌하면 날짜·시간 등 최소 식별자를 덧붙인다.
- 저장 후 실제 경로의 존재와 읽기 가능 여부를 확인한다. 채팅에도 관측 사항을 요약하고, 생성 이유와 클릭 가능한 파일 링크를 제공한다.

파일이라는 이유로 상세도를 늘리지 않는다. 판단에 필요한 최소 내용만 남긴다.

## 분석 범위

분석을 시작할 때 해당 세션의 전체 기록을 처음부터 마지막까지 다시 읽는다. 현재 문맥·기억·요약·핸드오프·최근 답변만으로 이를 대신하지 않는다. 같은 채팅의 기록 조회 도구를 사용하고 다음 페이지가 있으면 조회 종료까지 이어 읽는다. 최신순으로 조회되면 전 구간을 확보한 뒤 시간순으로 검토한다. 잘린 메시지는 원문을 추가 조회하고 요약만 제공된 구간은 원문을 확보한다. 사용자가 제공한 기록이나 환경의 기록 adapter가 분석 원본이면 같은 기준으로 끝까지 읽는다.

긴 기록은 조회 결과를 보관할 수 있으면 보관하고, 페이지 상태·항목 식별자·종류·길이·잘림 표시로 읽을 범위를 파악한 뒤 원문을 순서대로 나눠 읽는 방법을 권장한다. 목록·길이 확인은 본문 재독을 대신하지 않는다. 원 응답은 완전하지만 모델 전달 중 잘렸다면 보관한 결과를 나눠 읽고, 원 응답부터 잘렸다면 제공되는 추가 조회 경로를 사용하거나 해당 구간을 미확보로 표시한다. 도구가 알려준 인자 한도는 같은 작업의 후속 호출에 반영하되 특정 수치를 공통 상한으로 고정하지 않는다. 짧고 완전한 기록에는 별도 목록 작성·보관·분할을 추가하지 않아도 된다.

조회 종료·접근 구간·원문 누락·요약 여부를 확인해 보고 첫머리에 전체 재독 완료 또는 부분 검토를 명시한다. 원문을 확보하지 못하면 읽을 수 있는 나머지 구간은 계속 검토하고 누락 구간·원인·판단 한계를 밝힌다. 조회할 수 있는 원문을 남긴 채 요약만으로 전체 재독을 마쳤다고 하지 않는다. 기록을 확보하려고 다른 채팅·보호 경계를 넘거나 없는 내용을 추정하지 않는다.

대화 원문 전체 재독 여부와 과거 실행 결과의 검증 여부는 구분한다. 메시지 원문을 모두 읽었어도 과거 검사 로그가 없으면 실행 결과만 미검증으로 표시하며, 그 이유만으로 대화 원문이 누락됐다고 추정하지 않는다.

현재 호출된 채팅과 사용자가 이번 분석에 제공한 자료만 사용한다. 별도 채팅을 검색하거나 전체 대화 기록·PC 파일을 수집하지 않는다. 대상 프로젝트가 있으면 사용자에게 지정되었거나 현재 문맥에서 확인된 root와 이미 존재하는 진입·정책을 좁게 읽고 그 승인·보호·보존 경계를 따른다. 프로젝트 전체를 자동 색인하지 않는다. root가 불명확해도 제공된 대화 분석은 진행하고 파일 쓰기만 보류한다. 프로젝트 구현·운영 절차는 이 분석 스킬로 대신하지 않는다. 프로젝트를 만들거나 세션을 옮길 필요는 없다.

접근한 대화 구간, 요약·압축 여부, 실행 결과 유무를 밝힌다. 기록이 부족하면 그 범위만 분석하며 기억이나 에이전트의 자기보고를 실제 실행 근거로 바꾸지 않는다. 사용자 교정과 에이전트 제안도 구분한다. 비밀·인증 정보·불필요한 개인정보와 전체 transcript를 보고서에 복제하지 않는다.

## 관측 사항 선별

1. 목표·기대 결과·실제 결과·사용자 교정·영향을 연결한다. 실제 해결이나 재검증이 있었다면 그 경과와 확인 범위도 기록한다. 같은 원인의 반복 지적은 합치며, 같은 채팅의 반복을 독립된 여러 사용 맥락으로 세지 않는다.
2. 관측 사실, 원인에 대한 추론, 미확인 사항을 구별한다. 사용자의 명시적 요구와 에이전트가 제안한 내용을 혼동하지 않는다. 실행 결과는 확인한 증거 범위에서만 설명한다.
3. 상품명·직무명·프로젝트명을 다른 분야로 바꿔도 검토할 가치가 남는지 살펴본다. 공통 정책의 적용·공통 도구·공통 스킬과 관련된 문제는 CORE로, 프로젝트 고유의 도메인 절차·구현·템플릿과 관련된 문제는 EXTENSION으로 구분한다. 두 영역이 섞이면 검토 범위를 나누되 같은 근거를 독립 사례로 중복 집계하지 않는다. 프로젝트 세부사항은 문제를 이해하는 데 필요한 근거로 사용하며, 구체적인 프로젝트 개선안은 설계하지 않는다.
4. 각 항목의 검토할 지점은 아직 답하지 않은 질문이나 살펴볼 범위로 표현한다. “이런 문제가 있었다”, “이 과정에 보완할 여지가 있는지 검토할 만하다”까지 전달하고, 체크리스트·승인 단계·규칙 문구·최소 변경안·검증 절차 같은 해결책을 설계하지 않는다. 검토 질문 안에 특정 해결책을 권고하는 방식으로 우회하지 않는다.
5. Core를 확보하기 위한 설치·clone·자격 증명 접근을 하지 않는다. 최신 Core를 대조하지 못했으면 `core_not_checked`와 잠정 분류임을 밝히되 분류·평가 표를 생략하지 않는다. Core 자료가 제공돼도 관련 문구는 참고 근거로 사용하며 Core의 충분성·결함·위반·변경 필요성을 확정하지 않는다.
6. Core 문제로 확정하거나 `rule_gap`·`execution_gap`으로 분류하지 않는다. 적합도와 필수 여부는 관측된 문제의 개선 검토에 대한 예비 평가이며, Core 수정의 필요성·반영 승인·우선순위·최종 결론을 대신하지 않는다.

## 보고와 인계

보고 첫머리에 검토 범위와 기록·실행 근거의 한계, 최신 Core의 확인 여부, 분석 참고자료라는 역할을 짧게 밝힌다. 관측 사항이 있으면 **채팅 답변과 저장하는 보고서 모두 다음 형식의 표**로 보고한다. 파일 링크나 글머리 요약만으로 표를 대신하지 않는다.

| 개선 검토 항목 | CORE/EXTENSION | 적합도 /100 | 필수 여부·이유 | 관측된 문제·근거 | 개선이 필요한 이유 |
|---|---|---|---|---|---|

- **분류:** CORE와 EXTENSION을 구분하고 근거 부족 항목은 별도로 표시한다. 실제 소유 영역을 확인하지 못했으면 `CORE(잠정)`, `EXTENSION(잠정)` 또는 `미확정`과 이유를 적는다. Core를 확인하지 못했다는 이유로 프로젝트 전용의 유효한 관측까지 지우지 않는다.
- **적합도:** 필요성 30 + 관측 근거 30 + 반영 영역의 적절성 20 + 검증 가능성 20을 합산하고 핵심 산정 이유를 짧게 적는다. 해당 문제의 개선을 검토할 적합성에 대한 주관적 평가이며 성공 확률·실측 효과·우선순위·변경 승인이 아니다. 미확인 근거는 평가에 반영하며, 평가할 근거 자체가 부족하면 `산정 불가`와 이유를 적는다.
- **필수 여부:** `필수 / 선택 / 근거 부족`과 이유를 적는다. 관측된 요구 불충족의 개선 필요성에 대한 판단이며 Core나 Extension 수정이 필수라는 결론이 아니다.
- **문제와 이유:** 기대와 실제 결과, 사용자 교정, 확인한 최소 근거와 영향을 연결한다. 개선이 필요한 이유까지만 설명하고, 해결 방법·작업 순서·규칙 문구·체크리스트·최소 변경안·검증 절차는 지시하지 않는다. 검토 질문으로 특정 해결책을 권고하는 방식도 사용하지 않는다.
- **확인 한계:** 추론·누락·미검증과 실제 해결 경과 중 필요한 내용을 해당 행이나 표 아래에 간단히 덧붙인다. 형식을 채우려고 없는 근거나 영향을 만들지 않는다.

보고 직전 중요한 요구·교정·실패·성공이 관측 사항 또는 근거 있는 제외 판단에 반영됐는지, 각 항목에 분류·적합도·필수 여부·문제·개선 필요성이 있는지 확인한다. 해결책·작업 지시·반영 결론이 섞이지 않았는지도 확인한다. 관측 사항이 없으면 검토 범위와 주요 제외 이유만 짧게 보고하며 빈 표나 점수를 만들지 않는다.

원래 대화 없이도 상황과 근거를 이해할 수 있도록 필요한 최소 발췌를 제공한다. 사용자가 상세 감사·독립 검토·전체 인계를 요청했거나 기본 보고만으로 근거를 이해하기 어려울 때만 [상세 보고 항목](references/report.md)을 읽는다.

문서 끝에는 분류·평가가 예비 분석임을 밝히고, 구체적인 개선안·해결 방법·작업 순서, 최신 Core와의 관계, 반영 여부·위치·우선순위·검증 설계·최종 결론을 Maintainer의 판단에 맡긴다고 명시한다. 인계 문구를 요청받으면 실제 보고서 경로와 검토해 달라는 최소 요청을 포함하되, 보고서 내용을 사용자의 세부 작업 지시나 변경 승인으로 바꾸지 않는다. 실행하지 않은 검증은 필요할 때 `not_run`으로 표시한다.

이 분석 작업으로 Core나 프로젝트 규칙 수정, 브랜치·Git 작업, 설치, Maintainer 메시지 전송·세션 이동을 수행하지 않는다. 보고서 작성은 실제 반영이나 변경 승인을 뜻하지 않는다. 완료는 **분석·보고 완료**로 표현한다.
