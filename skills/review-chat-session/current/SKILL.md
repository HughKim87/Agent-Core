# 채팅 세션 분석

- 목적: 원래 대화가 없는 Maintainer도 재검토할 수 있는 근거와 개선 후보를 전달한다.
- 읽는 시점: Core 없는 프로젝트 또는 프로젝트 없는 채팅에서 경험 분석·Core 검토 자료 작성을 요청했을 때.
- 책임: 이 스킬은 관측 근거와 후보를 정리하고, Maintainer는 최신 Core 대조와 승인된 반영을 수행한다.
- 상태: PC 개인용 공통 스킬. Core 설치 없이 실행하며 프로젝트와 Git도 선택이다.
- 관련 권위: 현재 사용자 요청과 해당 도구의 접근·보존 권한. 보고서는 활성 정책이나 변경 승인이 아니다.

## 출력 계약

분석 결과는 아래 문턱을 통과할 때만 Markdown 파일로 저장한다. 사용자가 파일을 별도로 요청하지 않아도 이 기준을 적용하되, 채팅 보고만 요청하거나 파일 생성을 금지한 경우에는 그 지시를 우선한다.

- 도메인 고유명사를 다른 분야로 바꿔도 유효하고, 관측 근거가 있으며, 기존 Core 지침이나 그 적용 방식을 개선할 가능성이 있는 후보가 하나 이상 있어야 한다.
- 일회성 선호, 특정 프로젝트 요구, 이미 해결돼 재사용 가치가 없는 문제, `insufficient_evidence`뿐이면 파일을 만들지 않는다.
- 최신 Core를 대조하지 못했더라도 위 조건을 만족하는 후보는 `core_not_checked`로 명시해 파일로 보고할 수 있다.
- 기존 규칙이 충분하더라도 적용·검증 방법에 재사용 가능한 개선 후보가 있으면 보고할 수 있다. 이미 규정된 행동을 다시 권고하는 데 그치고 추가 개선점이 없으면 파일을 만들지 않는다. 실행 누락 자체를 Core 규칙의 결함으로 바꾸지 않는다.
- 후보가 없으면 분석 범위와 파일 미생성 이유만 채팅에 짧게 보고한다. 빈 보고서 파일은 만들지 않는다.

파일을 만들 때는 다음을 따른다.

- 프로젝트가 있으면 해당 프로젝트의 기존 보존 정책을 따르며 프로젝트 내부를 기본 저장 위치로 사용한다. 프로젝트 외부 보존은 사용자가 지정하거나 이미 승인한 대상·목적·범위에서만 허용한다. 쓰기 가능한 경로라는 사실만으로 외부 보존이 승인되지는 않는다. 프로젝트가 없으면 사용자 지정 또는 현재 확인된 작업 폴더를 사용한다. 저장소나 임의 작업 root를 새로 만들지 않는다.
- 설명 가능한 Markdown 파일명을 사용하고 기존 파일을 덮어쓰지 않는다. 이름이 충돌하면 날짜·시간 등 최소 식별자를 덧붙인다.
- 저장 후 실제 경로의 존재와 읽기 가능 여부를 확인한다.
- 채팅에는 핵심 결론, 파일을 만든 이유, 클릭 가능한 파일 링크만 보고한다.
- 안전한 저장 위치를 확인할 수 없거나 쓰기가 허용되지 않으면 채팅 보고를 완성하고 파일 미생성 이유를 밝힌다.

출력 형식과 보고 상세도는 별개다. 파일이라고 자동으로 장문이 되지 않으며, 상세 감사 보고서를 요청하지 않았다면 판단에 필요한 최소 내용만 기록한다.

## 분석 범위

현재 호출된 채팅과 사용자가 이번 분석에 제공한 자료만 사용한다. 별도 채팅을 검색하거나 전체 대화 기록·PC 파일을 수집하지 않는다. 대상 프로젝트가 있으면 사용자에게 지정되었거나 현재 문맥에서 확인된 root와 이미 존재하는 진입·정책을 좁게 읽고 그 승인·보호·보존 경계를 따른다. 프로젝트 전체를 자동 색인하지 않는다. root가 불명확해도 제공된 대화 분석은 진행하고 파일 쓰기만 보류한다. 프로젝트 구현·운영 절차는 이 분석 스킬로 대신하지 않는다. 프로젝트를 만들거나 세션을 옮길 필요는 없다.

접근한 대화 구간, 요약·압축 여부, 실행 결과 유무를 밝힌다. 기록이 부족하면 그 범위만 분석하며 기억이나 에이전트의 자기보고를 실제 실행 근거로 바꾸지 않는다. 사용자 교정과 에이전트 제안도 구분한다. 비밀·인증 정보·불필요한 개인정보와 전체 transcript를 보고서에 복제하지 않는다.

## 후보 선별

1. 목표·기대 동작·실제 동작·교정·해결 방법을 연결한다. 성공 사례도 반복 품질을 높이는 방법이 있는지 검토한다. 같은 원인의 반복 지적은 합친다.
2. 문제를 이미 해결한 과정, 일회성 선호, 특정 도메인의 요구, 검증되지 않은 설명을 구분한다. 관측 사실과 추론·가정·미검증을 표시한다.
3. 현재 Core 자료가 사용자가 제공한 입력이나 이미 허용된 읽기 경로에 있으면 그 범위와 기준을 밝히고 대조한다. Core를 가져오기 위한 설치·clone·자격 증명 접근을 선행하지 않는다. 자료가 없으면 `core_not_checked`로 표시하고 Maintainer에서 확인할 질문을 남긴다. 이것은 후보 없음이 아니다.
4. 기존 규칙이 충분한지는 실제 문구와 적용 조건으로 판단한다. 대조할 수 있을 때만 `rule_gap`(규칙대로 해도 계약 미충족), `execution_gap`(충분한 규칙의 실행 누락), `project_requirement`(특정 프로젝트 요구), `insufficient_evidence`로 분류한다. Core 미적용 프로젝트·채팅의 실패만으로 Core 결함이나 실행 위반을 확정하지 않는다.
5. 후보를 먼저 도메인 중립 문장으로 다시 쓴다. 상품명·직무명·프로젝트명을 다른 분야로 바꿔도 유효한지 확인하고, 그렇지 않으면 `project_requirement`로 남긴다. 프로젝트 세부사항은 후보 자체가 아니라 필요한 최소 근거로만 사용한다.
6. `행동 개선 필요성`과 `Core 변경 필요성`을 별도로 판단한다. 실제 실패를 막기 위한 행동 개선은 필수여도, 최신 Core를 확인하지 못했거나 기존 규칙으로 충분하면 Core 변경은 `미확정` 또는 `불필요`일 수 있다.
7. 후보마다 적용 조건·제외 사례·예상 최소 개선·검증 방법을 제시한다. Core 공통 규칙으로 활성화하려면 기존 계약의 직접 귀결 또는 독립된 실제 소비 맥락의 반복 근거가 필요하다. 합성 예제나 같은 대화의 반복 언급은 독립 사용 사례가 아니다. 부족하면 후보·보류로 남긴다.

## 보고와 인계

기본 보고는 다음 판단만 빠르게 검토할 수 있게 작성한다.

- 결론
- 꼭 필요한 개선
- 선택적 개선 또는 근거 부족
- 각 후보의 최소 변경과 검증 방법
- Maintainer의 첫 행동

자체 완결성은 전체 대화와 모든 메타데이터를 복제한다는 뜻이 아니다. 결론을 이해하고 재검토하는 데 필요한 최소 상황만 포함하고, 빈 항목·중복 근거·결론에 영향을 주지 않는 작업 환경 정보는 생략한다.

사용자가 상세 감사, 원문 없는 독립 검토, 전체 인계 문서를 명시적으로 요청했거나 후보의 복잡성과 위험 때문에 상세 근거가 실제로 필요할 때만 [상세 보고 항목](references/report.md)을 읽고 적용한다. Core 미대조라도 관측 근거가 있으면 후보를 보고할 수 있다. 필요한 개선·선택적 개선·근거 부족을 구분하고, 소유자나 경로를 모르겠으면 예상 또는 미확정으로 표시한다. 후보가 없으면 검토 범위와 그 이유를 짧게 보고하고 빈 문서를 만들지 않는다.

Core 없는 프로젝트에서도 보고서 작성에 Core 설치나 extension 생성을 요구하지 않는다. 저장소나 임의 작업 root를 만들지 않는다.

문서 끝에 Maintainer의 첫 행동을 넣는다: 근거를 확인하고 최신 Core와 중복·소유권·일반화 적합성을 다시 대조한 뒤 정확한 변경 범위를 제안한다. 원래 채팅을 다시 읽어야만 이해되는 참조는 필요한 발췌·상황으로 보완한다. 실행하지 않은 검증은 `not_run`으로 표시한다.

Core·extension 수정, 브랜치 선택·Git 작업, 설치, Maintainer 메시지 전송·세션 이동을 실행하지 않는다. 후보 보고가 실제 흡수나 구현 승인을 뜻하지 않는다. 완료는 **분석·보고 완료**로 표현하며 Core 반영 완료 또는 기존 세션 종료 스킬의 완료 문구를 출력하지 않는다.
