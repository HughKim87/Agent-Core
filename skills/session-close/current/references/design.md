# 개선 설계 항목

- 목적: 승인한 세션 개선의 설계 입력과 검증 근거를 식별한다.
- 읽는 시점: 진행 후보 승인 뒤 작업 위치를 정하거나 설계·구현·작업 자원 정리를 할 때.
- 책임: 에이전트가 필요한 설계와 근거를 정리한다. 승인·작업 위치·정리·완료 판정은 본문과 대상 정책이 소유한다.
- 상태: 본문 §4~§6이 승인 뒤 연결하는 실행 절차와 설계 항목.
- 관련 권위: [세션 종료 스킬](../SKILL.md), 대상 저장소 정책의 단계 작업·버전 관리 규칙.

아래 항목 중 작업에 필요한 내용을 설계에 담는다. 승인·보류 결정과 종료 판정은 본문 §4·§6을 따르고, 승인 후의 작업 위치·설계 파일 보존·정리 절차는 아래 해당 절에서 확인한다. 내용 없는 템플릿이나 기존 정책의 복제본은 만들지 않는다.

## 전체 설계

- 설계 목적과 승인 범위. 파일로 보존할 때는 문서의 읽는 시점·책임·상태·관련 권위.
- 분석 원본 세션의 접근 범위와 근거 한계.
- 승인 후보 ID와 요청 조건 → 변경 표면 → 필수 검증 대응.
- 저장소별 절대 경로·역할·선택한 작업 위치·진입 기준, Core/extension/부모 경계와 기존 변경 보존 근거.
- 허용 행동·제외 범위·입력 참조·보호 경계·필요한 사용자 결정·완료 수준.
- Core와 extension 목적에 따른 소유권·일반화 근거·적용 조건·near-miss.
- 필요한 단계와 의존 조건·goal·성공 조건. 활동 구분만으로 단계를 늘리지 않는다.
- 논리적 커밋 단위, 필요한 부모 gitlink와 snapshot 검증 근거의 소유 저장소.
- 이번에 만들 임시 자원의 대상·생성 주체·목적·병합 대상·정리 위임과 보존할 근거.
- 후보 ID·승인/보류/거절·미채택 상태와 최종 보고의 연결.
- 사용자 요청 또는 적용 정책에 따라 보존할 파일의 경로·수명·Git 작업 범위.
- 실패·차단·복구·범위 변경 시 처리와 재개 조건.

## 현재 단계 설계

작업에 필요한 항목을 식별하며 다른 단계의 상세나 진행 상태를 중복 기록하지 않는다.

| 항목 | 정의 |
|---|---|
| 진입 조건 | 의존한 goal·검증·필요한 커밋 근거 및 현재 대상 상태 |
| 작업 정의 | 승인 후보 ID, 해결할 문제, 변경 경로와 동작 |
| 제외 범위 | 변경하지 않을 경계 |
| 검증 조건 | 실제 명령/관측, 예상 결과, 증거 수준과 확대 조건 |
| 성공 조건 | goal을 증명하는 관측 가능한 조건 |
| 후보 판정 | pass/fail/not_run/not_applicable과 비해당 근거 |
| 커밋 근거 | 실제 변경 범위·이유·수행 검사·snapshot 대응 |
| 전환 조건 | goal·선택 필수 게이트와 해당 완료 수준의 근거 |
| 복구 | 검증된 기준점·승인된 복구 범위·재개 조건 |

## 최종 검토 근거

본문 §6의 판정에 필요한 실제 변경·검사·커밋 대응, 보존/정리 대상과 위임, 기존 변경·고유 근거 보존, 남은 결정·한계를 식별한다. 설계라는 파일 종류만으로 삭제 대상을 정하거나, 참고자료에서 본문의 승인·완료 조건을 다시 정의하지 않는다.

## 작업 위치 선택

선택된 대상의 정책과 실제 상태를 다시 대조하고 §2의 기준 상태 이후 달라진 변경을 확인한다. 새 브랜치·워크트리는 승인된 후보의 구현에 필요하고 사용자가 해당 방식을 선택한 경우에만 만든다. 기존 대상에서 작업할 수 있으면 새 자원을 만들 필요가 없다.

로컬 변경은 기준 상태로 구분해 보존하고 승인된 비충돌 개선은 진행한다. 존재 자체로 작업 위치 재승인을 요구하지 않는다. 동일 파일의 분리 불가 변경·소유권 충돌·실제 전환이 필요한 구간만 현재 위임과 대조해 필요한 결정을 받는다. 기존 변경을 commit·stash·reset·clean·삭제·이동할 권한으로 확대하지 않는다. 다음 방식은 실제 필요에 따라 선택한다.

1. **선택한 브랜치에서 그대로 계속**: 기존 변경을 기준 상태로 구분해 보존하고 개선 범위만 작업한다. 이미 선택한 브랜치와 현재 체크아웃이 다르면 브랜치 전환 및 기존 변경의 처리 범위도 확인한다. 기존 변경을 개선 커밋에 섞거나 승인 없이 commit·stash·reset·clean·삭제·이동하지 않는다. 동일 파일 충돌 등 기존 변경을 안전하게 보존할 수 없는 구간만 별도 결정을 받는다.
2. **별도 개선 브랜치·워크트리에서 작업 후 병합**: 사용자가 선택한 기준 브랜치의 확인된 HEAD에서 작업 전용 브랜치와 워크트리를 만든다. 기존 작업 폴더는 전환하거나 정리하지 않는다. 별도 워크트리의 정책·실제 기준 commit·청결 상태·submodule 경계를 확인한 뒤 진행한다. 완료 후 검증된 개선만 기준 브랜치에 병합하고 이번 호출이 만든 자원은 §6에 따라 정리한다. push는 포함하지 않는다.

## 승인된 개선의 실행

개선 시작 직전에 대상 정책 라우터에서 **최신 단계별 작업 규칙과 버전 관리 규칙을 다시 확인**한다. 같은 논리 작업에서 이미 읽은 규칙은 읽기 이력을 존중하되 적용 절차를 다시 대조하고, 파일 변경 시 변경된 정본을 읽는다. 규칙을 찾지 못하거나 승인 경계가 충돌하면 추정 실행하지 않고 필요한 결정을 받는다.

이 문서의 전체 설계와 현재 단계 설계 항목을 확인하고 필요한 작업 설계를 채팅에 제시한다. 설계 파일은 사용자가 파일 보존을 명시적으로 요청하거나 대상 정책이 요구할 때만 작성한다. 전체 설계·현재 단계·현재 상태의 책임을 분리하며 기존 정책 본문을 복제하지 않는다. 설계는 승인된 개선 ID, 정확한 대상, 작업 정의, 단계별 진입·검증·goal 성공·전환·커밋과 복구 조건을 갖는다.

설계 완성 뒤 단계 구성·성공 조건·정확한 임시 경로와 정리 범위, 요청받은 파일 보존 위치를 사용자에게 제시해 기존 승인으로 충족되는지 확인한다. 승인 범위를 넘는 결정은 답을 기다린다.

설계 파일의 작성·커밋을 승인받은 경우에만 **0단계**로 해당 파일을 정확한 경로에 커밋하고 snapshot 일치를 확인한다. 채팅 설계로 충분하면 별도 파일·0단계·빈 커밋을 만들지 않고 승인된 구현을 진행한다. Core 자체에 consumer 현재 상태를 만들지 않는다. 여러 저장소의 구현/부모 gitlink와 요청된 설계 파일의 커밋 경계를 명시한다.

구현 순서와 커밋 단위는 대상 정책의 의존 관계·공유 쓰기·원자성 기준을 따른다. 단계 이름만으로 직렬화하거나 커밋을 분리하지 않는다. 각 완료 단위에서 다음 근거를 확인한다.

1. 이전 단계 goal·선택 필수 게이트·후보 커밋 증거와 현재 진입 조건을 확인한다.
2. 승인된 작업 정의만 구현하고 선택한 검증을 실제 실행한다.
3. 조건별 pass/fail/not_run/not_applicable을 판정한다. 비해당은 근거를 남기고 필수 게이트에서 제외한다.
4. 상태·다음 행동을 갱신하고 논리적으로 함께 유효한 정확한 변경을 커밋한다. 서로 의존한 여러 단계 변경은 원자적 단위로 묶을 수 있다.
5. 실제 snapshot의 경로·내용·검증 증거를 대조한다. 해당 단계에서 요구하는 snapshot 검증을 수행한다.
6. **요청 결과 달성 + 남은 필수 게이트 전부 pass + 해당 완료 수준의 커밋 근거 확인** 이후에만 다음 단계로 전환한다.

fail 또는 not_run이면 전환하지 않는다. 대상 정책의 실패 처리/예산을 따른다. 범위·보장·필수 성공 조건을 실질적으로 바꾸면 설계와 승인을 재확정한다. Core 규칙 의미 변경의 독립 감사와 route 변경의 별도 의미 검증 등 대상 정책이 요구하는 게이트를 빠뜨리지 않는다. 설치·push·원격 변경은 스킬 호출이나 단계별 로컬 커밋 위임에 포함하지 않는다.

## 작업 자원의 병합과 정리

이번 호출이 만든 개선 브랜치·워크트리가 있으면 **종료 표시 전에 정리한다**. 생성 시 기록과 실제 대상·현재 사용자를 대조해 기존/공유/다른 Agent의 자원을 제외한다. 검증된 개선과 필요한 현재 상태가 승인된 기준 브랜치에 병합되고 필요한 commit이 그 브랜치에서 복구 가능한지 먼저 확인한다. 원래 작업 폴더를 전환하지 말고 필요한 경우 별도 통합 워크트리에서 병합한다. 기준 브랜치가 다른 작업에서 사용 중이거나 새 변경과 충돌하면 그 작업을 건드리지 않고 병합 방법을 확인한다.
   - 제거할 워크트리의 staged·unstaged·untracked·ignored 고유 자료와 관련 submodule을 확인하고 보존할 근거가 남지 않았음을 확인한다. 이번 호출이 만든 통합 워크트리도 같은 정리 대상이다.
   - 생성 때 사용자에게 제시하고 승인받은 정확한 종료 정리 범위를 재사용한다. 승인되지 않은 대상·새 사용자 변경·다른 Agent 사용·미병합 commit이 발견되면 해당 정리만 보류하고 필요한 결정을 받는다. 강제 삭제로 우회하지 않는다.
   - 작업 폴더 밖의 실행 맥락에서 워크트리를 정상 제거하거나 관리 도구로 보관 처리한 뒤, 다른 워크트리에 체크아웃되지 않았고 병합된 이번 개선 브랜치만 안전 삭제한다. 기존 기준 브랜치(main 등)와 원래 워크트리는 삭제하지 않는다. 원격 브랜치 삭제는 별도 승인 대상이다.
   - 파일 보존을 요청받은 산출물이 있으면 임시 워크트리에만 남지 않도록 승인된 보존 위치를 확인한다. 실제 워크트리 등록 및 개선 브랜치 부재, 기준 브랜치의 결과 보존, 설치 스킬 등 외부 정본 반영과 원래 작업 보존을 확인한다. 정리 결과를 최종 응답에 보고한다. 정리 미완료는 종료 완료로 표시하지 않는다.
