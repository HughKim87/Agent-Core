# 세션 종료

- 목적: 호출된 세션의 경험에서 재사용 가치가 있는 개선 후보를 넓게 찾고, 근거 수준과 실제 반영 기준을 따로 판단하여 승인된 개선과 보고를 마친다.
- 읽는 시점: 사용자가 이 스킬을 직접 선택하거나 $session-close로 호출했을 때만.
- 책임: 사용자가 대상·개선 범위·보류를 결정하고 에이전트가 분석·설계·검증·커밋·정리를 수행한다.
- 상태: 직접 호출 전용 스킬.
- 관련 권위: 현재 사용자 지시, 대상 저장소의 진입 정책·Core 정책·소비 정책과 현재 행동에 route된 규칙.

## 호출 경계

agents/openai.yaml의 allow_implicit_invocation: false를 유지한다. 별도의 트리거 단어를 등록하지 않는다. “세션 종료”, “끝내자”, 작업 완료, 핸드오프 요청으로 자동 실행하지 않는다. 이 스킬을 생성·수정하는 요청도 종료 실행이 아니다.

스킬 호출은 분석과 승인 절차의 시작이며 개선 전체의 승인이 아니다. 대기·차단·부분 완료 상태에서는 종료 문구를 표시하지 않는다.

## 1. 매 호출마다 작업 대상 확인

1. 호출된 세션을 분석 원본으로 고정하고 아래 전체 재독 절차를 수행한다.
2. 현재 저장소의 진입 포인터가 요구한 파일을 지정 순서대로 끝까지 읽는다. 대상 식별에 필요한 읽기 전용 Git 정보만 확인한다.
3. 접근 가능한 대상의 정책을 읽고 실제 저장소 루트·브랜치·HEAD·워크트리·submodule 경계를 읽기 전용으로 확인한다. host의 Core는 읽기 전용이며 Core 구현에는 별도로 확인된 maintainer 대상이 필요하다. 분석·제안만 제공할 때는 Core 구현용 브랜치 선택이나 maintainer 대상 확보를 선행 조건으로 요구하지 않는다. 정책상 브랜치 제한을 우회하지 않는다.
4. 후보 선별과 분류 보고를 먼저 마친다. 이 단계에서는 브랜치·워크트리를 생성·전환하지 않으며 작업 위치 선택도 §4의 진행 후보 승인 뒤로 미룬다.
5. Core와 extension의 실제 소유 경로 및 목적·공개 계약을 확인한다. extension을 무조건 consumer나 experimental로 추정하지 않는다. 식별되지 않으면 사용자에게 정확한 저장소/경로를 물어 확정한다.

분석을 시작할 때 해당 세션의 전체 기록을 처음부터 마지막까지 다시 읽는다. 현재 문맥·기억·요약·핸드오프·최근 답변만으로 이를 대신하지 않는다. 같은 채팅의 기록 조회 도구를 사용하고 다음 페이지가 있으면 조회 종료까지 이어 읽는다. 최신순으로 조회되면 전 구간을 확보한 뒤 시간순으로 검토한다. 잘린 메시지는 원문을 추가 조회하고 요약만 제공된 구간은 원문을 확보한다. 사용자가 제공한 기록이나 환경의 기록 adapter가 분석 원본이면 같은 기준으로 끝까지 읽는다.

조회 종료·접근 구간·원문 누락·요약 여부를 확인해 보고 첫머리에 전체 재독 완료 또는 부분 검토를 명시한다. 원문을 확보하지 못하면 읽을 수 있는 나머지 구간은 계속 검토하고 누락 구간·원인·판단 한계를 밝힌다. 조회할 수 있는 원문을 남긴 채 요약만으로 전체 재독을 마쳤다고 하지 않는다. 기록을 확보하려고 다른 채팅·보호 경계를 넘거나 없는 내용을 추정하지 않는다.

대화 원문 전체 재독 여부와 과거 실행 결과의 검증 여부는 구분한다. 메시지 원문을 모두 읽었어도 과거 검사 로그가 없으면 실행 결과만 미검증으로 표시하며, 그 이유만으로 대화 원문이 누락됐다고 추정하지 않는다.

## 2. 읽기 전용 기준 상태 확인

접근 가능한 분석 대상에서 후보 선별 전, 대상 저장소와 관련 submodule의 staged·unstaged·untracked·충돌·gitlink 변경을 읽기 전용으로 확인한다. ignored 파일은 확인 가능한 경로 메타데이터로 작업 전용/기존 사용자 자원을 구분하되 보호 경로를 열거하거나 비밀 내용을 읽지 않는다. 상태 조회 실패를 clean으로 간주하지 않는다.

로컬 변경은 기존 작업과 개선 후보를 구분할 기준으로 확인한다. 읽기 전용 분석·보고를 위해 기존 변경의 정리나 작업 위치 승인을 선행 요구하지 않는다. 상태 조회에 실패하면 확인 한계와 영향받는 판단을 표시하고, 접근 가능한 근거로 분석을 계속한다. 실제 작업 위치 선택과 쓰기 직전 상태 재확인은 진행 후보 승인 뒤 §4에서 수행한다.

## 3. 개선 후보 탐색과 반영 적합성 판단

### 경험에서 후보 찾기

§1~2에서 확인한 분석 대상·기준 상태를 바탕으로 세션 근거와 현재 파일을 읽기 전용으로 대조한다. **Core 개선 가능성도 매 호출 기본 분석 범위에 포함한다.** Extension 개선만 발견되거나 Core가 읽기 전용이어도 접근 가능한 Core 정책·규칙과 세션 근거를 함께 대조한다. Core 자료에 접근할 수 없으면 분석 미실시와 필요한 자료를 표시하며 “개선 없음”으로 판정하지 않는다.

사용자 교정·반복 시행착오·검증 누락뿐 아니라, 효과가 있었던 접근·도구 조합·확인 방법과 불필요한 작업·질문·재시도를 줄일 기회를 살펴본다. 각 관찰에서 다음 작업에 재사용할 가치와 구체적으로 달라질 행동을 설명할 수 있는지 판단한다. 실패가 해결됐어도 예방책이 재사용 가능한 형태로 반영됐는지, 성공한 방법도 적용 조건과 한계를 남길 가치가 있는지 확인한다. 세션 길이나 사용자 기대를 이유로 후보 수를 채우지 않으며 일회성 취향·단순 작업 이력·효과 없는 중복은 제외한다.

후보 발견과 실제 반영 자격을 구분한다. 한 번의 관측이나 아직 원인이 확정되지 않은 문제도 관측 근거와 확인할 가설·다음 검증이 있으면 검토 후보로 보고할 수 있다. 미검증 원인이나 효과를 사실로 단정하지 않는다. Core 일반화 근거가 부족하거나 기존 규칙이 있다는 이유만으로 후보를 지우지 않고, 반영 위치·추가 검증·이미 반영 여부를 따로 판단한다.

### 원인·개선 방식과 소유자 판단

후보의 성격을 `rule_gap`(기존 문구대로 실행해도 계약을 충족하지 못하는 반례), `execution_gap`(기존 규칙의 발견·실행·검증 누락), `successful_method`(조건과 한계를 붙여 재사용할 가치가 있는 성공 방법), `workflow_opportunity`(관측된 낭비나 선택적 품질 향상 기회), `project_requirement`(해당 프로젝트의 요구), `insufficient_evidence`(원인·효과·소유권 미확인)로 설명한다. 필요한 경우 함께 표시하고 분류명만으로 채택·제외하지 않는다.

적용 소유자와 기존 규칙의 충분성을 대조하고 개선으로 달라질 행동을 설명한다. `rule_gap`은 실제 반례를 해결하는 최소 소유자 수정을 검토한다. `execution_gap`은 발견 경로·확인 시점·실행 절차·도구·검증 중 무엇이 누락을 줄일지 검토한다. “기존 규칙을 잘 지킨다”는 재진술만으로 개선안을 대신하지 않는다. 성공 방법과 작업 개선 기회는 적용 조건·예상 이익·비용·한계를 보고하고, 근거가 부족하면 확인할 질문이나 비교 방법을 제시한다. 프로젝트 요구는 해당 프로젝트 소유자에서 처리한다.

일반화할 수 있는 원칙이라는 판단과 새 규칙 문구가 필요하다는 판단을 구분한다. 기존 규칙으로 같은 행동을 도출할 수 있으면 중복 의무 문구를 추가하지 않되, 발견·실행 지원이나 권장 방법의 개선 가능성은 따로 검토한다. 이미 동일한 예방책·방법이 충분히 반영됐으면 그 위치와 근거를 밝히고 중복 제안하지 않는다. 소유 경로의 쓰기 가능 여부는 소유권 판단을 바꾸지 않으며, 접근할 수 없으면 필요한 대상·결정을 보고한다.

### 실제 반영 적합성 판단

아래 기준은 발견한 후보를 어디에 어떤 수준으로 반영할지 판단하는 기준이며, 후보를 보고하기 위한 선행 자격이 아니다.

- **Core**: 대상의 헌장·보장·포함 기준과 현재 일반화 규칙을 따른다. 도메인 중립 계약의 직접 귀결 또는 독립된 실제 소비 맥락의 반복 근거를 제시한다. 합성 fixture를 실제 반복 사례로 세지 않는다. 프로젝트 경로·데이터·운영 상태는 Core에 흡수하지 않는다.
- **Extension**: 식별한 extension의 의도·선택 계층 여부·기능 계약에 맞는 반복 품질 향상인지 판정한다. 특정 도메인에 적합한 재사용성도 인정하되 Core 보장으로 확대하지 않는다. extension의 필수화나 Core 의존 확대는 별도 변경 범위다.
- 먼저 기존 소유자 보강 가능성을 판단한다. 새 소유자는 구별되는 책임이 있을 때만 제안한다. Core 공통 부분과 extension 적용 부분이 섞이면 분리한다.

후보마다 ID, 관측 근거, 현재 결함/재사용 가치, 의도와의 연결, 성격·소유자·예상 경로, 적용 조건·near-miss, 반영 적합성, 최소 개선안, 검증 방법을 필요한 만큼 짧게 보고한다. 경로·소유권이 미확정이면 그렇게 표시한다. 추론·가정·미검증을 관측 사실과 구분한다. 필요성과 반영 준비도는 별도로 판단한다.

| 반영 준비도 | 판단 |
|---|---|
| 반영 제안 가능 | 예상 소유자와 개선안·근거가 구체적이며 해당 반영 기준을 충족함. 구현 승인은 별도이며 대상 정책의 필수 감사·검증은 실제 활성화 전에 수행한다 |
| 추가 검증 필요 | 단일 경험의 일반화, 원인·효과·소유권 등 미확인 항목과 다음 확인 방법을 제시함. Core에 당장 반영할 수 없어도 후보는 보고한다 |

이미 반영됐거나 재사용 가치·차별성이 없어 제외한 관찰은 주요 제외 이유로 요약한다. 반영 준비도를 승인·보류·거절 상태와 혼동하지 않는다.

| 분류 | 판단 |
|---|---|
| 꼭 필요한 개선 | 근거 있는 현재 계약·보장 위반, 반복 결과의 정확성/복구/안전/완료 검증을 훼손하는 결함. 왜 지금 필요한지와 미개선 영향을 제시한다 |
| 꼭 필요하지 않은 개선 | 편의·표현·최적화·장래 가능성 또는 현재 보장에 영향이 없는 선택적 품질 향상 |
| 근거 부족 | 필요성이나 소유권을 판단할 근거가 부족함. 확인할 질문 또는 보류 사유를 표시한다 |

일반화 게이트를 통과하지 못한 후보를 “필요”라는 이유로 Core에 넣지 않는다.

## 4. 분류 보고와 개선 승인

### 기본 분석·분류 보고 계약

별도 요청이 없어도 전체 재독 결과를 바탕으로 아래 항목을 기본 보고한다. 이 계약은 이 스킬의 검토 보고에 적용하며 일반 작업 답변의 공통 형식으로 확대하지 않는다. 사용자의 현재 명시적 형식 지시는 우선한다.

1. **검토 범위**: 전체 세션 재독 완료 여부와 확인한 구간, 확보하지 못한 원문·요약·실행 근거의 한계.
2. **CORE / EXTENSION 분류**: 후보별 실제 개선 소유자를 구분한다. 공통 정책·도구·공통 스킬 개선은 CORE, 해당 프로젝트의 도메인 절차·구현·템플릿 개선은 EXTENSION으로 보고한다. Core 미설치 프로젝트도 프로젝트 고유 개선을 EXTENSION 후보로 보고할 수 있으며 실제 extension 경로가 있다는 뜻으로 쓰지 않는다. 소유자가 미확정이면 잠정 분류와 이유를 표시하고, 두 계층의 변경이 섞이면 나눠 보고한다.
3. **작업 적합도 /100**: 후보마다 필요성30 + 관측 근거30 + 반영 위치의 적절성20 + 검증 가능성20을 합산하고 점수와 핵심 산정 이유를 제공한다. 미확인 근거는 점수·한계에 반영한다. 점수는 현재 근거에서 해당 개선을 수행하는 적합도이며 성공 확률·실측 효과·Core 활성화 자격·실행 승인이 아니다.
4. **필수 여부**: 필수 / 선택 / 근거 부족과 이유. 점수, 행동 개선 필요성, Core 변경 필요성, 반영 준비도와 사용자 승인을 서로 대신하지 않는다.
5. **문제**: 어떤 상황에서 무엇이 기대와 달랐고 사용자에게 어떤 영향을 주는지 핵심 근거와 함께 설명한다. 성공 방법·개선 기회는 현재 불편이나 기대 이익을 설명하며 없는 결함을 만들지 않는다.
6. **개선 방법**: 무엇을 어떻게 바꾸며 이후 어떤 행동·결과가 달라지는지 사용자가 이해할 수 있는 말로 요약한다. 중요한 검증과 남은 불확실성만 덧붙이고 분류명·내부 용어·“규칙을 잘 지킨다”로 설명을 대신하지 않는다.

후보별 기본 표현은 `작업 | CORE/EXTENSION | 적합도 /100 | 필수 여부·이유 | 문제 | 개선 방법` 표다. 읽기 쉬운 항목별 설명으로 같은 정보를 제공해도 된다. 보고 첫머리의 검토 범위는 표와 별도로 밝힌다. 파일로 저장해도 채팅에 후보별 기본 요약을 제공하며 결론·파일 링크만으로 이를 대체하지 않는다.

보고 직전 전체 기록의 중요한 요구·교정·실패·성공이 후보 또는 근거 있는 제외 판단에 반영됐는지, 각 후보에 분류·점수·필수 여부·문제·개선 방법이 있는지 대조해 누락을 보완한다. Core 반영 기준을 통과하지 못했다는 이유로 EXTENSION 후보나 실행 방법 개선까지 지우지 않는다. 후보가 없으면 검토 범위와 주요 제외 이유만 보고하며 억지 후보·점수·빈 보고서를 만들지 않는다.


구현 승인 요청 전에 후보와 핵심 판단을 채팅으로 보고한다. 후보별 ID·성격·필요성·기존 소유자/예상 경로·반영 준비도와 일반화 판단·최소 개선안·검증 방법·근거 한계와 승인/보류/거절 상태를 필요한 만큼 제시한다. 즉시 반영 가능 후보가 없다는 사실을 개선 후보 없음으로 바꾸지 않는다.

후보가 없으면 실제 검토한 대화·기록·작업 근거와 접근 한계, 살펴본 주요 관찰 및 제외 이유를 짧게 보고한다. 기존 규칙이나 이미 반영된 개선으로 충분하다는 판단은 해당 위치와 연결한다. 제외할 관찰 자체가 없으면 억지로 예시를 만들지 않는다. Core 후보 없음과 전체 개선 후보 없음을 구분하고, 기록 부족이나 미결 가설이 남으면 “확인한 범위에서 후보 없음” 또는 “분석 불충분”으로 범위를 한정한다. “오래 작업했으므로 반드시 개선이 있다”거나 “Core에 반영할 수 없으므로 개선이 없다”고 결론내리지 않는다.

검토·보고·세션 종료 요청이나 스킬 호출 자체를 보고서 파일 생성·보존·커밋·push 승인으로 해석하지 않는다. 보고서를 파일로 저장하라는 명시적 요청이 있을 때만 지정된 범위에 저장하고, Git 작업은 별도 승인 범위를 따른다.

- 꼭 필요한 후보도 자동 구현하지 않는다. 정확한 대상·변경 범위·검증·단계별 커밋·임시 자원 정리 범위를 제시해 사용자 동의를 받는다.
- 꼭 필요하지 않은 후보는 관련 이슈를 보고하고 각 후보의 **진행 또는 보류**를 확인한다. 여기서 이슈 보고는 채팅 내 문제 설명이며 원격 이슈 생성을 뜻하지 않는다.
- 사용자가 승인·보류·거절한 ID를 구분한다. 응답이 없거나 모호하면 해당 후보를 진행하지 않는다. 근거 부족 후보는 확인하거나 사용자의 보류 결정을 받는다.
- 필요한 후보를 사용자가 거절하거나 보류해도 몰래 구현하지 않는다. 남는 위험을 보고하고 그 결정이 이번 종료에 포함됨을 명확히 한다.
- 모든 진행 후보와 보류 처분이 확정되면 승인된 후보만 아래 단계로 진행한다. 진행 후보가 없으면 작업 위치 선택·브랜치/워크트리 생성·전환·설계·빈 커밋 없이 §6의 해당하는 정리/보고로 간다. 후보 없음과 사용자가 전부 보류·거절한 경우를 구분해 보고한다. 근거 부족이나 미결 결정은 개선 없음으로 처리하지 않는다.

### 진행 후보 승인 뒤 작업 위치와 방식 선택

진행할 개선 후보가 승인된 호출에서만, 설계·변경 전에 “이번 개선은 어느 브랜치에서 진행할까요? `main`을 권장합니다.”라고 묻고 답을 기다린다. 선택지는 `main (권장)`을 첫 번째로, 확인된 현재 브랜치가 main과 다르면 그 브랜치를 다음으로 제시하고 다른 브랜치도 직접 지정할 수 있게 한다. 각 후보의 저장소·워크트리 절대 경로·실제 브랜치·역할을 함께 표시한다. `main` 권장은 자동 선택·생성·전환의 승인이 아니며 이전 호출의 선택, 현재 체크아웃, 질문 UI의 미제출 기본값을 답으로 간주하지 않는다. main이 없거나 정책상 선택할 수 없으면 그 사실과 허용 후보를 표시하고 main을 임의 생성하거나 정책을 우회하지 않는다. Core와 extension의 구현 대상이 서로 다른 저장소라면 한 질문에 저장소별 선택을 묶어 확인한다. 사용자 답에 필요한 생성·전환과 정확한 대상이 포함되어 있으면 그 승인으로 진행하고, 포함되지 않은 생성·전환만 추가 확인한다.

선택된 대상의 정책과 실제 상태를 다시 대조하고 §2의 기준 상태 이후 달라진 변경을 확인한다. 새 브랜치·워크트리는 승인된 후보의 구현에 필요하고 사용자가 해당 방식을 선택한 경우에만 만든다. 기존 대상에서 작업할 수 있으면 새 자원을 만들 필요가 없다.

로컬 변경이 있으면 경로·변경 종류·저장소와 실제 브랜치·워크트리 경로를 요약하고, **어디서 작업할지 또는 작업을 중단할지 사용자에게 질문해 명시적인 선택과 승인을 받는다.** 아래 세 선택지를 제시하되 다른 대상도 직접 지정할 수 있게 한다. 어느 선택지도 강제하거나 자동 실행하지 않는다. 기존 브랜치 선택만으로 로컬 변경을 둔 채 계속할 승인을 추정하지 않는다. 사용자가 답하고 승인하기 전에는 설계·파일 변경·브랜치/워크트리 생성·전환·병합을 시작하지 않는다. 앞선 읽기 전용 후보 분석·보고는 이 선택을 기다리지 않는다. 미응답·모호한 답변·UI 미제출 기본값·시간 경과를 승인으로 간주하지 않는다. 로컬 변경 자체를 작업 불가 사유로 삼거나 사용자에게 선행 정리를 강제하지 않는다.

1. **선택한 브랜치에서 그대로 계속**: 기존 변경을 기준 상태로 구분해 보존하고 개선 범위만 작업한다. 이미 선택한 브랜치와 현재 체크아웃이 다르면 브랜치 전환 및 기존 변경의 처리 범위도 확인한다. 기존 변경을 개선 커밋에 섞거나 승인 없이 commit·stash·reset·clean·삭제·이동하지 않는다. 동일 파일 충돌 등 기존 변경을 안전하게 보존할 수 없는 구간만 별도 결정을 받는다.
2. **별도 개선 브랜치·워크트리에서 작업 후 병합**: 사용자가 선택한 기준 브랜치의 확인된 HEAD에서 작업 전용 브랜치와 워크트리를 만든다. 기존 작업 폴더는 전환하거나 정리하지 않는다. 별도 워크트리의 정책·실제 기준 commit·청결 상태·submodule 경계를 확인한 뒤 진행한다. 완료 후 검증된 개선만 기준 브랜치에 병합하고 이번 호출이 만든 자원은 §6에 따라 정리한다. push는 포함하지 않는다.

3. **작업 중단 또는 보류**: 사용자가 이를 선택하면 개선 작업을 진행하지 않고 현재 상태와 재개 조건만 보고한다. 브랜치·워크트리를 생성하거나 기존 변경을 처리하지 않으며, 종료 완료 문구도 표시하지 않는다.

다른 Agent가 원래 작업 폴더를 사용 중이면 별도 워크트리 방식을 권장하되 반드시 사용자의 선택과 승인을 기다린다. 다른 Agent가 사용하는 원래 작업 폴더에서 개선·checkout·병합을 수행하지 않는다. 대상·생성·병합·정리 범위가 사용자 답에 이미 포함되어 있으면 같은 승인을 다시 묻지 않는다. 작업 전용 자원은 생성 시 저장소·기준 commit·브랜치명·워크트리 절대 경로·생성 주체와 종료 시 정리 대상을 기록한다. 기존 브랜치·기존 워크트리는 정리 대상에 넣지 않는다.

진행 중 새 무관한 변경을 발견해도 같은 선택 원칙을 적용한다. 사용자가 보존하며 계속하도록 승인한 기준 변경은 다시 일률 중단 사유로 삼지 않는다. 내용·소유자가 달라졌거나 이번 쓰기와 충돌하면 영향 구간을 재확인한다. 조회 불가·미해결 충돌·상위 정책 때문에 선택한 방식이 불가능하면 구체적인 제약과 가능한 대안을 설명한다. 체크아웃 변경과 각 Git 쓰기 직전에 대상 동일성을 재확인한다.

질문 도구가 비동기이면 답이 올 때까지 대상에 의존한 작업을 실행하지 않는다. 시간이 지난 것을 동의로 간주하지 않는다.

## 5. 설계와 단계별 실행

개선 시작 직전에 대상 정책 라우터에서 **최신 단계별 작업 규칙과 버전 관리 규칙을 다시 확인**한다. 같은 논리 작업에서 이미 읽은 규칙은 읽기 이력을 존중하되 적용 절차를 다시 대조하고, 파일 변경 시 변경된 정본을 읽는다. 규칙을 찾지 못하거나 승인 경계가 충돌하면 추정 실행하지 않고 필요한 결정을 받는다.

[설계 항목](references/design.md)을 읽고 필요한 작업 설계를 채팅에 제시한다. 설계 파일은 사용자가 파일 보존을 명시적으로 요청하거나 대상 정책이 요구할 때만 작성한다. 전체 설계·현재 단계·현재 상태의 책임을 분리하며 기존 정책 본문을 복제하지 않는다. 설계는 승인된 개선 ID, 정확한 대상, 작업 정의, 단계별 진입·검증·goal 성공·전환·커밋과 복구 조건을 갖는다.

설계 완성 뒤 단계 구성·성공 조건·정확한 임시 경로와 정리 범위, 요청받은 파일 보존 위치를 사용자에게 제시해 기존 승인으로 충족되는지 확인한다. 승인 범위를 넘는 결정은 답을 기다린다.

설계 파일의 작성·커밋을 승인받은 경우에만 **0단계**로 해당 파일을 정확한 경로에 커밋하고 snapshot 일치를 확인한다. 채팅 설계로 충분하면 별도 파일·0단계·빈 커밋을 만들지 않고 승인된 구현을 진행한다. Core 자체에 consumer 현재 상태를 만들지 않는다. 여러 저장소의 구현/부모 gitlink와 요청된 설계 파일의 커밋 경계를 명시한다.

구현 단계는 한 번에 하나만 활성화한다. 단계마다 다음 순서를 지킨다.

1. 이전 단계 goal·선택 필수 게이트·후보 커밋 증거와 현재 진입 조건을 확인한다.
2. 승인된 작업 정의만 구현하고 선택한 검증을 실제 실행한다.
3. 조건별 pass/fail/not_run/not_applicable을 판정한다. 비해당은 근거를 남기고 필수 게이트에서 제외한다.
4. 상태·다음 행동을 갱신하고 정확한 단계 변경만 커밋한다. 여러 단계 결과를 한 커밋에 합치지 않는다.
5. 실제 snapshot의 경로·내용·검증 증거를 대조한다. 해당 단계에서 요구하는 snapshot 검증을 수행한다.
6. **단계 goal 달성 + 남은 필수 게이트 전부 pass + 단계 커밋 확인** 이후에만 다음 단계로 전환한다.

fail 또는 not_run이면 전환하지 않는다. 대상 정책의 실패 처리/예산을 따른다. 범위·보장·필수 성공 조건을 실질적으로 바꾸면 설계와 승인을 재확정한다. Core 규칙 의미 변경의 독립 감사와 route 변경의 별도 의미 검증 등 대상 정책이 요구하는 게이트를 빠뜨리지 않는다. 설치·push·원격 변경은 스킬 호출이나 단계별 로컬 커밋 위임에 포함하지 않는다.

## 6. 정리, 보고, 종료

1. 승인한 각 조건과 개선 결과를 대조한다. 필요한 상태 문서에는 현재 상태만 남기고 완료 과정은 Git 이력이 소유하게 한다.
2. 작업 전용 설계·단계 설계·기타 임시 산출물 등 **이번에 만든, 정확한 정리 승인을 받은 임시 자원만** 제거한다. 고유 근거는 승인된 정본 또는 commit에 보존하고 활성 링크를 갱신한다. 기존 설계/사용자 파일/다른 작업 자원을 포함하지 않는다.
3. 설계 삭제 등 추적 파일 정리를 별도의 정리 커밋으로 기록한다. 이미 만든 설계·단계 커밋 이력을 삭제하거나 squash/reset해서 없애지 않는다. 최종 트리에 개선 결과와 필요한 활성 정본만 남긴다.
4. Core·extension·부모 gitlink를 포함해 실제 상태를 승인된 기준과 대조한다. 이번 개선이 만든 미커밋 변경·미해결 충돌·실패 검증·미결 결정이 있으면 종료를 보류한다. §4에서 보존하며 계속하기로 한 기존 변경은 존재만으로 종료를 막지 않으며, 이번 작업이 덮어쓰거나 개선 커밋에 포함하지 않았는지 확인한다. 격리 워크트리는 clean이어야 한다.
5. 개선 결과는 채팅으로 보고한다. 보고서 파일이나 검증 로그를 종료의 필수 산출물로 생성·영구 보존하지 않는다. 사용자가 파일 저장을 명시적으로 요청한 경우에만 해당 범위의 파일을 남기며, 보고서가 없다는 이유로 작업·재개·종료를 막지 않는다. 재개에 필요한 현재 상태는 기존 상태 소유자에 최소한으로 남기고, 실제 변경과 복구 근거는 작업 파일·규칙·Git 이력을 사용한다.
6. 채팅 보고에는 §4의 후보별 기본 항목과 실제 처리 결과를 유지하며 관련 commit 식별자, 수행한 검사와 미검증 한계, 임시 자원 정리 및 최종 Git 상태를 간결하게 담는다. 사용자가 요청해 보존한 파일이 있을 때만 그 위치를 안내한다. 보고 후 저장소 상태도 재확인한다.
7. 이번 호출이 만든 개선 브랜치·워크트리가 있으면 **종료 표시 전에 정리한다**. 생성 시 기록과 실제 대상·현재 사용자를 대조해 기존/공유/다른 Agent의 자원을 제외한다. 검증된 개선과 필요한 현재 상태가 승인된 기준 브랜치에 병합되고 필요한 commit이 그 브랜치에서 복구 가능한지 먼저 확인한다. 원래 작업 폴더를 전환하지 말고 필요한 경우 별도 통합 워크트리에서 병합한다. 기준 브랜치가 다른 작업에서 사용 중이거나 새 변경과 충돌하면 그 작업을 건드리지 않고 병합 방법을 확인한다.
   - 제거할 워크트리의 staged·unstaged·untracked·ignored 고유 자료와 관련 submodule을 확인하고 보존할 근거가 남지 않았음을 확인한다. 이번 호출이 만든 통합 워크트리도 같은 정리 대상이다.
   - 생성 때 사용자에게 제시하고 승인받은 정확한 종료 정리 범위를 재사용한다. 승인되지 않은 대상·새 사용자 변경·다른 Agent 사용·미병합 commit이 발견되면 해당 정리만 보류하고 필요한 결정을 받는다. 강제 삭제로 우회하지 않는다.
   - 작업 폴더 밖의 실행 맥락에서 워크트리를 정상 제거하거나 관리 도구로 보관 처리한 뒤, 다른 워크트리에 체크아웃되지 않았고 병합된 이번 개선 브랜치만 안전 삭제한다. 기존 기준 브랜치(main 등)와 원래 워크트리는 삭제하지 않는다. 원격 브랜치 삭제는 별도 승인 대상이다.
   - 파일 보존을 요청받은 산출물이 있으면 임시 워크트리에만 남지 않도록 승인된 보존 위치를 확인한다. 실제 워크트리 등록 및 개선 브랜치 부재, 기준 브랜치의 결과 보존, 설치 스킬 등 외부 정본 반영과 원래 작업 보존을 확인한다. 정리 결과를 최종 응답에 보고한다. 정리 미완료는 종료 완료로 표시하지 않는다.
8. 승인된 개선·정리·최종 채팅 보고가 모두 끝났을 때만 최종 응답의 **맨 마지막 줄**에 다음 Markdown을 출력한다. 이후 문장·링크·질문을 붙이지 않는다.
