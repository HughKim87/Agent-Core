# 세션 종료

- 목적: 호출된 세션의 검증된 경험에서 재사용 가치가 있는 개선만 선별하고 승인된 개선과 보고를 마친다.
- 읽는 시점: 사용자가 이 스킬을 직접 선택하거나 $session-close로 호출했을 때만.
- 책임: 사용자가 대상·개선 범위·보류를 결정하고 에이전트가 분석·설계·검증·커밋·정리를 수행한다.
- 상태: 직접 호출 전용 스킬.
- 관련 권위: 현재 사용자 지시, 대상 저장소의 진입 정책·Core 정책·소비 정책과 현재 행동에 route된 규칙.

## 호출 경계

agents/openai.yaml의 allow_implicit_invocation: false를 유지한다. 별도의 트리거 단어를 등록하지 않는다. “세션 종료”, “끝내자”, 작업 완료, 핸드오프 요청으로 자동 실행하지 않는다. 이 스킬을 생성·수정하는 요청도 종료 실행이 아니다.

스킬 호출은 분석과 승인 절차의 시작이며 개선 전체의 승인이 아니다. 대기·차단·부분 완료 상태에서는 종료 문구를 표시하지 않는다.

## 1. 매 호출마다 작업 대상 확인

1. 호출된 세션을 분석 원본으로 고정한다. 실제 관측한 작업·교정·실패·성공·검증 한계를 검토한다. 접근 가능한 기록이 부족하면 부족한 근거를 표시하고 내용을 만들어내지 않는다. 다른 세션을 임의로 수집하지 않는다.
2. 현재 저장소의 진입 포인터가 요구한 파일을 지정 순서대로 끝까지 읽는다. 대상 식별에 필요한 읽기 전용 Git 정보만 확인한다.
3. **매 호출마다** 본격 분석·설계·변경 전에 “이번 개선은 어느 브랜치에서 진행할까요? `main`을 권장합니다.”라고 묻고 답을 기다린다. 선택지는 `main (권장)`을 첫 번째로, 확인된 현재 브랜치가 main과 다르면 그 브랜치를 다음으로 제시하고 다른 브랜치도 직접 지정할 수 있게 한다. 각 후보의 저장소·워크트리 절대 경로·실제 브랜치·역할을 함께 표시한다. `main` 권장은 자동 선택·생성·전환의 승인이 아니며 이전 호출의 선택, 현재 체크아웃, 질문 UI의 미제출 기본값을 답으로 간주하지 않는다. main이 없거나 정책상 선택할 수 없으면 그 사실과 허용 후보를 표시하고 main을 임의 생성하거나 정책을 우회하지 않는다. Core와 extension의 구현 대상이 서로 다른 저장소라면 한 질문에 저장소별 선택을 묶어 확인한다. 사용자 답에 필요한 생성·전환과 정확한 대상이 포함되어 있으면 그 승인으로 진행하고, 포함되지 않은 생성·전환만 추가 확인한다.
4. 선택된 대상의 정책을 읽고 실제 저장소 루트·브랜치·HEAD·워크트리·submodule 경계를 확인한다. host의 Core는 읽기 전용이며 Core 구현에는 별도로 확인된 maintainer 대상이 필요하다. Core 분석·제안 문서만 작성하는 경우에는 Core 구현용 브랜치 선택이나 maintainer 대상 확보를 선행 조건으로 요구하지 않는다. 정책상 브랜치 제한을 우회하지 않는다.
5. Core와 extension의 실제 소유 경로 및 목적·공개 계약을 확인한다. extension을 무조건 consumer나 experimental로 추정하지 않는다. 식별되지 않으면 사용자에게 정확한 저장소/경로를 물어 확정한다.

질문 도구가 비동기이면 답이 올 때까지 대상에 의존한 작업을 실행하지 않는다. 시간이 지난 것을 동의로 간주하지 않는다.

## 2. Local change 정지 게이트

대상 확정 뒤 **본격 분석 전**, 각 대상 저장소와 관련 submodule에서 staged·unstaged·untracked·충돌·gitlink 변경을 읽기 전용으로 확인한다. ignored 파일도 확인 가능한 경로 메타데이터로 작업 전용/기존 사용자 자원을 구분하되 보호 경로를 열거하거나 비밀 내용을 읽지 않는다. 상태 조회 실패를 clean으로 간주하지 않는다.

local change가 하나라도 있으면 **그 이후 작업을 중단**한다. 경로·변경 종류·저장소를 요약하고 사용자가 그 변경을 어떻게 처리할지 묻는다. 승인 없이 commit·stash·reset·clean·삭제·이동·checkout하지 않는다. 기존 변경을 개선 커밋에 섞지 않는다.

사용자가 직접 정리하거나 정확한 처리 범위를 승인하면 그 결정만 수행하고 모든 대상의 상태를 다시 확인한다. 변경을 그대로 남겨둔 채 개선을 시작하지 않는다. 별도의 깨끗한 대상 선택도 사용자에게 다시 확인한다. 조회 권한이 없으면 확인 불가 사실과 필요한 결정을 보고한다.

진행 중 새 무관한 변경이나 사용자 변경을 발견해도 같은 정지 게이트를 적용한다. 이번 승인된 단계가 만든 예상 변경은 단계 검증·커밋 절차로 처리하며 기존 local change와 혼동하지 않는다. 체크아웃 변경과 각 Git 쓰기 직전 대상 동일성을 재확인한다.

## 3. 목적에 맞는 개선 후보 선별

깨끗한 대상이 확인된 뒤 세션 근거와 현재 파일을 대조한다. **Core 개선 가능성도 매 호출 기본 분석 범위에 포함한다.** Extension 개선만 발견되거나 Core가 읽기 전용이어도 접근 가능한 Core 정책·규칙과 세션 근거를 함께 대조한다. Core 자료에 접근할 수 없으면 분석 미실시와 필요한 자료를 표시하며 “개선 없음”으로 판정하지 않는다. 모든 관찰을 규칙으로 만들지 않는다. 일회성 취향, 미검증 실패, 이미 해결된 중복 문제를 구분한다.

후보를 쓰기 전에 원인을 `rule_gap`(기존 문구대로 실행해도 계약을 충족하지 못하는 반례), `execution_gap`(충분한 기존 규칙의 실행·검증 누락), `project_requirement`(해당 프로젝트의 요구), `insufficient_evidence`(원인·소유권 미확인)로 분류한다. 적용 소유자와 기존 규칙의 충분성을 먼저 대조하고, 문구 변경으로 달라질 행동을 설명한다. `execution_gap`은 실행 절차·검증을 보강하고, `project_requirement`는 프로젝트 소유자에서 처리하며, `insufficient_evidence`는 확인하거나 보류한다. `rule_gap`일 때만 실제 반례를 해결하는 최소 소유자 수정을 제안한다.

일반화할 수 있는 원칙이라는 판단과 새 규칙 문구가 필요하다는 판단을 구분한다. 기존 규칙으로 같은 행동을 도출할 수 있으면 중복 문구를 추가하지 않는다. 소유 경로의 쓰기 가능 여부는 소유권 판단을 바꾸지 않으며, 접근할 수 없으면 필요한 대상·결정을 보고한다.

- **Core**: 대상의 헌장·보장·포함 기준과 현재 일반화 규칙을 따른다. 도메인 중립 계약의 직접 귀결 또는 독립된 실제 소비 맥락의 반복 근거를 제시한다. 합성 fixture를 실제 반복 사례로 세지 않는다. 프로젝트 경로·데이터·운영 상태는 Core에 흡수하지 않는다.
- **Extension**: 식별한 extension의 의도·선택 계층 여부·기능 계약에 맞는 반복 품질 향상인지 판정한다. 특정 도메인에 적합한 재사용성도 인정하되 Core 보장으로 확대하지 않는다. extension의 필수화나 Core 의존 확대는 별도 변경 범위다.
- 먼저 기존 소유자 보강 가능성을 판단한다. 새 소유자는 구별되는 책임이 있을 때만 제안한다. Core 공통 부분과 extension 적용 부분이 섞이면 분리한다.

후보마다 ID, 관측 근거, 현재 결함/반복 품질 영향, 의도와의 연결, 소유자·정확한 예상 경로, 적용 조건·near-miss, 일반화 근거, 최소 수정, 검증 방법을 짧게 보고한다. 추론·가정·미검증을 관측 사실과 구분한다.

| 분류 | 판단 |
|---|---|
| 꼭 필요한 개선 | 근거 있는 현재 계약·보장 위반, 반복 결과의 정확성/복구/안전/완료 검증을 훼손하는 결함. 왜 지금 필요한지와 미개선 영향을 제시한다 |
| 꼭 필요하지 않은 개선 | 편의·표현·최적화·장래 가능성 또는 현재 보장에 영향이 없는 선택적 품질 향상 |
| 근거 부족 | 필요성이나 소유권을 판단할 근거가 부족함. 확인할 질문 또는 보류 사유를 표시한다 |

일반화 게이트를 통과하지 못한 후보를 “필요”라는 이유로 Core에 넣지 않는다.

## 4. 분류 보고와 개선 승인

Core 개선 후보가 하나라도 있으면 **구현 승인 요청 전에 Core 개선 검토 문서를 작성하고 링크와 핵심 판단을 보고한다.** 보류·근거 부족 후보도 포함하며 문서 작성은 Core 수정 승인이 아니다. 문서는 작업 소유 Consumer의 정책상 허용된 내부 산출물 경로에 기본 보존하고, Core 내부에는 쓰지 않는다. 외부 보존은 사용자가 지정하거나 승인한 경우에만 사용한다. 문서에는 목적·읽는 시점·책임·상태·관련 권위, 세션 근거와 접근 한계, 후보별 ID·원인 분류·필요성·기존 소유자/예상 경로·일반화 판정·적용 조건/near-miss·최소 수정·검증 방법·미개선 영향, 승인/보류/거절 상태를 담는다. 아직 결정받지 않은 후보는 승인 대기로 표시한다. 접근 불가나 일반화 근거 부족을 숨기거나 통과로 기록하지 않는다. Core 후보가 없으면 문서를 억지로 만들지 않고 채팅에 분석 범위와 “Core 개선 후보 없음”이라는 판단 근거를 보고한다.

- 꼭 필요한 후보도 자동 구현하지 않는다. 정확한 대상·변경 범위·검증·단계별 커밋·임시 자원 정리 범위를 제시해 사용자 동의를 받는다.
- 꼭 필요하지 않은 후보는 관련 이슈를 보고하고 각 후보의 **진행 또는 보류**를 확인한다. 여기서 이슈 보고는 채팅 내 문제 설명이며 원격 이슈 생성을 뜻하지 않는다.
- 사용자가 승인·보류·거절한 ID를 구분한다. 응답이 없거나 모호하면 해당 후보를 진행하지 않는다. 근거 부족 후보는 확인하거나 사용자의 보류 결정을 받는다.
- 필요한 후보를 사용자가 거절하거나 보류해도 몰래 구현하지 않는다. 남는 위험을 보고하고 그 결정이 이번 종료에 포함됨을 명확히 한다.
- 모든 진행 후보와 보류 처분이 확정되면 승인된 후보만 아래 단계로 진행한다. 진행 후보가 없으면 설계·빈 커밋을 만들지 않고 정리/보고로 간다.

## 5. 설계와 단계별 실행

개선 시작 직전에 대상 정책 라우터에서 **최신 단계별 작업 규칙과 버전 관리 규칙을 다시 확인**한다. 같은 논리 작업에서 이미 읽은 규칙은 읽기 이력을 존중하되 적용 절차를 다시 대조하고, 파일 변경 시 변경된 정본을 읽는다. 규칙을 찾지 못하거나 승인 경계가 충돌하면 추정 실행하지 않고 필요한 결정을 받는다.

[설계 항목](references/design.md)을 읽고 작업 전용 설계를 작성한다. 전체 설계·현재 단계·현재 상태의 책임을 분리하며 기존 정책 본문을 복제하지 않는다. 설계는 승인된 개선 ID, 정확한 대상, 작업 정의, 단계별 진입·검증·goal 성공·전환·커밋과 복구 조건을 갖는다.

설계 완성 뒤 단계 구성·성공 조건·정확한 임시 경로와 정리·보고 위치를 사용자에게 제시해 기존 승인으로 충족되는지 확인한다. 승인 범위를 넘는 결정은 답을 기다린다.

**0단계**: 승인된 설계문서를 해당 설계 소유 저장소 Git에 정확한 경로로 커밋한다. 실제 commit snapshot과 설계 내용의 일치를 확인하고 그 후에만 구현한다. Core 자체에 consumer 현재 상태를 만들지 않는다. 여러 저장소의 설계/구현/부모 gitlink 커밋 경계를 명시한다.

구현 단계는 한 번에 하나만 활성화한다. 단계마다 다음 순서를 지킨다.

1. 이전 단계 goal·선택 필수 게이트·후보 커밋 증거와 현재 진입 조건을 확인한다.
2. 승인된 작업 정의만 구현하고 선택한 검증을 실제 실행한다.
3. 조건별 pass/fail/not_run/not_applicable을 판정한다. 비해당은 근거를 남기고 필수 게이트에서 제외한다.
4. 상태·다음 행동을 갱신하고 정확한 단계 변경만 커밋한다. 여러 단계 결과를 한 커밋에 합치지 않는다.
5. 실제 snapshot의 경로·내용·검증 증거를 대조한다. 해당 단계에서 요구하는 snapshot 검증을 수행한다.
6. **단계 goal 달성 + 남은 필수 게이트 전부 pass + 단계 커밋 확인** 이후에만 다음 단계로 전환한다.

fail 또는 not_run이면 전환하지 않는다. 대상 정책의 실패 처리/예산을 따른다. 범위·보장·필수 성공 조건을 실질적으로 바꾸면 설계와 승인을 재확정한다. Core 규칙 의미 변경의 독립 감사와 route 변경의 별도 의미 검증 등 대상 정책이 요구하는 게이트를 빠뜨리지 않는다. 설치·push·원격 변경은 스킬 호출이나 단계별 로컬 커밋 위임에 포함하지 않는다.

## 6. 정리, 보고, 종료

1. 승인한 각 조건과 개선 결과를 대조한다. 필요한 상태 문서에는 현재 상태만 남기고 완료 과정은 Git 이력이 소유하게 한다.
2. 작업 전용 설계·단계 설계·기타 임시 산출물 등 **이번에 만든, 정확한 정리 승인을 받은 임시 자원만** 제거한다. 고유 근거는 승인된 정본 또는 commit에 보존하고 활성 링크를 갱신한다. 기존 설계/사용자 파일/다른 작업 자원을 포함하지 않는다.
3. 설계 삭제 등 추적 파일 정리를 별도의 정리 커밋으로 기록한다. 0단계 및 단계 커밋 이력을 삭제하거나 squash/reset해서 없애지 않는다. 최종 트리에 개선 결과와 필요한 활성 정본만 남긴다.
4. Core·extension·부모 gitlink를 포함해 승인된 모든 저장소가 예상 브랜치에서 clean인지 확인한다. 남은 local change, 실패 검증, 미결 결정이 있으면 종료를 보류한다.
5. 개선 보고 문서를 만든다. 기본 위치는 작업 소유 Consumer의 정책상 허용된 내부 산출물 경로로 잡고, 저장소 밖 보존은 사용자가 지정하거나 승인한 경우에만 사용한다. Git 추적·ignore·보고 커밋 여부는 대상 정책과 사용자 승인에 따라 설계 때 확정하여 최종 clean 조건과 맞춘다. Core 개선 검토 문서가 있으면 그 문서의 후보별 결정과 처리 결과를 갱신하고 최종 보고에서 링크한다. 보고와 Core 개선 검토 문서는 임시 자원이 아니며 보존 위치를 안내한다.
6. 보고에는 목적·읽는 시점·책임·상태·관련 권위, 개선 전후 동작, 후보별 승인/보류/거절과 남은 위험, Core/extension 소유 판단, 단계별 commit 링크/식별자, 실제 검사와 not_run·한계, 임시 자원 정리 및 최종 Git 상태를 담는다. 정책이 금지하는 Core revision 중복 정본은 만들지 않는다. 보고 문서 링크와 핵심 결과를 사용자에게 전달하고 보고 후 저장소 상태도 재확인한다.
7. 승인된 개선·정리·최종 보고가 모두 끝났을 때만 최종 응답의 **맨 마지막 줄**에 다음 Markdown을 출력한다. 이후 문장·링크·질문을 붙이지 않는다.
