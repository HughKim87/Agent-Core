# 공통스킬 설치

- 목적: Core의 공통 설치 대상으로 선언된 스킬만 PC 개인용 설치 위치에 관리한다.
- 읽는 시점: Core 연결 프로젝트에서 공통 스킬의 설치·갱신을 요청했을 때.
- 책임: 프로젝트는 설치 입력과 검증을, 사용자 환경은 실제 설치본과 영수증을 소유한다.
- 상태: 프로젝트 스킬. 개인용 공통 설치 대상으로 자신을 포함하지 않는다.
- 관련 권위: 선택한 Core의 [공개 스킬 계약](../../../docs/COMPATIBILITY.md#3b-공통-workflow-진입-계약), 프로젝트 정책과 현재 설치 요청.

## 입력과 승인

프로젝트 진입 정책을 읽고 소비 계약의 실제 Core root와 역할을 확인한다. 프로젝트·Core를 새로 만들거나 내려받아 이 스킬을 실행하지 않는다. 다른 작업의 로컬 변경을 처리하지 않으며 Core는 읽기 입력으로 유지한다. Host에서는 공개 계약이 요구하는 전후 Core 불변을 증명하고, 시작 기준을 증명할 수 없으면 개인용 설치 전에 중단한다.

공통 스킬 설치 요청은 아래 관리 목록의 신규 설치·수정되지 않은 구버전 교체·교체된 구버전 정리를 함께 위임한다. 스킬이 자동 선택됐다는 이유만으로 설치 승인이 생기지 않는다. 제작·점검 요청은 읽기와 계획만 수행한다. 설치할 에이전트와 **실제 지원되는 사용자 범위 스킬 root의 절대 경로**를 확인해 알린다. 선택 근거가 없으면 도구·경로만 묻고, 확정된 범위의 파일마다 승인을 반복하지 않는다. 프로젝트 native 폴더·Core·보호 경로와 겹치는 목적지는 사용하지 않는다. 관리자·다른 사용자·원격 환경은 이번 PC 사용자 설치로 추정하지 않는다.

설치 root는 각 제품의 현재 공식 문서·현재 설치 경로를 대조해 선택한다. Codex와 Claude의 경로·동명 선택 우선순위를 같다고 가정하지 않는다. 개인 파일 전체를 검색하지 않고 선언된 공통 이름과 설치 영수증만 조사한다. 자격 증명·개인 키를 읽거나 새 패키지·환경 설정을 추가하지 않는다.

## 계획과 실행

[관리 도구](scripts/manage_common_skills.py)는 표준 Python만 사용한다. Core 안에 cache·임시 파일을 쓰지 않도록 `python -B`로 호출하고 작업 위치는 프로젝트 root로 둔다. `--core-root`, `--target-root`, `--agent codex|claude`를 명시한다. 기본 호출은 읽기 전용 계획이다. `skills/INSTALLATION.json`의 `common` 항목만 읽으며 분류 누락·오류는 추정 설치하지 않는다.

계획 결과의 대상·버전·행동과 `plan_id`를 보고한다. 승인된 설치 요청과 도구·경로 범위 안이면 그 계획에 `--apply --plan-id <계획 ID>`를 추가해 실행한다. 계획 이후 입력·목적지가 달라지면 도구가 거부하므로 새 계획과 범위를 대조한다. 검사할 수 없었던 경로를 미설치나 정상으로 처리하지 않는다.

- `install`: 미설치 → 독립 패키지 설치.
- `update`: 동일 공급자의 이전 버전이고 영수증과 실제 파일이 일치 → 새 패키지 검증 후 교체, 구버전 관리 파일 제거.
- `current`: 버전과 내용 동일 → 쓰지 않음.
- `newer`: 설치본이 더 최신 → 보존, 자동 downgrade 없음.
- `conflict`: 수동 수정·다른 공급자·미등록 파일·동일 버전 내용 차이·경로 이상 → 보존하고 해당 항목만 결정 요청.

정상 항목은 진행하고 충돌만 보류한다. 도구의 `--apply`도 충돌을 덮어쓰지 않는다. 충돌 해결은 설치기의 우회 옵션이 아니라 고유 내용 보존과 정확한 대상의 별도 사용자 결정으로 처리한다. 최신 목록에서 사라진 이름은 자동 삭제하지 않는다. 이 버전은 개명·폐기 자동 이전을 제공하지 않는다.

설치 영수증은 공급자·스킬·에이전트·스킬 버전·설치 파일 해시를 기록하며 Core gitlink의 대체 정본이나 권한 증명이 아니다. 개인 설치 폴더만 가리키며 Core 전체를 복사하지 않는다. 새 설치본은 프로젝트 Core가 없어도 필요한 본문·자료를 읽을 수 있어야 한다.

## 실패·검증·보고

도구는 목적지 lock을 배타적으로 사용하고 새 패키지를 준비·검증한 뒤 구버전을 옮겨 교체한다. 교체 실패 시 기존 설치본 복원을 시도한다. 활성화 후 검증이 실패하면 새 디렉터리가 여전히 이번 payload와 정확히 일치하는 경우에만 격리·복원하고, 외부 변경이나 읽기 실패로 확인할 수 없으면 두 설치본을 보존한다. 부분 쓰기·복원·구버전 정리가 실패하면 경로·활성 상태·복원·정리 결과를 구조적으로 보고한다. 잔여물이 있으면 사용자 root의 스킬별 recovery 기록으로 다음 계획을 충돌 처리하며 정상 완료로 숨기지 않는다. OS 강제 중단은 이 기록도 남기지 못할 수 있으므로 기존 lock·미완료 자원을 임의 제거하거나 재설치하지 않는다. 새 패키지 준비가 실패했다고 기존 설치본부터 삭제하지 않는다.

실행 뒤 실제 설치 파일과 영수증 해시, 프로젝트 Core와 무관한 상대 자료 연결을 확인한다. 구조 검사·모의 설치와 실제 제품의 발견·선택·호출 검증을 구분한다. 발견 여부를 확인할 때 분석 스킬의 업무를 무관한 세션에 자동 실행하지 않는다. 실제 선택 출처를 확인하지 못했으면 제품 검증은 `not_run`으로 보고한다.

도구·절대 설치 위치·스킬별 설치/갱신/유지/보류·구버전 정리·검증과 한계를 보고한다. Git stage·commit·push, 프로젝트 스킬 제거, 환경 전체 동기화는 포함하지 않는다.
