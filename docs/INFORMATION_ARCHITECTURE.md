# 정보 유형과 단일 정본 소유 구조

- 목적: 활성 정보의 유형을 구분하고 각 유형의 단일 정본 위치와 갱신 책임을 소유한다.
- 읽는 시점: 새 문서를 만들지 판단할 때, 어떤 사실이 어디에 있어야 하는지 판단할 때, 중복 정본을 검사할 때.
- 책임: 사용자가 유형·위치의 추가·병합·이동을 승인하고 프로젝트 에이전트가 배치를 유지한다.
- 상태: 활성 정본. 현재 문서 역할, 배치와 수명주기 반영.
- 관련 권위: [Core 헌장](CHARTER.md), [계층과 의존 방향](ARCHITECTURE.md).

---

## 1. 원칙

- 모든 활성 사실은 정본이 정확히 하나다. 다른 문서는 링크하거나 결정론적으로 파생한다.
- 정본은 경로와 책임으로 판별할 수 있어야 한다. 내용을 읽어야만 정본인지 알 수 있으면 배치가 잘못된 것이다.
- 현재 상태와 완료 이력은 서로 다른 유형이다. 섞으면 시작 문맥이 무한히 커진다.
- 새 문서는 기존 소유자가 그 지속적 목적을 충족하지 못할 때만 만든다.
- 실제 파일이 필요하기 전에는 빈 미래 디렉터리를 만들지 않는다.

## 2. 정보 유형과 정본 위치

아래 선언이 정책·상태·진입 포인터의 기계 판독 소유자다. 사람용 절 제목은 역할 판정에 사용하지 않는다.

<!-- core-document-roles:v1 -->
```json
{
  "policy": "PROJECT_RULES.md",
  "state": "SESSION_HANDOFF.md",
  "entry_pointers": [
    "AGENTS.md",
    "CLAUDE.md"
  ]
}
```

| 정보 유형 | 정본 위치 | 계층 | 갱신 책임 | 갱신 시점 |
|---|---|---|---|---|
| 상시 정책 | 루트 정책 문서 | L1 | 사용자 승인, 에이전트 유지 | 권한·안전 경계가 바뀔 때 |
| 에이전트 진입 | 루트 진입 파일 | L1 | 에이전트 | 지원 에이전트가 늘거나 줄 때 |
| 규칙 라우팅 | 루트 정책 문서의 라우팅 표 | L1 | 에이전트 | 활성 규칙이 추가·개명·폐기될 때 |
| 조건부 규칙 | `rules/` | L2 | 에이전트, core 변경 승인 필요 | 해당 행동의 절차가 바뀔 때 |
| 계약·설계 | `docs/` | L3 | 에이전트, 범위 변경은 사용자 승인 | 책임 범위가 바뀔 때 |
| 현재 상태 | `SESSION_HANDOFF.md` | L3 | 에이전트 | 검증된 상태나 첫 다음 행동이 바뀔 때 |
| 완료된 전체 구축 설계 | `AGENT_CORE_BUILD_BLUEPRINT.md` | L3 | 사용자 승인 | 최초 구축의 역사적 기준을 대체할 때 |
| 단계 작업 설계 | `SESSION_HANDOFF.md`가 가리키는 활성 설계 | L3 | 에이전트 | 현재 단계가 전환될 때 |
| 확정된 결정 | 그 결정이 규율하는 계약 문서 | L3 | 에이전트 | 결정이 대체될 때 |
| 실패 예방 | 해당 행동의 기존 규칙 또는 결함 주입 테스트 | L2·L5 | 에이전트 | 원인·해결·검증이 확인될 때 |
| 예외 진단 | `failures/`의 최소 문서 | L4 | 에이전트, 삭제·이동은 사용자 승인 | 현재 규칙에서 도출할 수 없는 비자명 정보가 남을 때만 |
| 파생 artifact | 각 artifact의 선언된 대상 경로 | L5 | 재생성 도구 | 인간 정본이 바뀔 때 |
| 완료 이력 | Git 커밋 | — | Git | 단계 완료 시 |
| 실행 데이터 | 추적하지 않는 실행 경로 | L7 | Runtime | 해당 없음 |

## 3. 디렉터리 구조

저장소 루트가 곧 Core의 내용이다. Core 내용을 다시 하위 폴더로 감싸지 않는다.

```
/
├─ README.md                        사용자 진입. 파생 표현
├─ AGENT_CORE_BUILD_BLUEPRINT.md    전체 구축 설계
├─ SESSION_HANDOFF.md               현재 상태 단일 정본
├─ docs/                            계약과 설계
│   ├─ CHARTER.md                   목적·보장·비보장·판정 기준
│   ├─ KERNEL_SCOPE.md              포함·제외 분류
│   ├─ ARCHITECTURE.md              계층과 의존 방향
│   └─ INFORMATION_ARCHITECTURE.md  이 문서
├─ rules/                           조건부 규칙
├─ failures/                        선택적 최소 진단 정보
├─ schemas/                         기계 판독 구조 계약     (필요 시)
├─ src/                             검증 도구와 기반 원시
├─ tests/                           회귀 검증
├─ experimental/                    격리된 실험 Runtime     (필요 시)
└─ tmp/                             한시 참고 자료. 정본 아님
```

루트의 에이전트 진입 파일, 정책과 상태 문서의 정확한 경로는 §2의 기계 판독 선언이 소유한다.

선택 디렉터리는 실제 소유 정보가 생길 때만 만든다. 빈 미래 구조는 만들지 않는다.

## 4. 복제 금지 규칙

| 복제되기 쉬운 사실 | 정본 | 다른 문서의 처리 |
|---|---|---|
| 현재 단계와 첫 다음 행동 | `SESSION_HANDOFF.md` | 링크만 한다 |
| 단계별 성공 조건 | 전체 구축 설계 | 링크만 한다 |
| 완료된 단계의 상세 과정 | Git 커밋 | 활성 문서에 남기지 않는다 |
| Core의 목적과 판정 기준 | `docs/CHARTER.md` | 링크만 한다 |
| 계층과 의존 방향 | `docs/ARCHITECTURE.md` | 링크만 한다 |
| 구성요소의 등급 | `docs/KERNEL_SCOPE.md` | 링크만 한다 |
| 지원 런타임 버전 | `docs/COMPATIBILITY.md`의 기계 판독 선언 | 링크만 한다 |
| Git 상태와 파일 수 | 실행 조회 | 문서에 수치를 적지 않는다 |

마지막 행이 특히 중요하다. 참고 구현의 현재 상태 문서에는 추적 파일 수와 같은 동적 수치가 들어 있어 실제와 어긋나기 쉬웠다. 동적 사실은 명령으로 조회하고 문서에 고정하지 않는다.

## 5. 현재 상태와 완료 이력의 분리

| 구분 | 포함 | 불포함 |
|---|---|---|
| 현재 상태 | 현재 단계, 활성 설계, 차단, 승인 상태, 첫 다음 행동 | 완료된 단계의 과정, 과거 판정 근거, 동적 Git 수치 |
| 완료 이력 | 무엇을 왜 바꿨고 어떤 게이트를 어떻게 통과했는지 | 현재 무엇을 해야 하는지 |

단계가 완료되면 그 상세는 커밋 메시지에 남기고 현재 상태 문서에서 제거한다. 이 규칙이 없으면 시작 문맥이 단계 수에 비례해 커진다.

### 5.1 문서 상태와 수명주기

| 상태 | 의미 | 현재 사실 갱신 |
|---|---|---|
| 활성 정본 | 현재 판단과 행동을 직접 규율하는 단일 소유자 | 관련 사실이 바뀌면 반드시 갱신 |
| 활성 개요 | 정본을 링크하는 파생 표현 | 링크와 현재 범위만 갱신 |
| 완료 설계 | 실행이 끝난 설계의 역사적 기준 | 현재 활성 설계로 참조하지 않음 |
| 역사적 snapshot | 특정 시점의 평가·보고·증거 | 현재 사실의 정본으로 갱신하지 않음. 오류가 확인되면 정정 주석만 추가 |
| 한시 자료 | 흡수 또는 판단 후 종료할 비정본 | 활성 문서가 정본으로 참조하지 않음 |

- `SESSION_HANDOFF.md`의 활성 설계는 진행 중인 설계만 가리킨다. 완료 설계와 역사적 snapshot을 활성 설계로 지정하지 않는다.
- 사용자가 요청한 평가·보고 문서는 역사적 snapshot으로 보존할 수 있지만 현재 상태와 완료 판정을 소유하지 않는다.
- 완료 설계와 역사적 snapshot은 상태 설명에서 자신이 현재 정본이 아님을 명시한다.
- 파일 삭제·이동은 정확한 대상에 대한 사용자 승인 후 수행한다.

## 6. tmp 디렉터리의 처분

`tmp/`의 문서는 과거 요구사항과 실패 기록이다. 정본이 아니라 한시 참고 자료다.

| 항목 | 처분 |
|---|---|
| 재사용 가능한 실패 예방책 | 해당 규칙·테스트에 흡수한다 |
| 사용자 요구 원문 | `docs/CHARTER.md`가 이미 흡수했다 |
| 결합 실측 데이터 | 별도 승인된 Host 후속 설계의 입력으로만 사용한다 |
| 나머지 | 흡수 완료 후 종료 대상. 삭제는 사용자 승인이 필요하다 |

종료 조건이 충족되기 전까지 `tmp/`는 유지하되 어떤 활성 문서도 이곳을 정본으로 참조하지 않는다.

## 7. 문서 생성 게이트

새 문서를 만들기 전에 순서대로 확인한다.

1. §2의 표에서 그 정보 유형의 기존 정본을 찾는다.
2. 기존 정본이 그 목적을 충족하지 못하는 이유를 한 문장으로 설명한다.
3. 정보 유형과 계층을 각각 하나씩 정한다.
4. 포함 정보와 금지 정보를 정하고 §4의 복제 금지에 걸리지 않는지 확인한다.
5. 갱신 책임과 종료 조건을 정한다.
6. 기존 정본의 갱신으로 충분하면 새 문서를 만들지 않는다.

전체 파일 목록 문서는 만들지 않는다. `README.md`, 정본, Git 검색을 사용한다.

## 8. 최소 문서 설명

새로 만들거나 책임이 바뀌는 유지 문서는 다음을 갖는다.

- 목적
- 읽는 시점
- 책임
- 상태
- 관련 권위

기계 스키마를 강제하지 않는다. 기존 문서가 같은 정보를 명확히 제공하면 변환하지 않는다.

## 9. 검사 가능한 형태의 정본 규칙

| ID | 검사 | 현재 강제 수준 |
|---|---|---|
| O1 | §2의 모든 정보 유형에 존재하는 정본 경로가 정확히 하나 배정되어 있다 | 역할 선언과 단일 상태 정본 검사 |
| O2 | 활성 문서에 §4의 복제 금지 대상이 중복 서술되어 있지 않다 | 사람 의미 감사 |
| O3 | 현재 상태 문서에 완료된 단계의 상세가 누적되어 있지 않다 | 크기 예산 자동 검사 + 사람 의미 감사 |
| O4 | 모든 유지 문서에 §8의 다섯 항목이 있다 | 자동 검사 |
| O5 | 어떤 활성 문서도 `tmp/`를 정본으로 참조하지 않는다 | 자동 링크 검사 |
| O6 | 문서에 동적 수치가 고정 값으로 적혀 있지 않다 | 사람 의미 감사 |

## 10. 이 문서의 한계

- O2·O6과 O3의 의미 판정은 범용 자연어 검사 대신 변경 시 사람 감사에 의존한다. 나머지 구조 계약은 통합 무결성 검사가 강제한다.
- 루트 진입 파일과 정책·상태 문서의 역할은 §2의 선언이 소유한다.
- `SESSION_HANDOFF.md`의 위치와 책임은 이 문서가, 내용 계약과 갱신 절차는 [현재 상태와 세션 인수인계](../rules/handoff.md)가 소유한다.
