# Agent Core 내부 검증 개선 설계

- 목적: 현재 Agent Core의 구현 의도와 구현 상태를 보존하면서, 교차검증에서 확인된 내부 결함을 의존 순서대로 수정하고 독립 Core 완료 판정을 다시 받을 수 있게 한다.
- 읽는 시점: I0~I6 개선의 승인 범위, 단계 의존성과 성공 조건을 역사적으로 확인할 때.
- 책임: 에이전트가 완료된 설계의 의미를 보존하고 사용자가 대체·종료 여부를 결정한다.
- 상태: 완료 설계. I0~I6 종료 후 현재 활성 설계가 아니며 현재 상태는 `STATE.md`가 소유한다.
- 관련 권위: [상시 정책](../POLICY.md), [현재 상태](../STATE.md), [최종 작업 검증](CORE_BUILD_FINAL_VALIDATION.md), [전체 구축 설계](../AGENT_CORE_BUILD_BLUEPRINT.md).

## 1. 작업 의도

현재 Core는 처음부터 다시 만들어야 하는 상태가 아니다. 다음 기반은 이미 존재한다.

- 모든 에이전트가 같은 정책과 현재 상태에 도달하는 진입 구조
- 작업 종류에 따라 필요한 규칙만 읽는 라우팅 구조
- 사용자 승인과 위험 행동의 경계를 정의한 정책
- 대화 없이 작업을 재개하기 위한 현재 상태와 인수인계 구조
- 문서·링크·코드·계층을 확인하는 무결성 검사
- 시작 컨텍스트 구성, 공개 CLI, 통합 게이트
- 실제 자체 운영과 콜드 세션으로 결함을 발견한 경험
- 사용 근거가 부족한 Runtime을 필수 Core에 넣지 않은 최소주의

문제는 기능 부족보다 **검증 결과의 신뢰성**에 있다. 정상 Windows 줄바꿈을 오류로 판단하고, 라우팅 시험 데이터는 실제 의미 판정에 사용되지 않으며, 일부 코드와 문서가 검사 범위 밖에 있다. 이 상태에서는 기능이 존재하더라도 “완료됐다”는 말을 신뢰할 수 없다.

따라서 이 작업은 새 기능 확장이 아니라 다음 결과를 목표로 한다.

> **Core가 자신이 보장한다고 말한 범위를 실제로 검사하고, 검사 통과가 현재 checkout과 clean clone에서 같은 의미를 갖게 한다.**

## 2. 요청사항 해석과 작업 계약

| 계약 항목 | 내용 |
|---|---|
| 원하는 결과 | 현재 구현과 의도를 설명하고, 확인된 문제와 개선 방법을 단계별 구현·검증·성공 게이트로 정의한 독립 실행 가능 설계 |
| 허용 행동 | 저장소 읽기, 개선 설계 문서 생성, 설계 문서 자체 검증 |
| 이번 작업의 제외 범위 | 실제 코드·정책·규칙 수정, 파일 삭제, Git 커밋, Host 연결, Runtime pilot |
| 입력 참조 | 최종 작업 검증, 기존 청사진, 정책·규칙·구조 문서, 현재 구현과 테스트 |
| 보호 경계 | 외부 보고서는 읽기 전용 증거이며 저장소 밖 파일을 수정하지 않는다 |
| 구현 시 사용자 결정 | 정책·헌장 변경 승인, 실패 문서 종료·삭제 승인, 독립 Core 완료 복원 승인 |
| 현재 검증 수준 | 설계 문서의 구조·링크·정합성 검증. 구현 게이트는 `not_run` |

## 3. 기존 프로젝트의 구현 의도

### 3.1 최상위 의도

Agent Core는 AI 모델 자체를 개선하려는 시스템이 아니다. 세션과 에이전트가 바뀔 때마다 규칙·상태·안전 경계·완료 기준을 다시 추측하는 문제를 줄이는 파일 기반 운영 기반이다.

핵심 원칙은 다음과 같다.

1. 시작할 때 같은 정책 정본에 도달한다.
2. 대화 기록 없이 현재 상태와 첫 행동을 복원한다.
3. 위험한 행동은 승인 전에 멈춘다.
4. 완료 주장은 실행한 검증과 연결한다.
5. 같은 실수를 줄이는 예방책을 다음 작업에 재사용한다.
6. 사용 근거가 없는 복잡한 Runtime은 필수 Core에 넣지 않는다.

### 3.2 구성요소별 구현 의도와 현재 구현

| 영역 | 원래 구현 의도 | 현재 구현 |
|---|---|---|
| Agent 진입 | 지원 Agent마다 정책을 복제하지 않고 같은 정본으로 연결 | `AGENTS.md`, `CLAUDE.md`가 `POLICY.md`를 가리킨다 |
| 정책과 라우팅 | 항상 필요한 경계만 먼저 읽고 행동에 맞는 절차만 선택 | `POLICY.md`의 단일 라우팅 표와 `rules/`의 조건부 규칙 |
| 작업 계약 | 목표·범위·제외·검증을 작업 중 유지 | `work-contract`, `staged-work-design`, `core-change-control` 규칙 |
| 현재 상태 | 대화 없이 현재 단계와 첫 행동을 복원 | `STATE.md` 단일 정본과 크기 예산 검사 |
| 문서 소유 | 같은 사실이 여러 문서에서 서로 달라지는 것을 방지 | `docs/INFORMATION_OWNERSHIP.md`와 문서 메타데이터 검사 |
| 실패 처리 | 해결된 실패가 반복되지 않게 예방 지식을 남김 | `rules/failure-records.md`, `failures/` 정본, Git 이력 |
| 무결성 검사 | 문서·링크·JSON·Python·라우팅·계층 결함 탐지 | `src/core_check/integrity.py`의 등록형 검사 |
| 컨텍스트 | 정책·상태·일치 규칙만 선택하고 예산을 강제 | `src/core_check/context.py` |
| 공개 인터페이스 | 소비자가 사용할 최소 명령과 종료 상태 제공 | `verify`, `context`, `gate` CLI |
| 통합 게이트 | preflight부터 회귀 테스트까지 하나의 판정으로 묶음 | `src/core_check/gate.py` |
| 실험 기능 | 검증되지 않은 기능이 시작·검증 경로를 막지 않게 함 | optional 등록 구조, 현재 필수 Runtime 추가 없음 |
| 완료 이력 | 활성 문서를 키우지 않고 복구 지점을 보존 | Stage별 Git 커밋 |

## 4. 현재 문제와 개선 원칙

### 4.1 문제 요약

| 문제 | 현재 영향 | 개선 원칙 |
|---|---|---|
| 정상 CRLF를 후행 공백으로 오인 | Windows 현재 테스트와 clean clone 실패 | 저장소 표준은 LF로 고정하되 검사기는 LF·CRLF를 모두 정상 해석 |
| 라우팅 fixture가 발화문을 사용하지 않음 | route 의미 정확성을 검증하지 못함 | 구조 검사와 Agent 의미 검증을 분리하고 보장 수준을 정확히 명명 |
| 복합 요청 fixture 없음 | 여러 규칙이 동시에 필요한 상황 미검증 | 최소 `composed` 사례 추가 |
| 일부 모듈만 계층 배정 | 미감시 모듈의 경계 위반을 놓침 | 발견된 모든 모듈이 정확히 한 계층을 갖도록 A7 강제 |
| 절 제목으로 정책·상태 문서를 발견 | 제목 변경이 코드 동작을 깨뜨림 | 사람용 제목이 아닌 기계 판독 역할 선언으로 발견 |
| 짧은 루트 문서의 광범위한 헤더 예외 | 일반 문서가 메타데이터 검사를 우회 | 선언된 진입 포인터만 예외 허용 |
| 실패 기록과 규칙·테스트가 예방책을 중복 소유 | 문서와 라우팅 증가 위험 | 예방책은 규칙·테스트가 소유하고 상세 역사는 Git이 소유 |
| Stage 8 체크포인트의 고아 route | 단계별 복구 지점의 독립성 훼손 | 완료 선언 전 커밋된 snapshot 자체를 검증 |
| README·STATE·완료 문서의 상태 불일치 | 다음 세션이 오래된 상태를 복원 | 구현과 게이트를 먼저 고친 뒤 활성 문서를 한 번에 정합화 |

### 4.2 실패 경험 처리 원칙

실패를 모두 별도 문서로 남기고 매 작업에서 검색하는 방식은 채택하지 않는다. 그것은 규칙, 테스트, 실패 문서가 같은 예방책을 중복 소유하게 하고 시작 경로를 무겁게 만든다.

개선 후 책임은 다음처럼 나눈다.

| 정보 | 정본 |
|---|---|
| 현재 지켜야 할 행동 | 해당 `rules/` 문서 |
| 자동으로 막을 수 있는 재발 | 회귀 테스트와 무결성 검사 |
| 현재 미해결 문제 | `STATE.md` |
| 완료된 사건과 수정 과정 | Git 커밋 |
| 규칙·테스트만으로 설명할 수 없는 비자명한 진단 지식 | 예외적으로 유지하는 최소 실패 문서 |

새 실패가 해결되면 다음 순서로 처리한다.

1. 같은 문제가 다시 발생하지 않게 규칙 또는 테스트를 고친다.
2. 예방책이 규칙·테스트에 완전히 표현됐는지 확인한다.
3. 완전히 표현됐다면 별도 실패 문서를 만들지 않는다. 과정은 Git에 남긴다.
4. 환경과 코드 결함을 구분하는 진단처럼 현재 규칙에서 도출할 수 없는 정보만 최소 문서로 남긴다.
5. 실패 문서는 기본 시작 문맥과 일반 작업 라우팅에 넣지 않는다.

즉 개선 목표는 `실패 기록을 더 잘 검색`하는 것이 아니라 **실패 기록이 없어도 예방되는 Core**다.

## 5. 확정 설계 결정

1. 기존 Core를 폐기하거나 전면 재작성하지 않는다.
2. Host 연결과 실제 프로젝트 검증은 내부 완료 복원 이후로 유지한다.
3. 자연어를 결정론적으로 분류하는 새 Runtime을 만들지 않는다.
4. 라우팅의 기계 검증은 구조만 보장하고, 의미 정확성은 독립 Agent 재현이 보장한다.
5. 저장소의 정규 텍스트 형식은 LF로 두되, 검사 입력의 정상 CRLF는 허용한다.
6. 정책·상태·계층 소유자는 기계 판독 선언에서 찾는다. 사람용 절 제목은 계약으로 사용하지 않는다.
7. 발견된 모든 Core 모듈은 정확히 하나의 계층에 배정한다.
8. 해결된 실패의 기본 종착지는 규칙·테스트·Git이다. `failures/`는 필수 지식 저장소가 아니라 예외적 진단 자료가 된다.
9. 과거 Stage 커밋은 다시 쓰지 않는다. Stage 8 결함은 재발 방지 절차로 해결한다.
10. 코드 수정과 검증이 끝나기 전에 완료 문서를 다시 `pass`로 만들지 않는다.

## 6. 단계 의존 관계

```text
I0 완료 상태 정정과 기준선 고정
  ↓
I1 텍스트·줄바꿈·clean clone 복구
  ↓
I2 라우팅 검증 책임 교정
  ↓
I3 계층 배정과 선언 기반 발견
  ↓
I4 실패 지식 최소화
  ↓
I5 단계 snapshot과 활성 문서 정합성
  ↓
I6 통합 재검증과 완료 재판정
```

각 단계는 이전 단계의 필수 게이트가 모두 `pass`일 때만 시작한다. 구현 세션은 `STATE.md`에 활성 단계를 하나만 기록한다.

## 7. 단계별 개선 설계

## I0. 완료 상태 정정과 기준선 고정

### 구현 목표

완료가 무효화된 상태에서 Host 작업이나 새 기능 구현이 시작되지 않게 하고, 이후 개선 결과를 비교할 재현 가능한 기준선을 만든다.

### 구현할 내용

- `STATE.md`의 현재 단계를 `내부 완료 재검증`으로 바꾼다.
- `docs/COMPLETION.md`의 완료 판정을 `재검증 중`으로 표시한다.
- Host 연결은 I6 통과 전까지 차단한다고 명시한다.
- 현재 checkout과 Windows clean clone의 검사 결과를 같은 명령으로 다시 측정한다.
- 실패 수 같은 동적 상세는 활성 상태에 누적하지 않고 Stage 커밋 증거에 남긴다.

### 변경 예상 범위

- `STATE.md`
- `docs/COMPLETION.md`
- 필요 시 `docs/VERIFICATION.md`

### 검증 방법

- 새 세션이 문서만 읽고 현재 상태를 “완료”가 아니라 “재검증 중”으로 설명하는지 확인한다.
- Host 작업이 첫 다음 행동으로 제시되지 않는지 확인한다.
- 기준선 명령과 결과가 재현되는지 확인한다.

### 성공 게이트

- 활성 문서에서 완료와 재검증 중이라는 표현이 충돌하지 않는다.
- 첫 다음 행동이 I1의 정확한 대상과 검증 명령을 가리킨다.
- 구현은 I1 이전에 확장 기능이나 Host 경로를 건드리지 않는다.

### 복구 방법

문서 변경만 되돌린다. 코드와 Git 이력은 변경하지 않는다.

## I1. 텍스트·줄바꿈·clean clone 복구

### 구현 목표

저장소의 정규 줄바꿈과 검사기의 입력 허용 범위를 분리해, 운영체제와 checkout 설정이 달라도 같은 파일 내용을 같은 결과로 판정하게 한다.

### 구현할 내용

- `.gitattributes`에 추적 텍스트의 LF 정규화 정책을 선언한다.
- `check_text_encoding`이 줄 종료 문자 `\r\n`과 `\n`을 후행 공백과 구분하게 수정한다.
- 실제 오류는 줄 종료 직전의 공백과 탭으로 한정한다.
- 테스트 fixture는 의도한 줄바꿈을 `bytes` 또는 명시적 `newline`으로 만든다.
- 정상 LF, 정상 CRLF, LF+후행 공백, CRLF+후행 공백을 각각 시험한다.
- 혼합 줄바꿈은 내용 무결성 실패로 만들지 않는다. 정규화는 Git 정책이 소유한다.

### 변경 예상 범위

- `.gitattributes`
- `src/core_check/integrity.py`
- `tests/test_integrity.py`
- `docs/COMPATIBILITY.md`

### 검증 방법

- 현재 checkout에서 전체 회귀 테스트를 실행한다.
- Windows 임시 clean clone에서 전체 게이트를 실행한다.
- 사용할 수 있는 Python 최소 runtime과 현재 runtime에서 같은 fixture를 실행한다.
- 테스트 실행 전후 작업 트리 digest를 비교한다.

### 성공 게이트

- 정상 LF와 CRLF가 모두 `pass`다.
- LF와 CRLF의 실제 후행 공백은 모두 `fail`이다.
- 현재 checkout의 전체 회귀 테스트가 통과한다.
- Windows clean clone의 통합 게이트가 exit 0이다.
- 게이트가 작업 트리를 바꾸지 않는다.

### 복구 방법

검사기와 fixture 변경을 함께 되돌린다. `.gitattributes`만 단독으로 남기지 않는다.

## I2. 라우팅 검증 책임 교정

### 구현 목표

구조 검사를 자연어 의미 검증으로 과장하지 않고, 실제 Agent가 요청의 행동과 경계를 근거로 올바른 규칙을 선택하는지 별도로 증명한다.

### 구현할 내용

- 현재 `test_rule_routing.py`의 책임을 `라우팅 구조·fixture 위생 검사`로 명확히 바꾼다.
- 테스트 설명과 검증 문서에서 `결정론적 라우팅 정확성` 표현을 제거한다.
- 기존 fixture는 버리지 않고 의미 재현 입력 세트로 사용한다.
- 최소 `composed` 사례를 추가한다. 예: 문서 생성과 커밋을 함께 요청하는 경우.
- 독립 Agent 재현 절차를 `rules/rule-governance.md`에 명확히 정의한다.
- 저장소에는 transcript를 보존하지 않고 runtime, 날짜, 케이스 수, 실패 ID와 요약만 Stage 커밋에 남긴다.
- 자연어 판정 Runtime이나 키워드 분류기는 새로 만들지 않는다.

### 변경 예상 범위

- `tests/test_rule_routing.py`
- `tests/fixtures/rule-routing-intents-v1.json`
- `rules/rule-governance.md`
- `docs/VERIFICATION.md`
- 필요 시 `docs/COMPLETION.md`

### 검증 방법

- 기계 테스트가 링크, 유일성, fixture 구조만 보장한다고 출력하는지 확인한다.
- 모든 기존 의미 fixture와 composed fixture를 대화 맥락 없는 Agent에게 제시한다.
- Agent가 선택한 소유자와 기대·금지 소유자를 비교한다.
- 한 번 실패한 케이스는 trigger 문구를 보강한 뒤 새로운 콜드 세션에서 다시 실행한다.

### 성공 게이트

- 기계 검사가 보장하지 않는 의미 정확성을 `unit-tested`라고 보고하지 않는다.
- 모든 활성 route에 initial·colloquial·mid-task·near-miss 사례가 있다.
- composed 요청에서 필요한 여러 소유자가 함께 선택된다.
- 독립 Agent 재현 결과가 기대·금지 소유자 조건을 충족한다.
- 새 자연어 Runtime과 새 상시 라우터가 생기지 않는다.

### 복구 방법

fixture 의미를 바꾸기 전 버전을 Git으로 복구한다. 규칙 trigger와 fixture 변경은 같은 체크포인트에서 되돌린다.

## I4. 실패 지식 최소화와 예방책 흡수

### 구현 목표

실패 기록·라우팅·검색 데이터를 늘리지 않고, 검증된 실패 경험이 규칙과 테스트에서 자동으로 재발을 막게 한다.

### 사용자 결정 게이트

이 단계는 헌장 G5, L4 실패 지식의 필수성, 기존 실패 문서의 종료 여부를 바꿀 수 있다. 구현 전에 다음 방향을 사용자에게 승인받는다.

> **권장안: G5를 “실패 문서를 검색한다”가 아니라 “검증된 실패가 규칙·검사에 흡수되어 같은 원인의 재발을 줄인다”로 정의한다.**

### 구현할 내용

- `rules/failure-records.md`의 기본 행동을 `새 문서 생성`이 아니라 `기존 규칙·테스트 보강`으로 바꾼다.
- 현재 `failures/` 각 사례를 다음 셋 중 하나로 분류한다.
  - `흡수 후 종료`: 예방책이 규칙·테스트에 완전히 표현됨
  - `최소 유지`: 현재 규칙에서 도출할 수 없는 비자명한 진단 정보가 남음
  - `미해결 이동`: 해결되지 않았으므로 `STATE.md`가 소유
- 흡수 후 종료 대상은 규칙·테스트의 소유자를 먼저 보강한다.
- 종료 대상 삭제는 정확한 목록을 제시하고 사용자 승인을 받은 뒤에만 수행한다.
- 실패 문서를 일반 작업 라우터나 기본 컨텍스트에 추가하지 않는다.
- 별도 작업 유형→실패 문서 매핑 데이터베이스를 만들지 않는다.
- 모든 실패 문서가 종료되면 빈 `failures/`와 색인을 유지하지 않는다.

- 실패 문서를 제거해도 현재 정책 선택, 검증, 복구 판단이 달라지지 않는지 확인한다.

### 성공 게이트

- 해결된 실패의 예방책이 규칙 또는 테스트에 존재한다.
- 같은 예방책을 규칙과 실패 문서가 중복 소유하지 않는다.
- 기본 시작 문맥과 일반 작업 route에 실패 문서가 추가되지 않는다.
- 유지되는 실패 문서는 현재 규칙만으로 도출할 수 없는 정보가 무엇인지 한 문장으로 설명한다.

### 복구 방법

## I6. 통합 재검증과 완료 재판정

### 구현 목표

개선된 Core가 현재 checkout과 독립 clean clone에서 같은 결과를 내는지 확인하고, 증거가 충분할 때만 독립 Core 완료 판정을 복원한다.

### 구현할 내용

- I1~I5의 필수 게이트 증거를 감사한다.
- 현재 checkout 전체 게이트를 실행한다.
- Windows clean clone 전체 게이트를 실행한다.
- 사용할 수 있는 선언 최소 Python과 현재 Python에서 실행한다.
- 라우팅의 구조 검사와 독립 Agent 의미 재현 결과를 별도 표로 정리한다.
- 계층 배정, 문서 역할, 실패 예방책의 단일 소유를 감사한다.
- 모든 필수 조건이 통과하면 `COMPLETION.md`의 완료 판정을 복원한다.
- 하나라도 실패하거나 미실행이면 재검증 상태를 유지한다.

### 변경 예상 범위

- `docs/COMPLETION.md`
- `docs/VERIFICATION.md`
- `STATE.md`
- 필요 시 `README.md`

### 검증 방법

- 통합 게이트와 clean clone 게이트를 직접 실행한다.
- 실행하지 않은 환경은 `not_run`으로 표시한다.
- 새 콜드 세션이 목적, 현재 상태, 변경 절차, 첫 행동을 설명하게 한다.
- 최종 보고의 모든 `pass`를 실행 로그와 대조한다.

### 성공 게이트

- 현재 checkout의 회귀 테스트와 통합 게이트가 전부 통과한다.
- Windows clean clone 게이트가 통과한다.
- LF·CRLF 정상 입력과 실제 후행 공백이 구분된다.
- 모든 활성 route의 구조 검사와 의미 재현이 통과한다.
- 모든 발견 모듈이 단일 계층에 배정된다.
- 활성 문서 간 상태 모순이 없다.
- 실패 예방책이 규칙·테스트에 단일 소유된다.
- 완료 문서의 모든 `pass`가 현재 증거와 연결된다.

### 복구 방법

완료 판정 복원만 되돌리고 재검증 상태를 유지한다. 실패한 구현 단계를 건너뛰어 Host 단계로 전환하지 않는다.

## 8. 구현 세션의 진행 규칙

다른 세션은 이 문서만으로 다음 순서를 따른다.

1. `POLICY.md`와 `STATE.md`를 읽는다.
2. 이 설계의 fingerprint 또는 시작 커밋 SHA를 기록한다.
3. 현재 활성 Stage 하나만 `STATE.md`에 등록한다.
4. Stage의 현재 구현, 변경 범위, 제외 범위, 검증 명령을 재확인한다.
5. 정책·규칙·구조 변경 또는 삭제가 있으면 사용자 결정을 먼저 받는다.
6. 최소 변경만 구현한다.
7. Stage의 모든 검증을 직접 실행한다.
8. `pass`, `fail`, `not_run`, `not_applicable`을 구분한다.
9. 모든 필수 게이트가 `pass`일 때만 완료 커밋을 만든다.
10. 완료 커밋의 clean clone을 다시 검증한 뒤 다음 Stage로 전환한다.

- 모든 실패 이력을 활성 문서로 보존
- 과거 Git 이력 재작성
- 테스트 통과 전 완료 문구 복원

## 10. 전체 완료 조건

다음 조건을 모두 충족해야 개선 작업이 끝난다.

- 현재 checkout 전체 게이트 exit 0
- Windows clean clone 전체 게이트 exit 0
- 정상 LF·CRLF 오탐 0건
- 실제 후행 공백 탐지 성공
- 라우팅 구조 검사와 의미 재현의 증거 수준이 분리됨
- composed 요청 검증 통과
- 발견된 모든 Core 모듈이 정확히 한 계층에 배정됨
- 사람용 절 제목 변경이 소유자 발견을 깨뜨리지 않음
- 진입 포인터 외 짧은 문서의 헤더 우회 0건
- 해결된 실패의 예방책이 규칙·테스트에 흡수됨
- 불필요한 실패 라우팅·검색 데이터 추가 0건
- 활성 문서 간 현재 상태 모순 0건
- 완료 커밋 snapshot 자체가 clean clone에서 통과
- `COMPLETION.md`의 모든 `pass`가 현재 실행 증거와 일치

## 11. 기대 결과

이 설계를 완료해도 Core의 기능 수는 크게 늘지 않는다. 대신 다음이 달라진다.

- Windows와 Linux 줄바꿈 차이가 검사 결과를 바꾸지 않는다.
- 라우팅이 무엇을 실제로 검증했는지 과장 없이 알 수 있다.
- 검사 범위 밖의 모듈과 문서가 사라진다.
- 실패 경험은 문서 검색 부담이 아니라 규칙과 테스트의 예방력으로 남는다.
- 완료 커밋 자체가 복구 가능한 정상 지점이 된다.
- Host 연결을 시작할 때 Core 내부 결함을 Host 문제로 오인하지 않는다.

최종적으로 Core는 더 많은 문서와 Runtime을 가진 시스템이 아니라, **적은 구성으로도 자기 보장을 정확히 검사하는 시스템**이 된다.
