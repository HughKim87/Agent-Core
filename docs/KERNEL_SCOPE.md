# Kernel 범위 — 포함과 제외 분류

- 목적: 참고 구현의 모든 구성요소를 `필수 Kernel`, `검증된 선택 기능`, `실험 기능`, `제외 기능` 중 하나로 판정하고 그 근거를 소유한다.
- 읽는 시점: 어떤 구성요소를 1차 Core에 넣을지 판단할 때, 그리고 그 판정의 근거를 확인할 때.
- 책임: 사용자가 범위 변경을 승인하고 프로젝트 에이전트가 판정 근거를 유지한다.
- 상태: 활성 정본. Stage 2 성공 게이트 통과.
- 관련 권위: [Core 헌장](CHARTER.md) §7의 판정 기준 C1~C5.

## 2. 판정 단위

**판정 단위는 파일이 아니라 기능이다.** 참고 구현에는 한 파일이 필수 기능과 실험 기능을 함께 담은 사례가 있다(§4). 파일 단위로 판정하면 실험 기능이 필수 기능에 업혀 Kernel에 들어온다.

## 4. 숨은 의존성 검사 결과

Stage 2 검증 방법 3의 결과다. **제외·보류 대상이 필수 기능의 숨은 의존성인 사례가 1건 있다.**

참고 구현의 모듈 의존 방향은 다음과 같다.

```
유지보수 검증 ──> 컨텍스트 ──> 지식 ──> 기록 저장소
      │              │          │
      │              └──> 수명주기 ──┘
      └──> 파생 artifact ──> 기록 저장소
```

**문제:** 실제 소비자가 확인된 유일한 모듈(유지보수 검증)이 실험 등급인 지식·수명주기·기록 저장소를 전이적으로 끌어온다. 파생 artifact 검증도 기록 저장소에 의존한다.

**영향:** 실험 기능을 제거하면 필수 Kernel이 import 단계에서 실패한다. 즉 현재 구현 상태로는 §3의 분류를 그대로 파일 이동에 적용할 수 없다.

**처분:** 유지보수 검증을 두 기능으로 분해한다.

| 분해 후 기능 | 등급 | 의존 |
|---|---|---|
| 문서·링크·Schema·AST·보호 경로·Git 상태 검사 | 필수 Kernel | 경로 안전 판정만 |
| source drift·중복·컨텍스트 재평가 | 실험 기능 | 지식·수명주기 Runtime |

파생 artifact 검증의 기록 저장소 의존은 쓰기 계약이 아니라 오류 유형 참조이므로, 오류 유형을 필수 계층으로 올려 해소한다.

**이 처분은 Stage 3의 계층 경계와 의존 방향 설계가 반드시 해결해야 할 제약이다.** Stage 3에서 이 분해가 성립하지 않으면 Stage 2의 분류를 다시 판정한다.

## 5. 필수 Kernel만 남겼을 때의 작업 흐름

Stage 2 검증 방법 2의 결과다. 필수 Kernel만으로 아래 흐름이 성립한다.

| 흐름 | 담당 필수 구성요소 |

| 에이전트가 시작해 정책 정본에 도달 | 진입 문서, 상시 정책, rule-governance |
| 현재 작업에 필요한 규칙만 선택 | rule-governance, 라우팅 테이블 |
| 현재 상태를 읽고 첫 다음 행동을 확인 | 현재 상태 문서, staged-work-design |
| 위험 행동에서 정지 | core-change-control, user-data-work, version-control |
| 변경 후 무결성 검증 | 문서·링크·Schema·AST 검사, 파생 artifact 검증 |

**미충족 없음.** 실험 기능이 하나도 없어도 헌장 §4의 G1~G6을 시도할 수 있다. 단 G6(재현성)의 컨텍스트 부분은 검증된 선택 기능인 컨텍스트 구성이 담당하므로, 1차 Core에서 G6은 규칙 선택의 재현성까지만 보장한다.

## 8. Stage 24 판정 — 작업 상태 Runtime

판정: **제외**. 이 저장소로 옮기지 않는다.

### 8.1 비교 조건

[실험 기능의 격리와 승격](EXPERIMENTAL.md) §5의 기준을 판정 전에 고정한 뒤 적용했다.

- 기준선: Markdown 정본과 Git 커밋만 사용하는 현재 방식
- 후보: 참고 구현의 event·snapshot 기반 작업 상태 Runtime

### 8.2 기준선 실측

23개 단계를 실제로 수행하며 측정했다.

| 항목 | 실측 |
|---|---|
| 재개 정확도 | 콜드 세션 2회. 1회차 실패, 결함 수정 후 2회차 성공 |
| 상태 어긋남 | 2건 발생. 콜드 세션과 자동 검사가 모두 탐지 |
| 정보 재설명 개입 | 0회 |
| 상태 갱신 명령 비용 | 파일 편집 1회 + 커밋 1회 |
| 활성 상태 문서 수 | 1개 |
| 복구 | 단계마다 커밋. 실제로 파일 복구를 1회 수행 |

기준선은 헌장의 G2와 P4를 실제로 달성했다.

### 8.3 후보 실측

| 항목 | 실측 |
|---|---|
| 실제 저장된 작업 상태 데이터 | 0건 |
| 프로덕션 쓰기 | 구현상 차단됨 |
| 구현 규모 | 코드 592줄, schema 3종, CLI 명령 4개, 테스트 396줄 |

후보 쪽 pilot은 수행하지 않았다. 수행하려면 먼저 이식해야 하는데, 이식 자체가 판정 대상이기 때문이다. 이 사실을 통과로 표시하지 않는다. 후보의 성능은 `not_run`이다.

### 8.4 판정 근거

1. 승격 조건 1 미충족. Kernel 밖 실제 소비자가 0이다.
2. 승격 조건 3 미충족. 기준선이 이미 달성한 결과에 코드 592줄과 명령 4개를 추가한다.
3. 승격 조건 5 미충족. 같은 결과를 Markdown 정본과 Git으로 얻고 있음이 실측되었다.
4. 비교 기준의 "동률이면 더 단순한 기준선을 유지한다"에 해당한다.

### 8.5 재검토 조건

다음 중 하나가 실제로 발생하면 이 판정을 다시 연다.

- 둘 이상의 에이전트가 같은 상태를 **동시에** 갱신해야 한다. 현재는 한 번에 하나만 작업한다.
- 상태 갱신이 사람이 검토할 수 없는 빈도로 일어난다.
- Markdown 정본으로 복구할 수 없는 상태 어긋남이 발생한다.

세 조건 모두 현재 발생하지 않았다. 발생하기 전에 만들지 않는다.

## 9. Stage 25 판정 — 지식·결정·수명주기 Runtime

판정: **제외**. 이 저장소로 옮기지 않는다.

### 9.1 비교 조건

Stage 24와 같은 기준을 사용했다. 기준을 판정 시점에 바꾸지 않았다.

- 기준선: 원인별 Markdown 정본 + Git 이력 + 자동 중복·구조 검사
- 후보: 참고 구현의 source·knowledge·decision record와 lifecycle 상태 기계

### 9.2 대표 시나리오 대입

블루프린트가 지정한 네 시나리오를 이 저장소에서 실제로 발생한 사례로 대입했다.

| 시나리오 | 실제 발생 사례 | 기준선의 처리 | 결과 |
|---|---|---|---|
| 대체 결정 | Stage 18에서 컨텍스트 구성의 등급을 선택 기능에서 필수로 변경 | 등급 정본을 제자리에서 갱신하고 변경은 커밋이 소유 | 처리됨 |
| 충돌 지식 | 반복 지시 제거 요구와 승인 요구가 표면상 충돌 | 헌장에서 두 개념을 분리해 정의 | 처리됨 |
| 오래된 근거 | 알려진 위험 표에 완료된 단계를 해소 시점으로 적은 항목이 남음 | 콜드 세션이 지적해 수정 | **자동 탐지 실패** |
| 출처 변경 | 참고 구현은 읽기 전용이며 변경되지 않았다 | 해당 없음 | 미발생 |

### 9.3 유일한 약점과 그 해소

기준선의 약점은 시나리오 3이다. 자유 서술 표에 남은 오래된 항목을 자동으로 잡지 못했다.

그러나 이 약점은 구조화 Runtime으로 해소되지 않는다. 오래된 항목은 자유 서술 문장이었고, 이를 record로 만들려면 모든 위험 항목을 구조화 record로 관리해야 한다. 그 비용이 §9.4의 규모다.

실제 해소는 다른 방법으로 이루어졌다. 현재 상태 문서의 크기 예산을 강제하는 검사를 추가해 누적 자체를 막았다. 오래된 항목이 생기는 원인은 항목의 형식이 아니라 문서가 계속 커지는 것이었다.

### 9.4 비용 비교

| 항목 | 기준선 | 후보 |
|---|---|---|
| 코드 | 0줄 | 약 2,100줄 |
| Schema | 0종 | 7종 |
| CLI 명령 | 0개 | 26개 |
| 계약 문서 | 0개 (규칙 1개에 포함) | 3개 |
| 테스트 | 0줄 (구조 검사에 포함) | 약 1,378줄 |
| 실제 저장된 지식 record | 정본 7건, 총 약 1.2만 자 | 0건. 발견된 5개는 테스트 fixture다 |

### 9.5 판정 근거

1. 승격 조건 1 미충족. Kernel 밖 실제 소비자가 0이다.
2. 승격 조건 2 미충족. 기준선이 실패한 유일한 시나리오를 후보가 해결한다는 근거가 없다.
3. 승격 조건 3 미충족. 코드 2,100줄과 명령 26개의 비용이 관측된 개선을 넘는다.
4. 참고 구현의 계약 자체가 해결 실패 지식의 정본을 Markdown으로 두고 저장 표현을 만들지 않는다고 명시한다. 후보를 도입하면 그 계약과 충돌하는 중복 정본이 생긴다.

### 9.6 재검토 조건

- 지식 항목이 사람이 훑어 판단할 수 없는 수준으로 늘어난다.
- 같은 주장에 대해 서로 다른 정본이 실제로 생겨 Markdown 검사로 잡히지 않는다.
- 외부 출처의 변경을 추적해야 하는 작업이 실제로 발생한다.

세 조건 모두 현재 발생하지 않았다. 참고 구현의 코드는 그 저장소의 Git 이력에 남아 있으므로 필요해지면 그때 가져온다.
