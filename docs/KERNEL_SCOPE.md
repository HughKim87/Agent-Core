# Kernel 범위

- 목적: Agent Core에 포함되는 필수·선택·실험·제외 기능과 판정 기준을 소유한다.
- 읽는 시점: Core에 구성요소를 추가·제거·승격할 때.
- 책임: 사용자가 범위 변경을 승인하고 Core Maintainer가 판정을 유지한다.
- 상태: 활성 정본. 순수 Core contract v2.
- 관련 권위: [Core 헌장](CHARTER.md) §7, [계층 구조](ARCHITECTURE.md).

---

## 1. 판정 기준

| 기준 | 질문 |
|---|---|
| C1 도메인 중립 | 특정 프로젝트 이름·경로·어휘 없이 재사용되는가 |
| C2 보장 기여 | G1~G6 중 하나를 직접 제공하거나 검증하는가 |
| C3 소비자 존재 | 실제 공개 흐름이나 필수 gate가 사용하는가 |
| C4 격리 가능 | 없어도 필수 Core가 시작·검증되는가 |
| C5 단순성 | 더 단순한 파일·Git 계약으로 같은 결과를 얻을 수 없는가 |

판정 단위는 파일이 아니라 기능이다. 한 파일에 서로 다른 등급이 섞이면 의존을 분리한다.

## 2. 필수 Kernel

- Core 공통 정책과 규칙 route
- 작업 계약, 단계 설계, 인수인계, 문서, 파일 지식 추출, 추출 후 정리, 보호 데이터, Core 변경, 경계 의존성, Git, 교차검증, 실패 예방, 규칙 거버넌스
- Core·consumer 정보 소유 선언과 계약 문서
- 경로 안전, 선언 해석, 구조·링크·AST·계층 검사
- Core·consumer scope가 있는 시작 context와 fingerprint
- `verify`, `context`, `gate` 공개 CLI
- 필수 기능의 회귀·결함 주입 테스트

## 3. 소비 저장소 제공 계약

다음은 Core 목적에 필요하지만 Core 파일이 아니다.

- 루트 `AGENTS.md`, `CLAUDE.md`
- 프로젝트 `PROJECT_RULES.md`와 소비 계약 선언
- 현재 상태 문서
- 도메인 규칙과 보호 경로
- `.gitmodules`와 Core gitlink

이 항목을 Core에 넣으면 프로젝트별 상태가 공통 배포물에 섞이므로 consumer scope에 둔다.

## 4. 선택 계층

### 4.1 현재 검증된 기능

- 결정론적 파생 artifact 검사
- 규칙에서 도출되지 않는 최소 예외 진단
- 필수 경로와 분리된 추가 검사 등록

선택 기능 부재는 이유가 있는 `not_applicable`이며 실패가 아니다.

### 4.2 승인된 공통 데이터 흡수 범위

다음 기능은 필수 Kernel이 아니라 L7 선택 계층으로 일반화해 흡수하도록 승인됐다.

- strict JSON·UTF-8·경로 안전을 갖는 공통 record 외피와 원자적 저장
- source·knowledge·decision의 검증과 승인 기반 수명주기
- 문서와 문서 내부 `data_key`를 직접 선택하는 결정론적 evidence context package
- 기존 작업 상태·실행 계약을 잃지 않기 위한 비활성 호환 Runtime
- 위 기능을 증명하는 schema·계약·회귀·결함 주입 테스트

이 목록은 구현 완료나 공개 제공을 뜻하지 않는다. 기능별 구현과 검증이 완료되고 [호환성 선언](COMPATIBILITY.md)에 공개 인터페이스가 등록되기 전까지 상태는 `approved_for_absorption`이다.

선택 데이터 계층은 다음 경계를 지킨다.

- 실제 record·event·snapshot·context 결과는 Core 저장소가 아니라 소비 저장소가 소유한다.
- 기본값은 비활성이며 L1~L6, 시작 context와 필수 gate가 이 계층을 import하거나 요구하지 않는다.
- 시작 정책 복원용 `context`와 작업 근거 선택용 evidence context를 서로 다른 계약으로 유지한다.
- 보호 경로를 자동 탐색하거나 외부 서비스로 전송하지 않는다.
- 도메인 필드·도메인 workflow·소비 저장소의 artifact 등록은 포함하지 않는다.
- 참고 구현을 통째로 복사하지 않고 의존 순서에 따라 기능·계약·테스트를 함께 이전한다.

## 5. 필수 Kernel 제외와 선택 계층 밖의 기능

§4.2의 기능도 다음 형태로는 필수 Kernel에 도입하지 않는다.

- event·snapshot 작업 상태 Runtime을 소비 Markdown 정본의 필수 대체물로 사용
- 별도 지식·결정·수명주기 저장소를 시작 경로나 필수 gate에서 요구
- 모든 파일을 자동 탐색하는 source drift·중복 Runtime
- Core 저장소 내부에 소비 Runtime 데이터를 저장

다음은 선택 계층에도 포함하지 않는다.

- 특정 외부 도구용 계약
- 도메인 워크플로와 도메인 패키지명
- 배포 전용 하위 폴더, 모양이 다른 배포 브랜치, Host별 Core 복사본

현재 상태는 소비 Markdown 정본이, 완료·복구 이력은 Git이 이미 소유한다. 같은 결과를 위한 별도 저장 Runtime은 만들지 않는다.

## 6. 제거 영향

| 제거 대상 | 결과 |
|---|---|
| 소비 진입·정책·상태 | Core 자체 검증은 가능, 소비 G1·G2는 구성 불가 |
| L7 실험 Runtime | 필수 Core 영향 없음 |
| L6 기반 원시 | Core 검사 불가 |
| L5 검증 도구 | 규칙 읽기는 가능하지만 G4·G6 자동 검증 불가 |
| L2 공통 규칙 | 안전·작업 절차 보장 축소 |
| L1 Core 정책 | 공통 route와 권위 복원 불가 |

## 7. 재검토 조건

§4.2 밖의 제외 기능을 다시 판정하거나 선택 기능을 필수 Kernel로 승격할 때는 다음 실제 문제가 반복돼야 한다.

- 둘 이상의 에이전트가 같은 상태를 동시에 갱신해야 함
- Markdown 정본과 Git으로 복구할 수 없는 상태 어긋남
- 사람이 검토할 수 없는 빈도의 상태·지식 변경
- 둘 이상의 실제 소비자가 같은 추가 기능을 요구

§4.2는 기존 구현과 실제 소비 흐름, 여러 프로젝트에서 공통 데이터를 보존하려는 사용자의 승인에 따라 예외적으로 흡수 범위가 확정됐다. 각 기능의 `available` 판정은 구현 단계의 직접 게이트를 통과한 뒤에만 부여한다.
