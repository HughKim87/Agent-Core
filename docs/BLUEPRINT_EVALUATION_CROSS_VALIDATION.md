# Core 구축 평가 교차 검증 보고서

- 목적: 기존 Core 청사진 구현 평가와 사용자가 제공한 다른 Agent의 자체 평가를 현재 저장소 증거로 교차 검증하고, 확인된 사실·오류·미검증 주장을 구분해 조정 점수를 제시한다.
- 읽는 시점: Core 완성도를 다시 판단할 때, 두 평가의 차이를 확인할 때, 보완 작업의 우선순위를 정할 때.
- 책임: 평가자는 저장소 파일, Git 단계 이력, 직접 실행 결과를 기준으로 판정하며 사용자가 최종 평가와 후속 작업 착수를 결정한다.
- 상태: 2026-08-13 기준 평가 스냅샷. 실제 프로젝트에서 사용해야만 확인 가능한 항목은 점수에서 제외했다. 현재 상태의 정본이 아니다.
- 관련 권위: [전체 구축 설계](../AGENT_CORE_BUILD_BLUEPRINT.md), [기존 구현 평가](BLUEPRINT_IMPLEMENTATION_EVALUATION.md), [검증 수준](VERIFICATION.md), [완료 판정](COMPLETION.md).

## 1. 교차 검증 결론

사용자가 제공한 다른 Agent 보고서의 **핵심 기술 지적은 대부분 사실**이다. 특히 기존 구현 평가가 충분히 반영하지 못한 다음 결함을 정확히 발견했다.

- 의도 fixture의 발화문이 실제 라우팅 판정에 사용되지 않는다.
- 규칙에서 요구한 의미 기반 재현 없이 route가 활성화됐다.
- `composed` 라우팅 사례가 정의만 있고 fixture에는 없다.
- Stage 8 체크포인트에 Stage 9 route가 먼저 들어가 독립 체크아웃이 깨진다.
- 검사기가 문서 파일명 대신 절 이름에 결합돼 있다.
- 짧은 루트 문서가 문서 헤더 검사를 우회할 수 있다.
- 실패 지식의 색인은 존재하지만 작업 영역에서 관련 사례를 발견하는 경로가 불완전하다.

반면 다른 Agent 보고서의 `clean clone 통과`, `이식성과 독립성 10/10`, `G3 완전 달성` 주장은 현재 직접 검증 결과와 맞지 않거나 증거가 부족하다.

따라서 두 보고서 중 하나를 그대로 채택하지 않는다. 기존 평가의 83.8점은 라우팅·단계 경계·실패 지식 발견성 문제를 충분히 감점하지 않아 높았고, 다른 Agent의 78점은 총점 범위는 타당하지만 이식성 세부 배점이 잘못됐다.

**교차 검증 조정 점수는 225/280점, 환산 80.4/100점이다.**

판정은 다음과 같다.

> **Core의 설계 골조와 운영 계약은 양호하다. 그러나 라우팅 검증이 명목상 수준에 머물고 Windows clean clone 게이트가 실패하므로 독립 Core 완료 판정은 재검증해야 한다.**

## 2. 평가 범위

### 2.1 이번 점수에서 제외한 것

다음은 실제 프로젝트에서 사용해야만 확인할 수 있으므로 점수와 감점에서 제외했다.

- 실제 Host 1·2에 Core를 연결한 결과
- 다른 도메인 프로젝트에서 실패 지식이 재사용되는지
- 실제 보호 데이터와 외부 시스템을 대상으로 한 운영 결과
- 후보 Runtime의 실제 프로젝트 장기 pilot과 효용
- Host 내부에서 에이전트 진입 파일이 실제로 어떻게 로드되는지

### 2.2 이번 점수에 포함한 것

다음은 현재 저장소만으로 확인할 수 있으므로 평가에 포함했다.

- 문서·코드·계약의 존재와 정합성
- 정적 검사, 단위 테스트, 통합 게이트
- 라우팅 fixture가 실제 입력을 소비하는지
- 단계별 커밋이 독립 체크포인트로 성립하는지
- 현재 운영체제에서의 clean clone
- 현재 설치된 Python runtime에서의 실행
- 문서 탐색, 실패 지식 발견, 단일 정본 연결 구조

## 4. 직접 확인한 핵심 증거

### 4.1 라우팅 fixture는 발화문을 소비하지 않는다

fixture에는 36개의 `utterance`가 있지만 테스트는 다음만 확인한다.

- ID 유일성
- 기대·금지 소유자의 route 등록 여부
- 기대와 금지 집합의 배타성
- 각 route의 `initial`, `colloquial`, `mid-task`, `near-miss` 종류 존재 여부
- fixture가 별도 라우터가 아니라는 선언

발화문을 입력받아 route를 계산하는 함수와 assertion은 없다. 따라서 현재 테스트가 입증하는 것은 **fixture 구조의 일관성**이지 **발화→소유자 선택의 정확성**이 아니다.

`composed`는 규칙 문서에 정의됐지만 테스트 필수 종류에 없으며 실제 케이스도 0건이다.

### 4.2 Stage 8 체크포인트는 독립적으로 유효하지 않다

Stage 8 커밋 `8699da1`에는 다음 불일치가 있다.

- `POLICY.md`: `rules/staged-work-design.md` route 존재
- Git tree: `rules/staged-work-design.md` 부재
- 해당 파일 생성: Stage 9 커밋 `74732db`

따라서 Stage 8 커밋은 단계별 독립 복구 지점이라는 계약을 충족하지 않는다. 작업 트리에 다음 Stage 파일이 미커밋 상태로 존재한 채 테스트했을 가능성이 높지만, 현재 Git 증거만으로 당시 작업 트리 상태까지 확정할 수는 없다.

### 4.3 문서 이름 결합은 줄었지만 문서 의미 결합이 남았다

현재 검사기는 `POLICY.md`, `STATE.md` 같은 파일명을 직접 상수로 쓰지 않는다. 대신 아래 절 이름으로 문서를 찾는다.

- `규칙 라우팅`
- `첫 다음 행동`

이는 파일 개명에는 버티지만 절 개명에는 깨진다. “이름을 상수로 쓰지 않는다”는 A6의 문자 조건은 통과하더라도, 검증기가 상위 문서의 의미와 구조를 하드코딩하지 않는다는 아키텍처 원칙은 충족하지 못한다.

### 4.4 문서 헤더 검사의 우회 경로가 존재한다

루트에 있는 2,000자 미만 문서가 메타데이터 항목 없이 시작하면 `document-headers` 검사에서 제외된다. 포인터 전용 진입 파일을 허용하기 위한 예외지만, 다른 짧은 루트 문서도 같은 조건으로 우회할 수 있다.

예외는 파일 이름이 아니라 선언된 역할이나 허용된 문서 유형을 기준으로 제한해야 한다.

### 4.5 실패 지식은 저장됐지만 발견 경로가 약하다

`failures/README.md`에는 원인별 색인이 있고 `rules/failure-records.md`에는 과거 실패 영역 진입 시 검색하라는 행동이 있다. 그러나 다음 연결이 없다.

1. 실패 기록 규칙에서 색인으로 가는 명시적 링크
2. 현재 작업의 영역을 어떤 실패 사례와 연결할지에 대한 최소 선택 규칙
3. 선택된 실패 지식이 실제 컨텍스트에 포함됐는지 확인하는 경로

현재 컨텍스트 구성기는 `failures/`를 기본 선택에서 의도적으로 제외한다. 이 선택 자체는 타당하지만, 조건이 맞을 때 다시 포함하는 명시적 인터페이스가 없으므로 G5는 정본 보존 수준을 넘지 못한다.

### 4.6 clean clone 완료 주장은 현재 무효다

현재 Windows 환경과 Python 3.12.13에서 직접 실행한 결과다.

| 환경 | 검사 | 결과 |
|---|---|---|
| 현재 작업 트리 | 무결성 검사 | 13종, 위반 0 |
| 현재 작업 트리 | 회귀 테스트 | 76건 중 70건 통과, 6건 실패 |
| clean clone | 무결성 검사 | CRLF 오탐 5,434건 |
| clean clone | 회귀 테스트 | 76건 중 69건 통과, 7건 실패 |
| clean clone | 전체 게이트 | `fail` |

원인은 Git `core.autocrlf=true`와 `.gitattributes` 부재, 검사기의 CRLF 처리 방식이 결합한 것이다. 이는 실제 Host 없이도 재현되는 Core 자체 이식성 결함이다.

## 5. 두 평가의 비교

| 평가 | 장점 | 누락·오류 |
|---|---|---|
| 기존 구현 평가 83.8점 | clean clone 실패, CRLF 원인, 문서 drift, A7·O2·O6 누락을 직접 확인 | 라우팅 fixture의 실질, Stage 8 고아 route, 실패 지식 발견성, 문서 헤더 우회를 충분히 감점하지 않음 |
| 다른 Agent 평가 78점 | 라우팅 검증의 핵심 공백과 단계 경계 위반, 과장된 증거 수준을 정확히 지적 | clean clone 통과와 이식성 10점이 현재 사실과 반대. G3 완전 달성도 근거 부족. 일부 작업 이력은 독립 검증 불가 |
| 교차 검증 80.4점 | 양쪽의 확인된 증거만 반영하고 실제 프로젝트 실사용 항목은 제외 | 실제 Host·타 프로젝트 효용은 의도적으로 미평가 |

다른 Agent의 총점 78점은 교차 검증 범위와 멀지 않다. 그러나 이는 세부 배점이 모두 맞아서가 아니다. 라우팅·검증을 더 엄격하게 본 감점은 타당하지만, clean clone과 이식성은 오히려 과대평가했다. 서로 반대 방향의 오차가 총점에서 일부 상쇄됐다.

## 7. 보완 우선순위

### 1순위 — clean clone 복구

- CRLF 허용 또는 LF 강제 중 하나를 계약으로 확정한다.
- Windows clean clone에서 무결성 0건, 회귀 테스트 전부 통과, 전체 게이트 exit 0을 확인한다.
- `COMPLETION.md`, `VERIFICATION.md`, `COMPATIBILITY.md`의 환경 증거를 실제 결과와 맞춘다.

### 2순위 — 실제 라우팅 판정 검증

- 발화문을 입력받아 route를 계산하는 판정 경로를 정의한다.
- fixture의 `utterance`, `prior_owners`, `expected_owners`, `forbidden_owners`를 모두 assertion에 사용한다.
- `composed` 사례를 추가하고 둘 이상의 소유자가 함께 선택되는지 확인한다.
- 기계 판정과 모델 의미 재현의 증거 수준을 별도로 기록한다.

### 3순위 — 실패 지식 발견 경로 연결

- 실패 기록 규칙에서 `failures/README.md` 색인으로 가는 링크를 둔다.
- 작업 영역 진입 시 관련 실패 사례를 선택하는 최소 규칙을 정의한다.
- 기본 시작 컨텍스트에는 넣지 않되, 조건 일치 시 명시적으로 포함할 수 있게 한다.

### 4순위 — 문서 구조 결합 축소

- 라우터와 상태 소유자를 절 이름이 아니라 단일 선언으로 찾는다.
- 포인터 문서 예외를 문서 길이가 아니라 선언된 역할로 제한한다.
- Stage별 커밋에서 다음 Stage의 파일이나 route가 선행되지 않는지 검사한다.

### 5순위 — 완료 판정 재감사

- Stage 7, 8, 11, 14, 15, 17, 18, 22, 26, 27의 게이트를 다시 확인한다.
- 모든 필수 내부 게이트가 `pass`가 된 뒤 독립 Core 1차 완료를 복원한다.
- 실제 Host 검증은 그 다음 단계로 유지하며 이번 내부 완료 점수에는 섞지 않는다.

## 8. 최종 판정

교차 검증 결과, Core는 처음부터 다시 설계해야 할 상태가 아니다. 정책·상태·단계·안전 경계·최소 실행 도구의 기본 구조는 유지할 가치가 있다.

보완이 필요한 핵심은 구조 추가가 아니라 **증거의 정확도**다. 현재 가장 큰 문제는 라우팅 fixture가 실제 라우팅을 검증하지 않는데도 결정론적 라우팅 검증으로 표현된 점과, clean clone 성공 주장이 현재 Windows 환경에서 재현되지 않는 점이다.

따라서 현재 상태의 적절한 표현은 다음과 같다.

> **독립 Core의 설계와 주요 구현은 완료됐지만, 의미 기반 라우팅과 이식성 게이트를 보완하는 내부 완료 재검증이 필요하다.**
