# Core 청사진 구현 검토 및 점수 평가

- 목적: `AGENT_CORE_BUILD_BLUEPRINT.md`를 기준으로 저장소 내부의 구현·직접 검증 증거를 대조하고, 28개 구축 항목의 현재 충족도를 점수와 후속 게이트로 기록한다. 실제 프로젝트 적용이 필요한 실사용 검증은 이번 점수에서 제외한다.
- 읽는 시점: 독립 Core 완료 주장을 재검토할 때, 보완 작업의 우선순위를 정할 때, Host 연결 단계 착수 여부를 판단할 때.
- 책임: 평가자는 현재 저장소와 직접 실행 결과를 근거로 판정하며, 구현 담당자는 지적 사항을 수정한 뒤 해당 단계의 성공 게이트를 다시 실행한다. 최종 완료 확인은 사용자가 소유한다.
- 상태: 2026-08-13 기준 재평가 스냅샷. 실제 프로젝트 실사용 검증 제외 기준을 적용했다. 현재 상태의 정본이 아니며, 후속 수정 결과는 `SESSION_HANDOFF.md`와 단계별 Git 이력이 소유한다.
- 관련 권위: [전체 구축 설계](../AGENT_CORE_BUILD_BLUEPRINT.md), [검증 수준과 완료 판정](VERIFICATION.md), [독립 Core 1차 완료 판정](COMPLETION.md), [현재 상태](../SESSION_HANDOFF.md).

## 1. 평가 결론

**총점은 234.5/280점, 환산 83.8/100점이다. 판정은 `설계·구현은 양호하나 내부 완료 게이트 보완 필요`다.**

Core의 목적·정책·작업 계약·세션 재개 구조는 일관성이 높고, 28개 Stage를 각각 별도 커밋으로 남긴 점과 저장소 내부 자체 운영·콜드 세션에서 결함을 찾아 수정한 과정은 강한 증거다. 단순한 문서 모음이 아니라 정책, 상태, 라우팅, 무결성 검사, 컨텍스트 구성, CLI, 통합 게이트가 연결된 최소 Core도 실제로 존재한다.

그러나 현재 환경에서 필수 통합 게이트가 실패한다. 특히 Windows clean clone에서 Git의 CRLF 변환을 무결성 검사가 후행 공백으로 오인해 5,434건을 보고하고, 회귀 테스트도 실패한다. 따라서 [완료 판정](COMPLETION.md) §7의 무효화 조건 중 `clean clone에서 게이트가 실패한다`가 현재 환경에서 성립한다.

Stage 24·25의 후보 Runtime pilot, 다른 프로젝트에서의 실패 지식 재사용, 실제 Host 연결처럼 **실제 프로젝트에 적용해야 확인 가능한 항목은 점수와 감점에서 제외했다.** 이 점수는 저장소 내부 설계와 구현 완성도를 뜻한다. **점수가 83.8점이라는 사실이 완료를 의미하지는 않는다. 내부 필수 게이트 하나의 실패만으로도 완료 판정은 보류된다.**

## 3. 직접 실행한 검증

### 3.1 현재 작업 트리

실행 환경은 Windows, Python 3.12.13이다.

| 검사 | 결과 | 판정 |
|---|---|---|
| `core-check gate` preflight | Core 0.1.0, runtime 조건 충족 | `pass` |
| 필수 무결성 검사 | 13종, 위반 0 | `pass` |
| 시작 컨텍스트 | 5,999자 / 예산 20,000자 | `pass` |
| 회귀 테스트 | 76건 중 70건 통과, 6건 실패 | `fail` |
| 선택 기능 부재 | 필수 실패와 분리됨 | `not_applicable` |
| 게이트 무부작용 | 실행 전후 트리 동일 | `pass` |
| 전체 게이트 | 회귀 테스트 단계에서 중단 | `fail` |

6개 실패는 모두 합성 저장소를 `Path.write_text()`로 만든 뒤 검사하는 경로에서 발생했다. Windows가 `\n`을 CRLF로 기록하지만 [무결성 검사](../src/core_check/integrity.py)는 문자열을 `\n`으로만 나누고 남은 `\r`까지 `rstrip()` 대상인 후행 공백으로 취급한다. 이 때문에 정상 CRLF 줄이 오류가 된다.

### 3.2 clean clone 재현

현재 저장소를 임시 디렉터리에 `git clone --no-hardlinks`로 복제한 뒤 같은 게이트를 실행했다.

| 검사 | 결과 | 판정 |
|---|---|---|
| clean clone 생성 | 성공 | `pass` |
| 필수 무결성 검사 | 후행 공백 오탐 5,434건 | `fail` |
| 회귀 테스트 | 76건 중 69건 통과, 7건 실패 | `fail` |
| 시작 컨텍스트 | 예산 이내 | `pass` |
| 전체 게이트 | 무결성·회귀 테스트 실패 | `fail` |

재현 조건은 Git `core.autocrlf=true`, 저장소의 `.gitattributes` 부재다. 원본 blob은 LF지만 새 Windows checkout은 CRLF가 되고, 현재 검사기가 이를 허용하지 않는다. 해결 방향은 둘 중 하나를 명시적으로 선택해야 한다.

1. CRLF를 정상 줄바꿈으로 허용하도록 검사와 fixture를 수정한다.
2. `.gitattributes`에서 검사 대상 텍스트를 LF로 고정하고 clean clone에서 강제한다.

선택 후 Windows clean clone과 선언된 최소 Python runtime에서 모두 다시 검증해야 한다.

### 3.3 참고 증거 — 별도 실사용 배점 없음

- Stage 1~28은 각각 별도 커밋으로 분리되어 있어 단계별 변경 추적과 복구 지점이 명확하다.
- Stage 20은 규칙 추가, 계층 위반 주입, 수행 불가 상태를 실제 저장소에서 실행하고 예상하지 못한 예외 처리 결함을 수정했다.
- Stage 21은 대화 맥락 없는 콜드 세션 2회를 실행해 첫 행동의 모호성, 오래된 위험 항목, 조용히 적용되지 않은 수정 문제를 발견했다.
- Stage 24·25의 기준선은 저장소 내부 운영 증거가 있고 후보 Runtime은 각각 `not_run` 또는 문서 비교에 머물렀다. 이번 재평가에서는 후보 Runtime의 실제 프로젝트 pilot을 요구하지 않고, 제외 판단의 논리와 재검토 조건만 채점했다.

이 절의 증거는 구현과 내부 검증 점수의 보조 근거로만 사용했다. 외부 프로젝트 실사용 여부에 별도 배점을 주지 않았다.

## 6. 핵심 발견 사항

### 6.1 P0 — 완료를 막는 결함

1. **Windows clean clone에서 통합 게이트 실패**
   - `core.autocrlf=true` checkout이 CRLF를 만들고 검사기가 이를 후행 공백으로 오인한다.
   - 현재 작업 트리에서는 무결성 검사가 통과하므로 clean clone에서만 드러나는 이식성 결함이다.
   - Stage 15, 22, 26, 27을 재개방해야 한다.

2. **Stage 27 완료 판정의 현재 무효화**
   - 완료 문서가 정한 무효화 조건을 현재 clean clone이 충족한다.
   - 수정과 재검증 전에는 Host 연결 단계로 진행하지 않는다.

Stage 24·25의 실제 프로젝트 pilot은 이번 재평가의 완료 차단 사항에서 제외했다. 두 단계는 현재 문서에 기록된 제외 근거와 재검토 조건만으로 평가했다.

### 6.2 P1 — 신뢰도를 낮추는 정합성 문제

1. `README.md`는 독립 Core가 아직 구축 중이라고 서술하지만 `SESSION_HANDOFF.md`와 완료 문서는 28단계 완료라고 서술한다.
2. `SESSION_HANDOFF.md`의 Host 경계 위험은 해소 시점을 이미 완료된 Stage 28로 적고 있다.
3. `SESSION_HANDOFF.md`는 O3까지 미구현이라고 적지만 `state-size-budget` 검사와 상태 계약 테스트가 이미 존재한다. 미구현 범위를 A7·O2·O6과 O3의 의미 검사 잔여분으로 정확히 나눠야 한다.
4. [검증 문서](VERIFICATION.md)의 clean clone `integrated` 표시는 현재 검증 환경 범위를 함께 적거나 재검증 뒤 갱신해야 한다.

### 6.3 유지할 강점

1. 정책과 조건부 규칙의 분리, 단일 라우터, 단일 현재 상태 구조는 계속 유지할 가치가 높다.
2. Stage별 독립 커밋과 상세 커밋 본문은 별도 완료 이력 문서보다 추적성이 좋다.
3. 실제 사용 중 발견한 결함을 게이트와 회귀 테스트로 환원한 Stage 20·21 방식은 이후 보완 작업에도 그대로 적용할 수 있다.
4. Host 문제를 Core 완성 이후로 미루고 실제 해를 먼저 확인하게 한 Stage 28의 문제 설정은 타당하다.

## 7. 권장 보완 순서와 재성공 게이트

### 1순위 — 줄바꿈·clean clone 계약 확정

- CRLF 허용 또는 LF 강제 중 하나를 계약으로 선택한다.
- 무결성 검사와 테스트 fixture를 같은 계약에 맞춘다.
- Windows clean clone에서 필수 무결성 0건, 회귀 테스트 전부 통과, 전체 게이트 exit 0을 확인한다.
- 선언된 최소 Python과 현재 Python에서 각각 실행 결과를 남긴다.

### 2순위 — 완료 판정과 활성 문서 정합성 복구

- Stage 15·22·26의 증거를 새 실행 결과로 갱신한다.
- `README.md`, `SESSION_HANDOFF.md`, `VERIFICATION.md`, `COMPLETION.md`의 현재 표현을 서로 맞춘다.
- Stage 27을 다시 감사해 모든 필수 게이트가 `pass`인지 확인한다.

### 3순위 — 자동 검사 공백 축소

- A7 전체 구성요소 단일 계층 배정 검사
- O2 금지된 중복 정본 탐지의 최소 구조 검사
- O6 동적 수치 고정 금지의 적용 가능한 범위 정의
- O3 크기 예산과 의미 기반 완료 이력 누적 검사의 책임 구분

### 4순위 — Host 단계 재진입

Stage 27이 다시 통과한 뒤에만 [Host 진입 조건](HOST_ENTRY_CONDITIONS.md)의 최소 재현 작업을 시작한다. 현재 점검 결과만으로는 Host 연결 구현 착수를 권장하지 않는다.

## 8. 최종 평가

이 구현은 실패한 프로젝트가 아니다. **실제 프로젝트 실사용 검증을 제외한 설계·구현 평가에서는 83.8점으로 양호하며, 특히 세션 독립성·규칙 라우팅·상태 단일화·저장소 내부 자체 운영 증거는 강하다.**

현재 문제는 구조 부재가 아니라 저장소 내부 이식성 게이트에 있다. 줄바꿈 결함은 비교적 국소적이지만 clean clone이라는 최상위 성공 조건을 깨뜨린다. 따라서 다음 작업은 새 기능이나 외부 프로젝트 실증이 아니라 Stage 15·22·26·27을 순서대로 재감사하고 내부 증거를 다시 닫는 것이어야 한다.

그 작업이 끝나기 전의 적절한 상태 표현은 **“독립 Core 구조 구축 완료, 1차 완료 판정 재검증 중”**이다.
