## 3. 최초 설계 분석과 점수

### 3.1 잘 설계된 부분

1. **문제를 정확히 Core 내부로 좁혔다.** Host·submodule·배포를 독립 Core 완료 뒤로 미룬 결정은 범위 팽창을 막았다.
2. **기존 구현을 정답으로 간주하지 않았다.** 실제 소비자와 사용 증거를 기준으로 Kernel·선택·실험·제외를 나눈 점이 좋다.
3. **순서를 기능 목록이 아닌 의존 단계로 설계했다.** 목적→범위→계층→정본→정책→검증→자체 운영→완료의 흐름은 합리적이다.
4. **검증 수준을 구분했다.** 단위 테스트, 통합, 자체 운영, cross-agent를 서로 다른 증거로 본 원칙은 현재 Core의 신뢰 기반이 됐다.
5. **미채택도 정상 결과로 허용했다.** 작업 상태·지식 Runtime을 억지로 포함하지 않고 비교 후 제외할 수 있게 했다.

## 4. 개선 후 현재 구현 분석과 점수

### 4.1 현재 구현의 핵심 구조

현재 Core는 다음 흐름으로 작동한다.

1. 진입 포인터가 공통 정책으로 연결된다.
2. 정책과 상태 역할은 [정보 소유 선언](INFORMATION_OWNERSHIP.md)의 기계 블록에서 조회된다.
3. 정책의 단일 route 블록이 현재 행동에 필요한 규칙만 선택한다.
4. `core_check`가 문서·링크·JSON·AST·계층·정본·context·파생 artifact를 검사한다.
5. 통합 게이트가 runtime preflight부터 회귀·무부작용까지 하나의 결과로 판정한다.
6. 단계 완료는 작업 트리가 아니라 후보 commit snapshot의 clean clone으로 검증된다.

이 구조는 초기 설계가 원한 “대화 기억 없이 같은 정책·상태·검증으로 합류하는 최소 운영 Kernel”을 실제 파일과 코드로 구현했다.

### 4.2 현재 구현의 강점

- **최소 Kernel이 실제로 독립적이다.** 실험 Runtime과 Host가 없어도 필수 게이트가 통과한다.
- **역할과 계층이 기계 판독 가능하다.** 발견된 모든 Core 모듈의 미배정·중복·금지 import를 검사한다.
- **정상 통과만 확인하지 않는다.** CRLF, 후행 공백, 고아 route, 중복 route, 계층 위반, 상태 중복, commit 누락 등 결함 주입 테스트가 있다.
- **검증 과장을 교정했다.** 라우팅 구조 검사와 모델 의미 재현을 별도 증거로 기록한다.
- **실패 기록을 Runtime 부담으로 만들지 않았다.** 해결 경험의 기본 소유자는 규칙·테스트·Git이며 예외 진단은 기본 context에서 제외된다.
- **완료 이력이 복구 가능하다.** I0~I6이 별도 체크포인트이고 최종 tree가 clean clone에서 검증됐다.

### 4.3 현재 구현에서 확인된 감점 요인

#### A. 활성 정본의 미래형·과거 Stage 문구가 남아 있음

자동 게이트는 통과하지만 다음 활성 문서는 현재 구현과 어긋나는 문장을 포함한다.

- [정보 소유 구조](INFORMATION_OWNERSHIP.md)는 진입·정책 이름이 이후 Stage에서 확정된다고 쓰고, 이미 존재하는 디렉터리를 “지금 만들지 않는다”고 쓰며, §9 검사가 아직 구현되지 않았다고 적는다.
- [Core 헌장](CHARTER.md)은 G1~G6 검사가 아직 구현되지 않았고 Runtime 판정이 미확정인 것처럼 남아 있다.
- [계층 구조](ARCHITECTURE.md)는 A1~A7 구현 완료를 적으면서도 같은 문서에서 “Stage 15가 구현할 검사”라고 표현한다.
- [Agent 진입 계약](AGENT_ENTRY.md)은 실제 I6 cross-agent 재개가 끝났는데도 Stage 21 이전의 `static-validated` 상태 문구를 유지한다.

따라서 [최종 개선 보고서](CORE_IMPROVEMENT_FINAL_REPORT_2026-08-14.md)의 “활성 문서 간 현재 상태 정합 `pass`”는 실행 상태·상위 완료 문서 수준에서는 맞지만, **모든 활성 정본의 의미 정합까지 포함하면 `partial`로 낮춰야 한다.** 이는 실행 Core를 깨뜨리지는 않지만 다음 Agent의 해석 비용과 완료 주장의 신뢰도를 낮춘다.

#### B. 라우팅 의미 검증이 과선택을 완전히 막지 못함

독립 Agent는 모든 기대 소유자를 포함하고 금지 소유자를 선택하지 않아 공식 조건을 통과했다. 그러나 37개 중 3개에서 fixture가 금지하지 않은 추가 소유자가 선택됐다.

현재 조건은 “기대 포함·금지 배제”를 보장하지만 “필요한 소유자만 선택”은 완전히 보장하지 않는다. 초기 목적의 최소 읽기 비용을 엄격히 평가하려면 케이스별 허용 추가 소유자 정책이나 exact-set 판정이 필요하다.

#### C. 문서 수명주기가 아직 완전히 닫히지 않음

- 예방책 흡수가 끝난 실패 문서가 종료 대기 표식으로 남아 있다.
- `tmp/` 과거 자료도 승인 전 삭제할 수 없어 남아 있다.
- 장문의 최초 설계와 역사 평가 문서는 기본 context에서 제외되지만 저장소 감사 비용은 계속 발생한다.

삭제하지 않은 선택은 권한 정책상 올바르다. 다만 프로젝트의 “필요한 문서만 유지” 목표가 완전히 달성됐다는 뜻은 아니다.

#### D. 실행 환경 검증 범위가 Windows에 한정됨

Python 3.10.20과 3.12.13, 현재 checkout과 clean clone 조합은 충분히 강한 내부 근거다. 그러나 다른 운영체제의 경로·권한·줄바꿈 동작은 현재 최종 증거에 포함되지 않는다.

## 6. 완료 판정과 품질 점수의 관계
