# 에이전트 진입 계약

- 목적: 지원 에이전트의 범위, 에이전트별 진입 파일의 책임과 금지 내용을 소유한다.
- 읽는 시점: 지원 에이전트를 추가·제거할 때, 진입 파일을 바꿀 때.
- 책임: 사용자가 지원 범위를 승인하고 에이전트가 진입 파일을 유지한다.
- 상태: 활성 정본. Stage 5 성공 게이트 통과.
- 관련 권위: [상시 정책](../POLICY.md), [정보 소유 구조](INFORMATION_OWNERSHIP.md).

---

## 1. 지원 범위

| 에이전트 | 진입 파일 | 발견 방식 |
|---|---|---|
| Codex 계열 | `AGENTS.md` | 저장소 루트의 규약 파일을 자동으로 읽는다 |
| Claude 계열 | `CLAUDE.md` | 저장소 루트의 규약 파일을 자동으로 읽고 `@` 참조를 따라간다 |
| 그 외 | `README.md` | 사람이 경로를 제시하거나 에이전트가 루트 개요를 읽는다 |

지원 범위를 넓힐 때는 새 진입 파일을 추가할 뿐 정책 정본을 늘리지 않는다.

## 2. 진입 파일의 책임

진입 파일은 **포인터 전용**이다.

| 포함 | 불포함 |
|---|---|
| 정책 정본으로 가는 링크 하나 | 정책 본문 |
| 읽기 시점 지시 한 줄 | 현재 상태 |
| — | 규칙 절차 |
| — | 에이전트별로 다른 판단 기준 |

에이전트별 진입 파일에 독자적인 정책이나 상태가 있으면 같은 저장소에서 에이전트마다 다른 규칙이 적용된다. 이는 헌장의 P1과 P3에 직접 위배된다.

## 3. 진입 경로

```
AGENTS.md  ─┐
CLAUDE.md  ─┼─→ POLICY.md ─→ STATE.md ─→ 현재 요청에 일치하는 규칙만
README.md  ─┘
```

모든 에이전트가 같은 두 문서에 도달한다. 세 번째 이후로 읽는 문서는 현재 요청에 따라 달라진다.

## 4. 현재 상태 선택

현재 상태 문서는 고정 경로 `STATE.md`다. 저장소 이름·브랜치 이름·디렉터리 이름으로 분기하지 않는다.

참고 구현은 저장소 이름으로 두 상태 문서 중 하나를 고르는 분기를 시작 정책에 두고 있었다. 이는 상위 정책이 하위 이름에 결합된 사례이며 이 저장소에서는 채택하지 않는다.

## 5. 검증

Stage 5 검증 방법의 결과다.

| 검사 | 결과 | 증거 수준 |
|---|---|---|
| 진입 파일 간 정책 내용 차이 | 0. 양쪽 모두 포인터 한 줄 | static-validated |
| 진입 파일의 독자 정책·상태 보유 | 0 | static-validated |
| 모든 진입 경로가 같은 정책 정본에 도달 | 통과 | static-validated |
| 실제 에이전트 새 세션의 읽기 순서 | 미검증 | — |

마지막 행은 이 Stage에서 확인하지 않았다. 실제 에이전트 재개 검증은 Stage 21이 소유한다. 그 전까지 이 계약의 증거 수준은 `static-validated`이며 `cross-agent`가 아니다.

## 6. Host 시점의 미결 문제

이 계약은 **독립 Core를 열었을 때**만 규율한다. Core가 다른 프로젝트의 하위 디렉터리로 들어가면 다음이 미결이다.

| 문제 | 상태 |
|---|---|
| Host의 하위 디렉터리에 있는 진입 파일이 언제 읽히는가 | 미검증 |
| Host 정책과 Core 개발 정책이 충돌할 때 무엇이 이기는가 | 미결 |
| Host 안에서 Core 진입 파일을 보이지 않게 할 필요가 있는가 | 미결 |

이 세 문제는 과거에 네 차례 해법이 시도되었다가 모두 철회된 지점이다. 근본 원인은 "Host의 Core 디렉터리 안에 자동 로드 파일이 있으면 **왜** 안 되는가"의 실제 해가 확정되지 않은 채 해법부터 만든 것이었다.

따라서 이 문제는 Stage 28이 소유하며, 그 전에 해법을 만들지 않는다. Stage 28의 첫 작업은 해법 선택이 아니라 **실제 해의 확정**이다.
