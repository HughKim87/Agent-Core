# Core 내부 계층과 의존 방향

- 목적: Core 내부의 계층, 각 계층의 소유 정보와 공개 인터페이스, 허용·금지 의존 방향을 소유한다.
- 읽는 시점: 구성요소를 어느 계층에 둘지 판단할 때, 새 의존을 추가할 때, 계층 경계 위반을 검사할 때.
- 책임: 사용자가 계층 추가·병합·이동을 승인하고 프로젝트 에이전트가 경계를 유지한다.
- 상태: 활성 정본. 현재 모듈 배정과 구현된 경계 검사 반영.
- 관련 권위: [Core 헌장](CHARTER.md), [Kernel 범위](KERNEL_SCOPE.md) §4의 분해 제약.

---

## 1. 계층 정의

| # | 계층 | 소유 정보 | 공개 인터페이스 |
|---|---|---|---|
| L1 | 진입·정책 | 에이전트 진입, 권위 순서, 작업 등급, 안전 경계, 규칙 라우팅 표 | 정책 정본의 경로와 라우팅 표 |
| L2 | 작업 계약 | 행동별 조건부 절차 규칙 | 각 규칙의 조건·행동·예외·검증 |
| L3 | 정보·문서 | 정보 유형별 단일 정본 소유 구조, 현재 상태, 문서 수명주기 | 정본 위치 선언 |
| L4 | 예외 진단 | 현재 규칙·검사에서 도출할 수 없는 최소 진단 정보 | 명시적으로 필요할 때의 문서 링크 |
| L5 | 검증 도구 | 무결성 검사, 파생 artifact 검증, 통합 게이트 | 검사 등록 인터페이스, 구조화 결과, 종료 상태 |
| L6 | 기반 원시 | 경로 안전 판정, 공통 오류 유형, 결정론적 해시 | 순수 함수와 예외 타입 |
| L7 | 실험 Runtime | 기록 저장소, 작업 상태, 지식·결정·수명주기, 지식 기반 컨텍스트 재평가 | L5에 자기 검사를 등록하는 경로만 |

L6은 블루프린트가 열거한 여섯 계층에 없던 계층이다. [Kernel 범위](KERNEL_SCOPE.md) §4가 확인한 숨은 의존성을 해소하려면 L5와 L7이 공유하는 순수 원시 계층이 필요하다. 근거는 §4에 있다.

## 2. 의존 방향

의존을 세 종류로 나눈다. 종류마다 규칙이 다르다.

| 종류 | 의미 | 허용 방향 |
|---|---|---|
| 라우팅 | 문서가 다른 문서를 읽도록 지시 | L1이 L2·L3 소유자를 선택한다. L2·L3·L4는 서로를 직접 라우팅하지 않음 |
| 구현 | 코드가 코드를 import | L5 → L6, L7 → L6 |
| 검사 | 도구가 파일을 데이터로 읽음 | L5 → L1·L2·L3·L4 |

### 2.1 라우팅

- L1이 유일한 라우터다. L2·L3·L4는 서로를 직접 라우팅하지 않고 L1을 경유한다.
- 상위 정책이 하위 구현의 파일명·경로·내부 구조를 알지 않는다. 필요한 이름은 L3의 선언에서 조회한다.
- 하위 계층이 상위 계층을 라우팅하지 않는다.

### 2.2 구현

- **L5는 L7을 import하지 않는다.** 이것이 §4 해소의 핵심이며 위반 시 실험 기능이 필수 경로에 들어온다.
- L7은 L5를 import하지 않는다. L5가 정의한 등록 인터페이스에 자신을 등록할 뿐이다.
- L6은 아무것도 import하지 않는다. 순수해야 한다.
- 순환 의존은 종류를 불문하고 금지한다.

### 2.3 검사

- L5는 상위 계층의 파일을 데이터로 읽을 수 있다. 이는 계층 역전이 아니다.
- 단 L5는 특정 문서의 의미나 이름을 하드코딩하지 않는다. 검사 대상과 소유자는 L3의 선언에서 조회한다.
- 이 규칙이 없으면 검증 도구가 문서 구조를 고착시켜 L3의 변경을 막는다.

## 3. 실험 격리 메커니즘

L7이 Kernel의 시작과 기본 검증을 막지 않게 하는 방식이다.

1. L5가 검사 등록 인터페이스를 정의한다.
2. L7이 있으면 자기 검사를 등록하고, 없으면 등록 건수가 0이다.
3. L5는 L7의 부재를 `선택 기능 부재`로 보고한다. 이는 실패가 아니다.
4. 통합 게이트는 `선택 기능 부재`와 `필수 기능 실패`를 서로 다른 상태로 반환한다.

이 구조에서 L7 전체를 삭제해도 Kernel의 시작과 필수 검증이 통과한다.

## 4. Stage 2 숨은 의존성의 해소

| 원 문제 | 해소 방식 |
|---|---|
| 유지보수 검증이 지식·수명주기·컨텍스트를 전이 의존 | 검사를 분해했다. 문서·링크·AST·보호 경로 검사는 L5가 소유하고 L6만 의존하며, 현재 채택하지 않은 drift·중복·지식 기반 컨텍스트 재평가는 L7 경계에 남겼다 |
| 파생 artifact 검증이 기록 저장소의 오류 유형에 의존 | 공통 오류 유형을 L6로 승격해 L5가 L6만 사용하게 했다 |
| 단계 설계 fingerprint가 실험 Runtime에 결합 | 결정론적 해시를 L6로 승격하고 승인 무효화 계약을 L2 규칙에 두어 실험 Runtime 의존을 제거했다 |

세 처분 모두 L6의 도입으로 성립한다. L6이 없으면 §1의 계층 정의는 유지되지만 §2.2의 금지 방향을 지킬 수 없다.

## 5. 참고 구현 실측 결과

Stage 3 검증 방법 1·2를 참고 구현에 적용한 결과다. 측정일 2026-08-13, 대상 13개 모듈, AST 기반 import 추출.

| 검사 | 결과 |
|---|---|
| 순환 의존 | **0건** |
| 역방향 의존 | **1건** |
| 중복 공개 인터페이스 | **1건** |
| 상위 정책의 하위 결합 | **1건** |

### 5.1 역방향 의존 1건

유지보수 검증(필수 등급)이 컨텍스트·지식·수명주기 Runtime(선택·실험 등급)을 import한다. §4의 분해로 해소한다.

### 5.2 중복 공개 인터페이스 1건

참고 구현은 패키지 초기화 모듈의 대규모 재export와 CLI의 하위 모듈 직접 import라는 두 공개 표면을 가졌다. 현재 Core는 실제 소비자가 있는 `verify`, `context`, `gate` CLI와 구조화 종료 상태만 공개해 이 결합을 제거했다.

### 5.3 상위 정책의 하위 결합 1건

참고 구현은 시작 정책에서 저장소 이름으로 상태 문서를 분기했다. 현재 Core는 기계 판독 역할 선언에서 고정된 상태 정본을 조회하므로 이 결합을 제거했다.

## 6. 계층 제거 영향

Stage 3 검증 방법 3의 결과다.

| 제거 계층 | Kernel 시작 | 필수 검증 | 상실되는 보장 |
|---|---|---|---|
| L7 실험 Runtime | 가능 | 통과 | 없음 |
| L6 기반 원시 | 불가 | 불가 | 전부 |
| L5 검증 도구 | 가능 | 불가 | G4, G6의 일부 |
| L4 예외 진단 | 가능 | 통과 | 비자명한 과거 진단 참고. G5 예방책은 L2·L5에 남는다 |
| L3 정보·문서 | 가능 | 부분 | G2 |
| L2 작업 계약 | 가능 | 부분 | G3 |
| L1 진입·정책 | 불가 | 불가 | 전부 |

L7 행이 이 Stage의 성공 게이트 3을 충족한다. L6과 L1이 최소 불가결 계층이다.

## 7. 구성요소별 계층 배정

모든 구성요소는 정확히 하나의 계층을 갖는다.

현재 구현 모듈의 기계 판독 배정은 다음 선언이 소유한다.

<!-- core-module-layers:v1 -->
```json
{
  "L5": [
    "src/core_check/__init__.py",
    "src/core_check/__main__.py",
    "src/core_check/cli.py",
    "src/core_check/context.py",
    "src/core_check/declarations.py",
    "src/core_check/derived.py",
    "src/core_check/gate.py",
    "src/core_check/integrity.py",
    "src/core_check/registry.py"
  ],
  "L6": [
    "src/core_check/primitives.py"
  ],
  "L7": []
}
```

| 계층 | 배정된 구성요소 |
|---|---|
| L1 | 에이전트 진입 파일, 상시 정책, 규칙 라우팅 표 |
| L2 | 작업 계약, 단계 작업 설계, 현재 상태와 인수인계, 문서 작업, 보호 데이터와 외부 효과, Core 변경 통제, 버전 관리, 실패 경험의 예방책 흡수, 규칙 거버넌스 |
| L3 | 정보 책임 구조, 현재 상태 문서, 문서 수명주기 |
| L4 | 규칙·검사에서 도출할 수 없는 최소 진단 문서 |
| L5 | 문서·링크·Schema·AST 검사, 보호 경로 검사, 파생 artifact 검증, 통합 게이트, 선언 해석, 시작 컨텍스트 구성, 공개 CLI |
| L6 | 경로 안전 판정, 공통 오류 유형, 결정론적 해시 |
| L7 | 기록 저장소, 작업 상태 Runtime, 지식·결정 Runtime, 수명주기 Runtime, drift·중복 탐지 |

현재 `context.py`는 필수 통합 게이트가 직접 호출하는 시작 문맥 예산 검사이므로 L5다. 향후 실험 Runtime의 지식 선택·재평가는 L7에 남고, L5에 자기 검사를 등록하는 경계를 지킨다.

## 8. 검사 가능한 형태의 경계 규칙

현재 통합 무결성 검사가 강제하는 항목이다.

| ID | 검사 |
|---|---|
| A1 | L5 코드가 L7 모듈을 import하지 않는다 |
| A2 | L6 코드가 어떤 내부 모듈도 import하지 않는다 |
| A3 | 모듈 import 그래프에 순환이 없다 |
| A4 | L2·L3·L4 문서가 서로를 직접 라우팅하지 않는다 |
| A5 | 모든 활성 규칙이 L1에서 정확히 한 번 라우팅된다 |
| A6 | L5 코드에 L1~L4의 문서 이름이 상수로 박혀 있지 않다 |
| A7 | 모든 구성요소가 정확히 하나의 계층에 배정되어 있다 |

## 9. 이 문서의 한계

- 실제 디렉터리와 문서 역할은 [정보 소유 구조](INFORMATION_OWNERSHIP.md), 모듈 배정은 §7의 기계 판독 선언이 소유한다.
- §8의 A1~A7은 통합 무결성 검사와 결함 주입 테스트에 구현되어 있다.
- §4의 분해는 현재 L5·L6 모듈 구조에 적용됐다. 마지막 완료 snapshot에서 L7 없이 회귀 테스트와 통합 게이트가 통과했으며 현재 작업의 최신 판정은 `STATE.md`가 소유한다.
