# Host 연결 단계의 진입 조건

- 목적: Host 연결을 시작하기 위한 선행 조건과 결정해야 할 항목만 소유한다. 해법은 소유하지 않는다.
- 읽는 시점: Host 연결 작업을 시작할지 판단할 때, 그 단계의 첫 작업을 정할 때.
- 책임: 사용자가 다음 단계의 착수를 승인하고 에이전트가 조건 충족 여부를 보고한다.
- 상태: 활성 정본. Stage 28 성공 게이트 통과.
- 관련 권위: [독립 Core 1차 완료 판정](COMPLETION.md), [Core 헌장](CHARTER.md).

**이 문서는 Host 연결의 설계나 구현이 아니다.** 여기에 해법을 적지 않는다.

---

## 1. 선행 조건

| 조건 | 상태 |
|---|---|
| 독립 Core 1차 완료 판정 통과 | 충족 |
| 공개 계약과 버전 선언이 단일 정본으로 존재 | 충족 |
| Host 정보 없이 Kernel 검증이 통과 | 충족 |
| Core 안에 특정 Host 이름·경로가 없음 | 충족 |

네 조건이 모두 충족되었으므로 Host 연결 단계를 별도 작업으로 시작할 수 있다.

## 2. Host가 사용할 공개 계약

Host는 아래만 의존한다. 그 외 Core 내부 구조에 의존하면 Core 변경이 Host를 깨뜨린다.

| 계약 | 내용 |
|---|---|
| 규칙 소유자 | `rules/` 의 각 규칙 문서. 라우팅은 Host의 정책이 소유한다 |
| 검증 진입점 | `core-check gate` 와 종료 상태 0·1·2 |
| 검증 결과 구조 | 단계별 이름·상태·필수 여부·설명 |
| 실패 예방 | 관련 규칙·결함 주입 테스트. `failures/`는 비자명한 예외 진단만 선택적으로 유지 |
| 버전 선언 | 호환성 선언 블록 |

## 3. Core가 알지 말아야 할 것

| 항목 | 이유 |
|---|---|
| Host의 이름과 디렉터리 구조 | 상위 정책이 하위 이름을 알면 이식되지 않는다 |
| Host의 도메인 어휘 | 도메인은 Host가 소유한다 |
| Host의 보호 경로 이름 | 선언에서 조회한다 |
| Host의 상태 문서 위치 | Host의 정책이 소유한다 |
| Host가 몇 개인지 | Core는 자기 자신만 안다 |

## 4. 다음 단계에서 결정해야 할 항목

해법을 지금 고르지 않는다. 아래는 결정 대상 목록이다.

| # | 결정 항목 |
|---|---|
| 1 | Host가 Core를 어떤 방식으로 가져오는가 |
| 2 | Core의 버전을 Host가 어떻게 고정하고 갱신하는가 |
| 3 | Host 안의 Core를 직접 수정하지 못하게 어디까지 강제할 수 있는가 |
| 4 | Host의 루트 문서와 Core의 규칙을 어떻게 연결하는가 |
| 5 | Host 안에서 Core의 진입 파일을 어떻게 처리하는가 |
| 6 | Host가 여러 개일 때 Core가 무엇을 선언으로 받아야 하는가 |
| 7 | 기존 도메인 프로젝트의 결합을 어떤 순서로 푸는가 |

후보 해법은 현재 방식과 비교한 **총 운영 비용**으로 평가한다. 추가 문서 읽기, 세션·저장소 수, 동기화·갱신 단계, 복구 부담을 각각 포함하며 한 항목의 편의만으로 선택하지 않는다.

Core 수정 통제는 같은 수준의 보장으로 묶지 않는다. 안내·예방, 즉시 차단, 변경 탐지, commit·merge 차단, 복구를 구분하고 각 후보가 실제로 제공하는 수준만 주장한다.

## 5. 다음 단계의 첫 작업 — 해법이 아니다

**5번 항목의 실제 해를 먼저 확정한다.**

이 문제는 과거에 네 차례 해법이 시도되었다가 모두 철회되었다. 배포 브랜치, 별도 브랜치, 일반 문서 단일화, bootstrap 생성이 각각 시도되었다.

네 번 모두 같은 이유로 실패했다. **"Host의 Core 디렉터리 안에 자동 로드 파일이 있으면 왜 안 되는가"의 실제 해가 확정되지 않은 채 해법부터 만들었다.**

따라서 다음 단계의 첫 작업은 해법 선택이 아니라 다음 세 가지를 실측으로 확정하는 것이다.

1. 각 에이전트가 하위 디렉터리의 지침 파일을 **언제 실제로** 읽는가. 문서 근거가 아니라 최소 재현으로 확인한다.
2. 그 파일이 읽혔을 때 **어떤 구체적 해**가 발생하는가. 발생하지 않으면 이 문제는 문제가 아니다.
3. 해가 발생한다면 그 해를 막는 가장 단순한 방법은 무엇인가.

1번과 2번이 확정되기 전에 저장소 구조나 브랜치를 만들지 않는다.

## 6. 실증 조건

Host 연결의 완료는 다음으로만 판정한다.

- 첫 번째 실제 Host에서 clean clone 후 게이트 통과
- **두 번째 서로 다른 실제 Host**에서 Core 변경 0건으로 게이트 통과

합성 호스트나 임시 디렉터리의 통과는 실증이 아니다. 과거에 합성 호스트 통과를 실증으로 보고한 사례가 있으며 그것은 사실이 아니었다.

실제 Host 연결 검증은 아직 수행되지 않았다.

## 7. 이 단계에서 하지 않은 것

- Host 연결 방식을 고르지 않았다.
- 저장소 구조를 바꾸지 않았다.
- 브랜치를 만들지 않았다.
- 기존 도메인 프로젝트를 건드리지 않았다.

이것들은 다음 단계의 별도 설계와 승인으로 시작한다.
